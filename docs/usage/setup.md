# Getting started

This is dockhand's guide: the one-time setup, and the straight path from a port's new release to its pull request. `dockhand usage <topic>` gives the rest of it, a workflow at a time: `hand-edits`, `unattended`, `checks`, `review`, `batches`, `new-port`, and `agents`. `dockhand <command> --help` is the reference for any one command, and `dockhand config` shows every setting in effect.

## Setting up

In your clone of `macports/macports-ports`, the one with your fork as a remote:

```sh
dockhand setup
```

`setup` first checks the Git dockhand runs, `git` on `PATH` or `$GIT_BIN`, and refuses one older than 2.40, which `rebase` needs; macOS's own Git is new enough on current releases, and `sudo port install git` gets one otherwise. It then registers the checkout and finds its remote for `macports/macports-ports`, whatever it is called. It also chooses where branch worktrees go: `~/Source/macports-branches`, wherever the clone is, unless `--worktrees <dir>` or the configuration's `worktrees` names another. Then it reports what dockhand runs with: Git, MacPorts, the places a check can build, the GitHub login, and its records. On a terminal it offers what's missing, each in turn, each declined by answering no: the GitHub login (`setup github`); the maintainers line the ports naming your GitHub login write, which it writes to the configuration file; and last, off unless you say yes, since it downloads macOS, the Tart image of this Mac's release (`setup tart`). `setup -y` skips these offers. Run `setup` again at any time to check your configuration. `init`, `providers`, and `auth`, which it replaces, are gone, `setup github` logging in and out and `setup` showing which GitHub account is signed in. `setup --json` gives the report for a script, its `github` the account, the login's `source`, and `renews_until`, or the `problem` there's none to use.

Every command works on one ports checkout: `--tree` (`-t`), else `$MACPORTS_TREE`, else the directory you are in. Inside a branch's worktree, that is the checkout it belongs to, and the branch checked out there is the one a command means, `$MACPORTS_TREE` or not.

### Somewhere to build

`dockhand setup` reports the places a check can build and whether each is ready. The usual first step is a Tart image of this Mac's macOS:

```sh
sudo port install tart
dockhand setup tart
```

See [Providers](checks.md#where-it-builds) for the others and for more releases.

### A GitHub login

`submit`, the github provider, and `status --refresh` need to act as you on GitHub. Dockhand takes the first of these it finds:

1. `GH_TOKEN`, then `GITHUB_TOKEN`;
2. its own login, from `dockhand setup github`, kept in the macOS Keychain. The login is a one-time code in the browser, asking for the `public_repo` scope and a refresh token (`offline_access`). Its access token lasts eight hours, and dockhand renews it, `serve` included, with a refresh token that lasts six months from its last use: a login used at least once every six months never needs making again. A login an earlier dockhand kept, a single token, is asked to be made again;
3. the GitHub CLI's login, through `gh auth token`.

`dockhand setup` shows your GitHub account, the credential source, and how long Dockhand can renew its own login; `dockhand setup github --logout` removes it, and names GitHub's page where you revoke dockhand's authorization too. `setup github --no-browser` prints the sign-in address rather than opening it, and `--client-id` names another OAuth application, as `DOCKHAND_GITHUB_CLIENT_ID` does. A running `serve` uses a new login without a restart, and says once when its login can't renew itself. Reading public data, as `outdated` does, needs none, and goes on without one; where none was found, it isn't looked for again for five minutes, so a running `serve` picks up a login made meanwhile soon after.

### The configuration file

Settings live in `~/.dockhand/config.toml`, or the file `$DOCKHAND_CONFIG` names. Nothing in it is required, and an unknown key is refused by name. Command-line flags override environment variables, which override the configuration file. [All the settings](#settings) are listed at the end of this page. Two are worth setting early:

```toml
maintainer = "{example.org:you @you} openmaintainer"   # your maintainers line, for --mine and create

[build]
default = "both"                                # where checks build unless --build or --on says otherwise
profiles.both = { releases = ["sequoia", "tahoe"] }
```

## Branches

All work happens on branches. A branch is an ordinary Git branch of the ports tree, named `dockhand/<name>`, with a base on MacPorts' master and at most one pull request. Dockhand keeps a record of each one it tracks.

- **`start <name>`** creates `dockhand/<name>` from master, fetched just now, in a worktree of its own. `--port <port>`, more than once if need be, brings those ports' directories in from the start; with no name, it's named for the first port and a short ID. `--here` creates it in this checkout instead, which must have no uncommitted changes to tracked files. `start --from <branch>` takes a merged branch's commits past what its pull request merged, the follow-up `status` names, and picks them onto the new branch; a commit master already has is dropped, and a conflict starts nothing.
- **`update`, `checksums`, `create`, and `edit` with `--new`**, or with no branch changing the port, start a branch named for what it does: an update's for the port and its new version, `dockhand/jq-1.8.1`; `create`'s `mods-new`, `checksums`' `jq-checksums`, `revbump`'s `gdal-rebuild`, and an edit's, with nothing more to say, the port and a short ID, `jq-4f2a`. The ID is added to the others only where the name is taken now, by a branch that isn't merged, a Git branch, or a worktree, so `jq-1.8.1-4f2a`; a merged branch, once cleaned, frees its name. A branch named for a version is renamed, before it has a pull request, when an update moves it to another: `jq-1.8.1` becomes `jq-1.8.2`, its worktree staying where it is. A version update starts it once there is an edit to make, so a port already current starts nothing. `revbump` starts one by itself unless `-b` names one or you are in one, since a rebuild has its own reason.
- **`adopt [branch]`** tracks a branch you made yourself, as it stands. Its base is where it leaves master. Where it's checked out, that's its worktree; where it isn't checked out anywhere, adopt checks it out as `start` does, in a worktree of dockhand's, rather than leaving `git switch` to switch your own checkout. A worktree you add for an adopted branch later, with `git worktree add`, is found and recorded the next time a command needs it, or when you adopt it again.


A branch's worktree is sparse: it holds `_resources` and the ports the branch changes. `edit <port>` brings another port's directory in, and once `tidy` has committed the branch's work, a directory it doesn't change is left out again, in a worktree dockhand made; one you made stays as wide as you made it. `dockhand path <branch>` prints the worktree's directory, for `cd "$(dockhand path jq-4f2a)"` or an editor; `path -p jq` finds it by its port. The `dockhand/` prefix is optional wherever a branch is named.


To try a branch's port with MacPorts itself, see `dockhand usage hand-edits`.

A command finds its branch from `-b` (`--branch`), its exact name, with or without `dockhand/`, which the shell completes with each open branch's pull request and title; else from the branch checked out where it runs. `-b` names an existing branch, everywhere: a name no tracked branch has is refused, "no tracked branch named jq-typo; --new=jq-typo starts one", so a typo starts nothing. An authoring command, `update`, `revbump`, `edit`, `checksums`, and `create`, starts a branch of a name with `--new=<name>`, from master, and says so first; `--new` alone names it for the port, or the version an update moves to. A Git branch of a name that dockhand doesn't track is refused, pointing at `adopt`, and a merged branch's name is said from its record, which `--new=<name>` reuses on purpose; a `--plan` starts nothing, planning an update against master instead. A branch is the port's from the moment it's started for it, by `start --port`, or by an authoring command, before it changes the port. A command about a whole branch, `check`, `tidy`, `submit`, `ship`, `rebase`, `diff`, `impact`, `open`, `status`, `path`, and `archive`, also takes `-p <port>`, the open branch that changes the port (its subports included, where its change record says), and `--pr <number>`, the branch tracking that pull request; one of the three at a time, and `status`, `path`, and `archive` keep their bare name argument too. The run commands, `logs`, `wait`, `cancel`, and `retry`, take them for the branch's latest check. `-p` with one branch changing the port works there, and says so first; with several, those changing more than the port's revision first, it asks on a terminal and refuses in a script, naming them. Any of them beats where the command runs, and says so where the two differ: "jq-4k2p (not uxprobe, checked out here)". An authoring command run on master names its port already, so with neither `-b` nor a worktree it works in the one open branch that changes the port, where exactly one does, and starts one where none does, as `revbump` always has, saying which on its first line, in a script too; `--new` starts another. Where several do, it asks once on a terminal, which one or a new one, and without one refuses, naming them. A branch you made yourself and haven't adopted that changes the port is refused, with a pointer to `adopt`. Output always names a branch exactly, since a line copied later must mean the same branch then. A branch you rename with Git keeps its record, recognized by its worktree or its pull request's last push.

## Changing ports

These commands edit files in the branch's worktree without committing them; `ship` and `bump` take an update on to its commit, check, and pull request. Each remembers what it did, so `tidy` can later write the commit subject a MacPorts reviewer expects, beside your own changes too, while every line it wrote still stands. `--plan` shows the edit and changes nothing.

### update

```sh
dockhand update jq --new           # the newest release, in a new branch
dockhand update jq 1.8.1           # a version you name, in the branch checked out here
dockhand update jq --new --plan    # what would change, from master, starting nothing
```

A plan never starts a branch. With no branch to plan in, none named and none checked out here or changing the port, `update jq --plan` plans on master too. A branch you made with Git, which dockhand doesn't track, counts as none while it doesn't change the port, and the plan says so. Where it does, in commits, edits, or files it adds, a plan on master would leave your changes out, so it refuses, and names `adopt`, which lets the plan read them, and `--new --plan`, which plans without them. Edits to the port on master itself, not committed, are refused the same way. `update jq` on such a branch starts a branch as it would on master, or refuses where the branch changes the port.

`update` lists other open pull requests for the port, as `submit --plan` does. It continues even if it finds one. It also names the port's plain-HTTP URLs, its `homepage` and its `master_sites` (never a mirror group, which is MacPorts' own), with whether the `https://` form answers, since MacPorts prefers HTTPS. It leaves them as they are, since changing them is the maintainer's call; `checksums` names them too. Dockhand probes each URL once, with up to four probes running at a time and a ten-second timeout per probe. It skips these probes when the port is already current. It finds the newest release the Portfile's own rules accept, from the project's GitHub or GitLab tags and releases, or its livecheck. A tag that compares newer than the port's version but was made on a commit older than the port's own tag's is set aside, as an old tag oddly spelled, dolt's `v040.15` for `v0.40.15`, would be; a release made on a branch, or tagged late, looks the same. If no other newer release is found, `update` cannot tell whether the port is current. It leaves the files unchanged, exits with code 3, and prints `dockhand update <port> <version>` so you can select the tag after confirming it is a release. It moves the version, resets the revision, and fills in checksums, a variant's own too: git's `+doc` appends git-htmldocs' in its body, and a variant that isn't on by default and fetches an archive of its own is asked about, so none keeps the old version's. For a Go or Rust port whose Portfile lists its dependencies, it regenerates the list with `go2port` or `cargo2port`, as [Go and Rust dependencies](#go-and-rust-dependencies) says. Where a patch hook edits the manifest the list is generated from, as editors/fresh's post-patch edits Cargo.toml, the list must be exactly what the current version's lock gives, or the update is refused. Where that can't be checked, because the module moved since, the list is regenerated, and that holds for a look like an upstream finding (`manifest-hook`). `--shared-release` moves every subport sharing the port's release, each subport's own archives fetched and its own checksums written where it declares them, as xapian-core's bindings do, and `--keep-old-checksums` refreshes legacy md5 or sha1 checksums in place rather than rewriting them as rmd160, sha256, and size. `--with-obsolete` also moves an obsolete stub the port replaces, as terraform beside terraform-1.16, to the same version in the same commit. `--closes <ticket>` names a Trac ticket the update closes, by number, which `tidy` writes as the commit's `Closes:` trailer with its URL; repeat it for more. Each Portfile an edit writes gets MacPorts' modeline as its first line; `--keep-modeline` leaves that line as it was, and `ship`, `bump`, `checksums`, `revbump`, and `serve` take it too. Where GitHub answers the port's repository by another name, by a redirect, it says so, a new owner as a transfer, and that holds an update nobody looks over; `--follow-moves` points `github.setup` at the new name, which is the person's choice and never made unasked. Where `update` refuses, as an edit it doesn't make, `--hand-edit` writes its best attempt for you to finish: the version, with the revision reset, and the checksums of the new version's archives where it can fetch them, saying what it couldn't write. The attempt is your hand edit, not dockhand's: no edit of dockhand's is recorded, and the refusal is, so `tidy`'s plan, `status`, the hold on an unattended commit, and the pull request's Description each say it, with whether the attempt is as written or adjusted by hand. `ship`, `bump`, and `serve` never take it.

It then compares the old and new source archives, and reports what a passing build can't catch: a changed license file, said by what its text is at each end as pkg.go.dev's classifier reads it, "was MIT, now ISC, by its text" or "is still MIT by its text, and changed beside it" (one whose copyright lines moved only their years is said with the line, and holds nothing; one that only drops text, but for its years, how it wraps, and the punctuation its words end with, says how many words it drops and from where, and still holds, since dropping text can narrow a license, as "MIT or GPL-2" losing "MIT or" would; any other is said with what the project's manifest declares beside the Portfile's license line, as "Cargo.toml says EUPL-1.2, and the Portfile says MIT", and once the candidate's line names what the manifest declares, or what the file's text now is, where the base's didn't, it's said with a `·`; a declaration that isn't an SPDX expression is said to be none), a changed build file, a new dependency a Python project declares, which is another port the software finds when it runs, a Python requirement that the port providing it, among those the Portfile depends on, doesn't meet at the version the branch has of it (read with its condition, its PEP 508 marker, as the port's build on macOS sees it, so a Windows-only pin asks nothing, and a requirement newly applying to macOS holds as one added), or, for a Go port built in module mode, a Go release its go.mod requires that the Portfile's `go.toolchain_min` doesn't gate on, or that the Go the Portfile pins doesn't provide, by `go.bin` or a build or library dependency on one of the `go-1.NN` toolchains, as trivy pinned `go-1.26` where 0.75.0's go.mod requires 1.27.0 (a build with the pin fails, and it's said before a check, as a pin that may be obsolete), or, for a Python project, a `requires-python` that leaves out a Python the port builds for (its `python.versions`, or the Python an application's port pins), since a build needn't enforce it. A `requires-python` that moves is said with a `·` otherwise, with whether it admits the port's Pythons; one whose verdict turns on a patch release, as `>=3.13.2`'s does on 3.13, is judged by the release MacPorts has. A port that pins an older Python than the python PortGroup's default, as sshuttle pins 3.13 where the default is 3.14, hears it with a `·`, unless the new version's `requires-python` leaves the default out. A minimum dockhand raised, to go.mod's `go` directive as go.mod writes it, or one that already gates on its series, is said too, and holds nothing, unless the Portfile pins an older Go; `update` warns of such a pin as it reads go.mod, and leaves it for the maintainer to remove. What the port was before the update is the base these are weighed against: a requirement its provider didn't meet there either, a Go requirement its minimum didn't gate on there either, or a Go pin the base had that didn't meet the base's go.mod either, is said and holds nothing, since an update isn't an audit of everything the port already was. A Python requirement whose provider's version can't be read holds, since a passing build may not settle it; one no port the Portfile depends on is named for is said and holds nothing, since a port needn't be named for its package (py313-yaml is PyYAML), unless the Portfile depended on one that is and no longer does, which holds. Only the files of the build systems the port uses hold, as MacPorts says it uses them, by its PortGroups and its configure script: flatbuffers, built with CMake, isn't held by its `package.json` or `Package.swift`, which are set apart, named in the line that says what was read. Where MacPorts can't say, as for a port that builds by its own commands, every file holds. A build file whose change is only the project's version, declared as its build system declares it, as `project(nuspell VERSION 5.1.9)`, is said with the line, and holds nothing; any other change to it holds, a dependency's minimum that happens to move with the version, as `find_package(SomeLibrary 1.0)`, included, unless it's a file the Python project's build backend doesn't read, as hatchling doesn't read the `setup.cfg` sshuttle keeps bumpversion's version in, which is said with a `·`. A CMakeLists.txt's change says what it does to the options it offers, with their defaults, and the packages it finds, with the `if()` each sits under, "option FLB_KAFKA added, off by default; find_package(OpenSSL) added, under FLB_TLS", or that it changes neither, and holds as any other change does; what else changes, it places by the `if()` it's under, "lines change under if(FLB_ALL), outside any if()", so the look starts where the change is. One that only adds options holds nothing: each is said with its default, which the port builds with, and what one off by default gates, as `find_package(Protobuf)` under an option off by default, isn't reached by the default build; what one on by default gates, a default that flips, and an option removed, still hold. Nor does a change the default build can't reach hold, under an `if()` whose condition is false where each option off by default that nothing turns on is off, as fluent-bit's under `if(FLB_ALL)`: "changes only what the default build doesn't reach, under if(FLB_ALL): neither it nor the Portfile turns FLB_ALL on". An option is taken as off where only `option()` declares it, off, no other command in the file but the `if()`s that test it and `message()` takes it as an argument, as `set()` or a macro setting it would, and the Portfile doesn't name it anywhere, in any variant, as `-DFLB_ALL=ON` would. The files a CMakeLists.txt `include()`s, by their path or as modules on its `CMAKE_MODULE_PATH`, are read in their place, as CMake reads them: an option one declares or flips is said as the root's would be, one it sets isn't taken as off, and a change in one is placed there, "outside any if() in cmake/plugins_options.cmake"; a path built from another variable, and a project's own macro, as fluent-bit's `DEFINE_OPTION`, aren't followed, and an option set that way still holds what it gates. Comments, and a version set in parts, as `set(FLB_VERSION_PATCH 3)`, aren't changes. What it couldn't read, it says, and that holds as a change would: a manifest it can't parse, one that reads another file or declares its dependencies dynamically, and a file past the 1 MiB it reads. A Go module or a Rust crate is compiled into what the port builds, and a check builds with only what the port declares, so what go.mod and Cargo.toml change is counted, "go.mod: 2 added, 4 moved", and holds nothing, as is what Cargo.lock changes of the crates it pins from crates.io or Git, a workspace's own crates left out, nor does what couldn't be read of them. A Node package is fetched and bundled by the build, as npm and yarn install it, and no port provides one, so what a `package.json` changes, a workspace's included, is counted the same way. A crate new to Cargo.lock that links a native library, as a `-sys` crate does, is listed with a `·` where MacPorts has a port for the library, named, as `archivers/zstd`: the crate may link a copy it finds installed, and the Portfile may declare the port instead. A library MacPorts has no port for, as `aws-lc`, is set apart in the comparison's coverage rather than listed, and one whose port couldn't be looked for is listed as one MacPorts may provide. One gone from it is listed where the Portfile still has a PortGroup or a dependency named for the library, as `PortGroup openssl` once `openssl-sys` goes, since what was there for the crate still reaches the build: zola's put OpenSSL 3's headers before aws-lc's own. For a Go or Cargo port whose Portfile lists its dependencies, the old and new source archives are compared without them. Each version is read where the port builds, the subdirectory its worksrcdir names below the archive's top, as a monorepo's Python bindings in `bindings/python`, with the license files at the top as well; a flat archive is read at its root, and an archive holding several top-level directories and nothing beside them isn't read, which holds. A Node project's workspaces, as its `package.json` names them, are read with it, since yarn and npm install them together: a dependency one of them adds or moves is said as the root's would be. A Cargo workspace's members, by its `members` and `exclude`, are read with its root too, as the Cargo Book has them: a license or dependency a crate inherits with `workspace = true` reads as the workspace's, so cargo's and uv's licenses are found where they read as none, a renamed dependency as the crate it is, and one only another platform's target table has, as `cfg(windows)`'s, isn't counted; the members' changes are counted in one line. The current version's archives are compared as MacPorts shipped them, checked against the Portfile's checksums, each with the archive that replaces it in every context that fetches them, as gh's source tarball and older systems' prebuilt zip each are. A port that fetches more than one archive has each compared with the one it corresponds to, by its name, by its name but for its version, or as the one left on each side, never by its place in the list: one the new version no longer fetches is said with a `·`, one no archive of the base's corresponds to by name holds, uncompared, and what each finds names its archive, so two archives' license changes are two, while a change every archive carries alike, as a source shipped as both a tar.gz and a zip does, is said once. They're fetched from where MacPorts' own fetch plan finds them, as the new version's are, so a port on a mirror group, such as PyPI's, CPAN's, or GNU's, is compared like any other. Where upstream now serves something else under the same name, as after a stealth update, or nothing, they come from MacPorts' distfiles mirror, under the port's `dist_subdir`; where neither has them, the update says so, and the comparison holds, as decision D4 in [Decisions](../decisions.md) has it. Patches it couldn't check before the build, a Git-fetched port's, are listed with a `·`; the build applies them. Those that apply are counted, "6 patches apply to 5.1.3's source", so a check that found nothing isn't taken for none. A patch the new source already holds, one that applies in reverse as upstream merging it leaves it, is dropped, from the Portfile's `patchfiles` and from `files/`, and said: "Dropped patch fix.diff, which the new source already holds; its file goes too." Only one written as a literal word of the top-level `patchfiles` is dropped; one in a variant or a condition stays a patch that no longer applies, for you to drop. Below what it found, a line says what it read and checked: "Read Cargo.lock, Cargo.toml, LICENSE; 9 patches apply; not compared, as the port doesn't build with them: package.json (node)". A revision's assessment, as `submit` and `review` make it, checks its patches the same way, and each patch the base applied that the revision drops, with whether it still applies to the new source; an update's own assessment, which the revision's reuses, checks them alike, taking the patches the update already checked as they stand. A port new to the tree has nothing earlier to compare: its license file is said with the Portfile's license line, "upstream ships LICENSE, and the Portfile says MIT", holding only where the project's manifest declares a license the line doesn't name, and its build files, all new to it, aren't said. `dockhand diff --source jq` shows the same comparison file by file. With `--json`, the result's `upstream` holds it: each change, with the rule that raised it, what it's about, and, for a port of more than one archive, the archive it's in (`source`), which identify it, and its class, how the update stands against its base on it (`introduced`, `present`, or `unknown-baseline`); why the archives couldn't be compared if they couldn't; what it read, what it checked, and what it set apart, and why, under `coverage`; and whether it holds the update for a look before `serve` or `bump` submits it, as a change a build can't catch does, and as archives it couldn't compare do. It is absent for a port with no archives, such as one fetched with Git.

`--revbump-dependents` also bumps the revision of every port that links the updated one directly, found in the port index at the branch's base, so users rebuild them. The index records only what default variants depend on, so a port that links it only under a variant, as enchant2 links nuspell under `+nuspell`, is found by asking MacPorts about the variants whose Portfile text names it, listed apart, and bumped too. `--except <port>` leaves one out, either kind, and the pull request's description lists what it left out, so a reviewer can disagree. `impact` lists such a dependent with its variant, and doesn't suggest building it, since `check --also` builds default variants. `tidy` commits each as "<port>: rebuild for <updated> <version>".

### Go and Rust dependencies

An update regenerates a Go port's `go.vendors`, and a Rust port's `cargo.crates` and `cargo.crates_github`, from the new release's `go.mod` or `Cargo.lock`, with `go2port` or `cargo2port`; `create` and `checksums` do the same for a block declared empty. Dockhand finds them on `PATH` (`sudo port install go2port cargo2port`), and `setup` reports whether each is there. A port that needs one that's missing is refused before anything is downloaded or edited; a Go port that declares no `go.vendors` needs neither.

- Before it changes a block, dockhand regenerates the current version's and compares it with what the Portfile declares. A difference is a maintainer's override, so the update stops, naming the crates or modules, for you to prepare by hand. One kind goes on: a crate pinned at another version than the old lock's is dropped once the new lock has it at that version or later, and the update says so.
- Rows whose values didn't change are kept byte for byte, and changed or new rows line up on the block's columns, so moving a dozen crates is a dozen-line diff.
- The helpers' output must cover the manifest exactly: every Go requirement once, at its version, with a checksum, and every crate Cargo.lock takes from crates.io at its version and checksum. Go workspaces, `go.mod`'s `replace` and `exclude`, another Cargo registry, a declaration built from an expression, and Go and Cargo blocks in one Portfile are refused, for preparation by hand.
- A Git crate must come from a `https://github.com` repository at a full commit. `cargo.crates_github` declares branches alone, so with an offline build, the cargo PortGroup's default, a crate pinned by tag, `rev`, or the default branch is refused, naming it; a port that empties `cargo.offline_cmd` leaves such crates to Cargo at build time, and the update names them.
- With `cargo.update` on, the source must ship a Cargo.lock, and the update says MacPorts re-resolves offline against the crates; dockhand never sets or clears the option. `cargo.dir` must be inside the source.

A consistent block is not proof the port builds; the check is.

### ship

```sh
dockhand ship jq                   # update, commit, check, and submit, asking once
dockhand ship jq --to check        # stop once the check is queued and run
dockhand ship -b jq-1.8.1          # carry a branch on from where it stands
dockhand ship --mine --to commit   # your outdated ports, a branch and a commit each
dockhand ship --passing            # the branches whose checks passed, to their pull requests
```

`ship` carries each change as far as `--to` says, `commit`, `check`, or `submit`, the default, from wherever it is now. A port names a version update from fresh master, in a branch of its own, or the open branch already changing it, which goes on from where it stands, brought to the newest release first where it isn't there; `-b`, `-p`, and `--pr` name a branch, and with none, the branch checked out here. `--mine` takes your ports with newer releases, as `outdated --mine` finds them, at the releases it found, and says each it leaves and counts the rest, and `--maintainer`, `--category`, and `--not-maintainer` take another selection the same way, as `outdated` makes it; `--passing` the branches whose checks passed for their commits, with no pull request of those commits yet. Run again, it resumes: a change already past `--to` is left as it is, a commit a check already passed is not checked again, and a check still queued or running for the same files is followed rather than started again. A batch carries each change to its check, queued, before it sees any check through, and submits each as its check passes: `serve` runs them side by side where it runs, and they run here one by one where it doesn't.

`ship` shows one plan with a row for each change. If the plan includes submission, each row also shows the current submission preview and any reasons for pausing. In a terminal, it asks you to confirm the plan once. `--yes` skips confirmation. Outside a terminal, running the command authorizes the plan without a prompt. With `--yes` or without a terminal nobody looks along the way, so it holds where `serve` would: a new major version before anything is prepared, a commit that isn't dockhand's own edits, and what holds a submission. A check builds where `build.unattended`'s profile says then, and else where `build.default`'s does; `--build` or `--on` names another, settled before anything is edited. It takes `update`'s edit flags, check's `--tests`, and submit's `--type`, `--draft`, `--tested-binaries`, `--tested-variants`, `--title`, `--note`, and `--skip-notification`, each stage's defined once, as `bump` does. `--draft` opens a draft pull request even if the check did not pass. The command returns the check's exit code. If a stage stops one change, `ship` continues with the others. It exits with code 1 if none complete, or code 3 if some require review. With `--json`, `changes` holds each change's update, with `tidy`, `check`, and `submit` inside it, as far as it went, and `skipped` the ports `--mine` left, with why.

`bump` is `ship` asking nothing; `dockhand usage unattended` says where it stops. `dockhand usage batches` takes many ports at once, and `dockhand usage new-port` a port MacPorts doesn't have.

## Seeing where things are

- **`status`** shows each open branch, with its ports, its work, its latest check, and its pull request each in a column. A check of the files as they are now counts, whichever it was, as submit counts it: a branch restored to files an earlier check passed shows that check, and each environment's newest result stands beside the others'. Above them is a list of what needs you, each row ending with the command that moves it forward. A passed branch whose Git-fetched port's tag named another commit when its update chose the release than when the check planned it says so there, and under its release, as submit's preview does, from what's recorded; whether a tag names another commit now takes the network, which `status` never reads, so `submit` alone says that. With `--json`, a branch's `moved` lists them. A branch with no pull request whose every change master has, as dockhand last fetched master, landed by another route, and says so, with `archive` to set it aside, rather than asking for it to be committed; `--json` gives that master as `on_master`. Its ports are the subports its files change, where they've been evaluated: an update, `checksums`, `revbump`, a check, or `submit` records which of a directory's subports the files change, as MacPorts evaluates them against the base, so a branch updating terraform-1.16 shows terraform-1.16, not all 24 of terraform's ports. Status evaluates nothing itself: a directory whose files no command has evaluated yet, as after a hand edit, is shown as the port it's named for, "(not yet evaluated)", and one whose change this Mac's evaluation doesn't see, as a block for another macOS release, "(no change this Mac's evaluation sees)". With `--json`, `changed_ports` lists them and `port_notes` says which are their directories'. Below the branches it lists the checks queued and running, each with its branch, what it checks, where, and its state, a check whose process ended said to be stopped; with `--json`, `queue` lists them. Below those it lists the dockhand processes working on the checkout, each with its pid, kind, build, start, and what it does, leading the queue or running a check, and says one whose build expects another database schema than the database's; with `--json`, `processes` lists them. Commands that open no session, such as `submit` and `update`, aren't listed. Inside a worktree, or naming a branch, it shows that branch in detail. `--attention` prints only what needs you and exits 3 when anything does, for a prompt or a script. `-b` and `--pr` name a branch, shown in detail, and `-p <port>` finds the branches touching a port, shown in detail where one does and listed where several do, or said to be none yet, `--all` includes merged, closed, and archived branches, an archived one marked so, and `--refresh` reads your pull requests from GitHub first. Run in a ports checkout with no command, dockhand shows status.
- **`open`** opens the branch's pull request in your browser, and prints its address; `-b`, `-p`, or `--pr` names the branch.
- **`status --watch`** is status kept current as `serve` works, redrawn when what it shows changes, as a check ends or a pull request is reviewed, and not for each line of a check's progress. On a terminal, a line such as `c <branch>` checks a branch, `l` shows its latest logs, `t` tidies it, and `s` submits it, each with its usual confirmations. `--plain` prints events as lines instead, for scrollback, SSH, and screen readers. It was `watch`, and `queue` is `status`'s list of checks.
- **`diff`** shows what the branch changes from its base, edits included, which is what a check captures and a pull request shows. It lists first the ports CI would build, each marked changed or revision-only. `--stat` lists the files, and `--source [<port>...]` compares the source archives instead, each with the one it corresponds to, as an assessment pairs them; `--json` gives each pair's `status`, `matched`, `added`, `removed`, or `uncertain`, and what a match rests on (`basis`).
- **`impact`** lists the ports the branch changes, each changed directory's other ports with it, as the base's index names them, "libuv and libuv-devel", as `review`'s summary does, the ports that depend on them directly, and the shared files it changes with the ports that load them. They are candidates to look at, not proof of anything: `check --also` builds some of them against the branch, and `impact` suggests one of each kind of dependent there is, a library dependent first, then a build and a runtime one where those aren't already covered, since nothing sizes a build to choose by.

## Shaping the commits

```sh
dockhand tidy
```

`tidy` proposes the commits a reviewer should see: by default one per port directory, and one per update where dockhand updated several of a directory's ports, with the subject dockhand's commands recorded or the one your own commits give, and every uncommitted edit included. The files come out as you have them, but for the lint findings dockhand fixes on the lines your branch adds or alters: trailing whitespace, tabs under MacPorts' modeline, a `\` that swallows the next line's option, and a lone `openmaintainer`. tidy says each as "Fixes:", commits it, and writes it into your files, and `check` makes the same fixes before it captures, so the check builds what tidy commits. `--restyle` restyles each Portfile the branch changes whole, in a last commit of its own, "<port>: whitespace": trailing whitespace, tabs, indentation in fours, and each run of declarations' values lined up at the column most of the run uses. A Portfile whose ports evaluate otherwise restyled is left as it was, and said; nothing else restyles a line the change didn't touch. `--restyle` makes its commit as tidy applies, so it isn't saved with `--plan --out`.

On a terminal, tidy shows the proposal and lets you review the diff, change the groups, edit the messages, and apply it. `-y` applies a plan made only of dockhand's own edits without asking, and that is also the only plan tidy applies without a terminal; anything else needs review. `--squash --message "port: what changed"` makes one commit of the whole branch, applied as given, since the message is yours. `--group "2 1+3"` rearranges the proposal: commit 2 first, then one commit of 1 and 3. A commit that would come before one it depends on, as the latest check of the files orders their ports, carries a note saying so; the order is still yours. `--author "Name <email>"` attributes a commit that combines several people's. `--plan --out plan.toml` saves the plan as TOML, each message as the commit will say it, to edit as plain text; `--apply plan.toml` shows each commit's whole message as it will be written, and applies it if the branch hasn't changed since. Where the commits break no rule of MacPorts' but one warns, as of a body line over 72 characters, tidy says so as `submit` does, keeps them, and `--plan --out` saves them as they are, to rewrite a message and `--apply`.

A commit the branch already has, where tidy would write the same one, from the same parent, with the same files, author, and message, stays as it is, though its Generated-By names an older build, unless that build was of uncommitted source; once one is written anew, those after it are too. So adding a commit to a submitted branch and tidying again keeps the pull request's commits, and submitting adds the new one rather than replacing its history. Where the branch's commits name an older dockhand in Generated-By, as a branch from before v3 does, tidy's plan says so: a commit it leaves as it is keeps that line, and one it writes names this build. `rebase` says the commits it replays keep theirs. Before rewriting, tidy keeps the old history as a checkpoint, such as `tidy-3`. `dockhand undo tidy-3` puts it back when nothing has been committed since; the files aren't touched, so edits tidy committed read as uncommitted again. `rebase` keeps one the same way, such as `rebase-4`. Restoring it puts back the files as they were before the rebase, and the master the branch started from, so master's newer files don't read as the branch's edits; a change to one of those files stops it. A rebase checkpoint made before dockhand kept the base puts back the history and files, and says the branch still counts from the newer master until the next `rebase`.

**`undo`** puts back the history the branch's latest `tidy` or `rebase` replaced, or the checkpoint named, `undo tidy-3`, when nothing has been committed since; after a tidy the files stay as they are, and after a rebase they go back with the master the branch started from. It takes `-b`, `-p`, or `--pr` for the branch. `restore`, its former name, is gone, and suggests `undo`.

One `tidy`, `rebase`, or `undo` of a branch runs at a time; another waits. If one is stopped part-way, killed or lost with its terminal, the next of them on that branch finishes it from what Git shows: a change that was made is recorded, and one that wasn't is dropped, so `undo` of it says it was never made.

Tidy writes commits by MacPorts' rules, and `submit` checks them: a subject naming the port, short and specific; a body wrapped at 72; tickets as full URLs; no merge or follow-up commits; the revision reset when the version changes. Each finding ends with a code in brackets, and `dockhand explain <code>` says what the rule asks and where MacPorts asks it. `explain` answers the other "why"s too: `dockhand explain check-42` says where a check failed, the last lines of the step it failed at, the test failures its test policy let pass, and whether a baseline can say more, which a failed check's `Next:` points to; `dockhand explain -b <branch>` (or `-p`, `--pr`) says what needs you there, what holds it, and what clears it, or what it's doing or waiting on.

## Submitting

```sh
dockhand submit --plan     # the preview: commits, destination, the account, title, checks, upstream, rule findings, and the description
dockhand submit
```

`submit` pushes the branch's committed head to your fork and opens its pull request against `macports/macports-ports`, or updates the one it has. The preview also lists any other open pull requests for the same ports, and what upstream's change means for each port the commit changes, against the branch's base: its net change, whoever made it, an update or a hand edit, so a license changed and changed back holds nothing, and a version changed by hand is assessed as dockhand's own update is. An update on a fresh branch records its own comparison as that assessment; otherwise a check records it once its builds finish, or submit collects it, fetching only archives it hasn't read before, which it keeps in `$DOCKHAND_READING_CACHE`, else `dockhand/readings` in your user cache directory. A Git-fetched port is compared through its forge's archive of the commit each version's `git.branch` names now, on GitHub or GitLab, where its forge PortGroup or its `git.url` says which repository: the commit's files, submodules left out. One whose `git.branch` can't be resolved, or whose repository is on no forge dockhand reads, isn't compared, which holds as what couldn't be checked does. And where a Git-fetched port's tag names another commit now than when the check planned it, the preview says the check built another source than the pull request would ship; where it named another when the update chose the release than when the check planned it, that the check built another source than the update chose; and where its assessment read another commit than the check planned, as a hand edit's may, that what upstream's change was judged of isn't the source the check built. With `--json`, its `concerns` list each, with where it came from and the rule that raised it, and the archive it's in where the port fetches more than one, for your own submission too. Either holds a submission nobody reviews. A `!` marks a finding that requires review before an unattended submission by `bump` or `serve`. A `·` marks an informational finding that does not pause submission. `status` says, for a branch serve prepared, whether its assessment is recorded yet, and never collects one. `ship`'s plan lists them under the same label. They're yours to weigh; a submission of yours isn't held for them, as `serve`'s and `bump`'s are. With `--json`, `upstream` holds them, by port. A commit whose `Generated-By` names a dockhand built from uncommitted source is flagged too, since nobody else can find that build; `modified_builds` lists them. So is one naming a build dockhand's repository on GitHub doesn't have: submit asks GitHub, once for each build its commits name, for the commit the build was built from, by the twelve characters its version gives an older build, and in full for the build you're running, or for a release's tag. A build of a commit you haven't pushed is said until it's pushed there, and a `devel` build, which recorded no commit, is said as one nobody can find. Tidy keeps a commit whose only change would be its `Generated-By`, so tidying again with another build doesn't replace that line. Asking needs your GitHub login, as submit does; where GitHub can't be asked, the preview says so once. With `--json`, `unfound_builds` lists them, each with its commits and what GitHub was asked for (`commit` or `release`), and `builds_problem` says why GitHub couldn't be asked. None of these lines holds a submission, yours or `serve`'s or `bump`'s. The preview names the account it pushes and writes the pull request as, and where its login comes from, as "As       ada, from GH_TOKEN"; under a sandbox or `--remote`, a fork another account owns is said beneath it. With `--json` they're `account`, `login_source`, and `fork_owner`.

The committed files must have passed a check, for every changed port in every environment. The environments are the default ones, `build.default`'s profile's, and every one any check of these files built in; each takes its newest result from whichever check built there, so `check --on sequoia` after a check on Tahoe adds Sequoia's results to Tahoe's rather than replacing them, and a check on one release alone can't stand for a default it didn't build on. Because a check builds the files rather than the commits, a check before `tidy` covers the commits `tidy` makes.

- `--accept <port>` acknowledges a failed extra from `--also` or a failed revision-only port, and the pull request says the cause wasn't established. It acknowledges a failed changed port too, where `check --baseline` failed it the same way at the base, at the same phase on each release it failed on: no regression, the usual case for a MacPorts pull request, and the pull request says the base fails it too, naming the baseline. submit names it so; `bump` and `serve` never accept one. `--accept <port> --standing` takes a port whose every failure is a dependency failing to install, as Monterey's Xcode image refusing lang/gcc15 fails anything that pulls in libgcc15, master included: it accepts that dependency's failure on that image for every branch, with no baseline. Later checks say so, and `submit`, `bump`, and `serve` take it unasked, until the dependency's version and revision, or the image, change. A Tart check says which dependency failed and its version; other providers don't, so their failures can't be accepted standing. With `--json`, `accepted` lists each accepted port with its reason's `kind`, `at-base` with its `baselines`, `cause-not-established`, `blocked-by-accepted`, or `standing` with its `dependencies`, and its words. An extra port that was never built does not block submission and needs no `--accept` acknowledgment. Extra ports provide additional information when a check builds them.
- `--draft` opens a draft, which unfinished or failing checks allow, and `--ready` takes it out of draft once its commit passes; `--ready --plan` says what it would do, and a draft's preview names it. GitHub can refuse dockhand that, as an organization restricting which apps may act for its members does; the macports organization does. dockhand then runs `gh pr ready` itself, when the GitHub CLI is installed and signed in as the account dockhand is, since that CLI signs in as its own app, and says it did. Otherwise the error names the pull request's page and `gh pr ready`, and why the CLI wasn't used. Only the organization's owners can let dockhand's own app through: on GitHub, Settings → Applications → Authorized OAuth Apps → dockhand, then Request access beside the organization, which asks them.
- `--no-check` submits without a check, and the pull request says no local build ran.
- Edits not yet committed are committed first, as `tidy` would commit them and shown as it shows them, then submitted: a plan of dockhand's own edits goes unasked, and one with yours is reviewed on a terminal and held without one, as `ship`'s tidy stage is. `--plan` shows the commits it would make and makes none.
- `--head` submits the committed head, leaving uncommitted edits out.
- `--note "<text>"` adds your own note to the description, under Description after what dockhand writes there, quoted and led by "Author's note:", so a reviewer tells your words from dockhand's; where dockhand writes nothing there, as for one commit with no body beyond its trailers, the note is the Description itself, unquoted. Use it to say why tests failed, for instance, where the table can only say that they did. It's kept with the branch and given each time dockhand writes the description, so submitting again keeps it, and the preview shows its first line. A new `--note` replaces it, which updates the pull request's description, and `--note ""` takes it out. A Description you edited on GitHub stays yours, without the note, and the preview says so. Someone else's pull request takes none, since its description stays theirs.

Every push is conditional on your fork's branch being where submit last saw it, so nobody else's push is ever overwritten. A description you edited on GitHub is kept: submitting again refreshes only what dockhand wrote, while it's still as dockhand wrote it. That is the Description, the commit's body or a table of the commits, with your `--note`, so a body written since the pull request opened reaches it; the Type(s), which only gain ticks that way; and everything from Tested on down. `--rewrite-description` replaces the whole description with dockhand's, yours included, keeping your `--note`; someone else's pull request keeps theirs. `--type` replaces the Type(s) however they read, or adds them before Tested on to a description that has none. A submit that is interrupted is finished by running it again, and never opens a second pull request: when opening one fails, submit looks for one on the branch at once, since GitHub may have opened it before the reply was lost, and the next submit finds one it opened but didn't record. The title is the commit subject unless `--title` says otherwise, and an existing pull request is never retitled unless you pass `--title`.

The description follows MacPorts' pull request template, beginning "Submitted by **dockhand**", dockhand's name in bold and linked, and ending with a line naming dockhand's version. A description dockhand wrote before its first line did so gains it when submitted again, where the last line is rewritten. `--type` fills in its Type (bugfix, enhancement, security fix); without it, a branch whose commits are all dockhand's own and include an update it made is an enhancement, and a commit citing a CVE adds security fix. `--tested-variants` and `--tested-binaries` tick its checkboxes, and `--skip-notification` keeps maintainers from being mentioned. *Tested on* says what each environment was, from what the guest reported: the macOS version and build, the architecture, and the Xcode or Command Line Tools version. Each line ends with how it was built and the ID of each provider run, such as `tart: built in a clean VM (Run ID: tart_7y62p4sigena6xlr - checked in check-12)`. For the github provider it gives the macOS release of each of the workflow's runners, as the label GitHub's jobs API gives its job names it: `macOS 14, 15, 26` for `macos-14`, `macos-15`, and `macos-26`. A label such as `macos-latest` names none, and a runner's Xcode, which only its log's text gives, isn't recorded. A table follows, each port's result in each environment, in the words `check` uses. A result that gave a reason for not wholly passing, a build that failed or tests that failed, advisory ones too, has its cell marked, and a note under the table quotes the reason, from the step of the build that failed, once for every port and environment that gave it: ``¹ rust on macOS 15, macOS 26: `tests: Failed to test rust: command execution failed` ``. A reviewer can't read the logs on your Mac, so the note is what the pull request says of why. A timeout's reason is its deadline, which the cell says. The last line names the dockhand that submitted it. Anything that wasn't recorded is left out rather than guessed. GitHub refuses a description past 65,536 characters, which a large rebuild checked on several releases can pass: dockhand trims its own parts under the limit, the Tested on table's rows first, then the runs' names, then the commits' table, each saying what it left out and where the rest is; one past the limit with a part kept as yours is refused before anything is pushed.

### After review

`status` reads your pull requests' state, reviews, and CI where what's recorded of them is older than five minutes, as `serve` reads them that often; `status --refresh` reads them whatever their age, and `--attention`, for a prompt, never does. A read that fails is said in one line, and status shows them as last read. To answer a review, edit the branch, check it, tidy, and submit again; the pull request is updated. When reviewers asked for changes, submit then asks whether to request their review again; `submit.rerequest_review` can make that `always` or `never`. Without a terminal it asks nobody, and says so; with `--json`, the result's `pull_request` names each reviewer under `changes_requested_by`, with whether they were asked again, `rerequested`, beside `updated_title` and `updated_description`. `rebase` replays the branch onto fresh master when it needs that, keeping a checkpoint. It makes the replayed commits before moving anything, so a rebase that conflicts leaves the branch as it was, and names the files. A branch with a merge commit is rebased by hand.

When a pull request is merged, its branch is marked merged. `dockhand usage review` covers reviewing someone else's pull request.

## Cleaning up

- **`clean`**, which is `clean --merged`, removes a merged branch's worktree, local branch, and fork branch, each only while it still holds the merged commit, and the `dockhand-check/` branches its checks left on your fork, each only while it still holds the commit checked. A worktree with edits or untracked files, and work that went on past the merge, are kept. So is a branch checked out anywhere clean doesn't remove, your checkout or a worktree dockhand didn't make, since deleting it would leave that checkout on a branch that's gone.
- **`clean --closed`** also takes branches whose pull request closed unmerged: their worktrees, and your fork's branch while it still holds the commit dockhand pushed, one moved since kept and said; merged branches are cleaned with them, unless `--merged=false` leaves those. A Git branch with nothing master lacks, holding no work, goes with its worktree, and `status --all` reads it as cleaned. Their work isn't merged, so a Git branch with work of its own and the checkpoints stay, and `path` or any command that needs the worktree checks it out again. The `dockhand-check/<commit>` branches a branch's GitHub checks left on your fork, as a canceled check's, go with any branch clean takes, closed, archived, or forgotten with `--delete` as well as merged, each while it holds the commit checked.
- **`clean <branch>...`** cleans the branches named alone, each as its state has it, merged, closed, or archived, and nothing else: no other branch, nothing a check left, no branch from before v3. An open branch has nothing to clean, and is refused. A branch cleaned by hand after its merge, before status has read the merge, says its pull request may have merged, with `status --refresh` to read it.
- **`clean --closed`, or `clean` naming an archived branch,** names one with work of its own where master has its port at another version than it started from, whether or not it has a worktree, for you to look at, with `git branch -D` to remove it. The branches earlier dockhand made before v3, `dockhand/bump/<port>-<id>`, are plain Git branches it doesn't track or sort: `dockhand adopt` takes one up, and `git branch -D` removes one.
- **What checks left behind.** A check deletes its Tart clone when it ends, and a later attempt of the same check deletes an earlier one's. A check whose process dies with no later attempt leaves its clone behind, sometimes still running and holding one of the Mac's two VM slots. Whichever branches it cleans, `clean` lists these clones too, and removes one once no process is running its check, stopping it first. It keeps a clone no check of this checkout made, since another database may be using it, and it never touches the images checks clone from.
- **`archive [branch]`** sets a branch aside in one step: status leaves it out, and its worktree goes where it holds nothing the branch's commits don't. The Git branch, your fork's branch, the checkpoints, the record, and the pull request stay, so `archive --undo` brings it back, and the worktree is checked out again when a command next needs it; `status --all` still shows it. A worktree with uncommitted edits or untracked files is asked about on a terminal: commit them, as `tidy` would where its plan needs no words from you, discard them, or keep the worktree. A script keeps it and says so; `--discard` removes it, edits and all, and `--keep-worktree` keeps any worktree. A pull request still open is said, with how to close it; archive never closes it. `clean <branch>` takes the worktree of a branch archived before archive did.

- **`clean --delete <branch>...`** forgets merged, closed, or archived branches named, so a person can end the listing of one clean keeps: each one's Git branch, listing first the commits master doesn't have, which go with it, its worktree, and its record, but for what other branches' results reused of its checks. `status --all` no longer lists it, and its name and pull request are free for another branch. It asks, and a script passes `--yes`.

`clean` shows what it would remove first, and `clean --plan` stops there, removing nothing. On a terminal it asks, and a script passes `--yes`; once done, it says one line a branch, what it removed and what it kept, which `status --all` and `status <branch>` say after, as "fork branch kept: it moved while clean ran". A branch's record stays but for `--delete`, so `status --all` still lists it, as cleaned, and `status <branch>` still finds it. Its checks' records and logs are automatic cleanup's to keep or remove, below.

**Automatic cleanup.** Once a day, dockhand cleans up by itself, unless `cleanup.automatic = false`. It removes:
- what `clean --merged` would;
- what checks whose process died left behind;
- port indexes unused for `cleanup.after`;
- the journal's events older than `cleanup.after`, and the sessions that ended or went quiet before then, but for one a lease still names, and for today's, which `serve.submit_limit` counts, however short `cleanup.after` is;
- the archives Tart's builds made, which checks keep in `~/.dockhand/archives` for later builds to install, but for the newest passed build of each port, on each environment, with each set of variants, which reuse may choose, and each open branch's newest passed result of each port on each environment. An older build's archive goes, however recent, so a port rebuilt often keeps one. It says how much stays;
- checks' logs, in `~/.dockhand/logs`, which are kept compressed with gzip once their check ends (`logs` reads them as they were written): an ended branch's, once it has been merged, closed, or archived for `cleanup.after`, and an open branch's where they stand for nothing, superseded for `cleanup.after`. An open branch keeps the logs of its newest check in each environment it has built in, and of its three newest checks;
- what an ended branch recorded of its checks, once it has been merged, closed, or archived for `cleanup.after`: each check's provider runs, results, plan, and revision, and the branch's assessments, but for its newest check, which `status --all` shows as it ended, and the builds reuse may still choose. `logs` says of a check that's gone that it's no longer recorded. An open branch's records are never touched, but for its assessments of a tree it moved past more than 7 days ago, which it would assess again;
- the vanilla images Tart pulled for `setup tart`, once unused for 30 days. Each is deleted from dockhand's own Tart home with `tart delete`, never `tart prune`, and the next setup of its release downloads it again.

`serve` runs it. Without serve, a command starts it in the background once its own work is done, and doesn't wait for it; what it removed goes to `cleanup.log` beside the database. When free space where the database or Tart's images are falls below `cleanup.min_free`, it runs at once, and says so, at most once an hour.

### Limits

The timeouts, capacities, `serve.submit_limit`, and `cleanup.*` above are the only limits you can change; no flag or environment variable tunes a time or size bound. The rest are fixed in code. Those a check or an update can run into:

| What | Bound | Once it's reached |
| --- | --- | --- |
| A download | 3 minutes without data | given up on, and said; one that keeps arriving goes on, whatever its size |
| Any other request to a host | 30 seconds to connect, 1 minute for a response | it fails |
| A source archive the comparison reads | 4 GiB uncompressed | the comparison stops there, and holds |
| A file the comparison reads: license, build file, manifest, lock | 1 MiB | said; it holds, but for `go.mod`, `Cargo.toml`, `Cargo.lock`, and `package.json` |
| `create`'s project files at the release tag | 4 MiB each | `create` stops, naming the file |
| A PyPI release's JSON | 8 MiB | the release isn't read |
| A source file a patch touches | 64 MiB | the patches are left unchecked; the build applies them |
| A compressed patch, unpacked | 64 MiB | that patch is left unchecked |
| `go.mod` or `Cargo.lock` in an archive | 16 MiB | the dependency edit is refused |
| `go2port` or `cargo2port` | 10 minutes | the edit fails |
| One call into the Portfile evaluator | 5 minutes | its interpreter is ended, and the call fails |
| A `portindex` run | 1 hour; a full pass takes 3 to 4 minutes | ended |
| A check's attempts per environment | 3, retried only after an infrastructure failure | the environment fails; a build, lint, install, or fetch failure is never retried |
| A target's lint | 10 minutes | it fails at lint |
| A GitHub Actions run to appear | 10 minutes | an infrastructure failure, retried as one, saying to check that Actions are enabled on the fork |
| A GitHub Actions job log kept | 64 MiB | cut, saying so |
| Other open pull requests for a port | the first 50 GitHub's search returns | the rest aren't seen |

Others are said where they come up: the HTTPS probes under [update](#update), GitHub's pace and rate limit under [Many ports at once](batches.md), `--variants each`'s 12 builds under [Checking](checks.md), and the Mac's two VMs under [tart](checks.md#tart).
