**What is rebuilt, and what carries over.** The v3 top layer replaces about 20,000 lines of v2:

- `cli` and `tui`
- `workflow` and its subpackages
- `record`, `state`, and `state/sqlite`
- `app` and `proc`

v2's command layer is deleted at the start of the rebuild (step 4), and its engine as step 5 replaces it, not kept alongside (the person's decision, 2026-09-25), because keeping it compiling would mean reshaping the shared packages twice. The last v2 commit is tagged `v2-final`, and building that tag gives a working `dockhand-v2` for real bumps in the meantime. Its `state.db` and v3's `dockhand.db` never touch.

The domain packages carry over: `macports/*`, `tcl`, `git`, `tart`, `upstream`, `forge`, `github`, `fetch`, `credential`, `archive`, `macos`, and the small utilities. Two adjustments come with them:

- **They import v2's `record` for shared vocabulary.** Types such as `Platform`, `ObjectID`, `Source`, `Target`, `BuildConfig`, `Release`, `Digest`, and `Reference` move to a vocabulary package of their own.
- **The providers (`verify/tart`, `verify/github`, `verify/staging`, `verify/ledger`) are reshaped.** They are built on v2's per-target `Attempt`, `BuildSpec`, and `ProviderExecution` records, plus v2's `state` provider store. They are reshaped to v3's guest execution with per-target checkpoints, keeping their idempotency and reconciliation rules. The v3 database is new (`~/.dockhand/dockhand.db`) and has no migration from v2. Breaking changes are expected until v3 is released.

v2's hard-won rules are ported as acceptance tests, not rediscovered:

- idempotent submission and reconciliation before any retry;
- observation-only recovery after an uncertain PR write;
- guarded branch replacement that never overwrites work dockhand didn't write;
- human-edited PR text kept.

## Later capabilities

### Dependent verification follow-up

Direct-dependent discovery, isolated Tart builds, per-target images, and full-cohort publication checks are implemented. Mostly decided on 2026-09-24 and built with changesets (Next items 6 and 9): a failed dependent is reported and may be acknowledged, and `--baseline` adds evidence without unblocking publication by itself (decisions 20, 21, 44); downstream revision bumps are `bump-revision` of several ports or `bump --revbump-dependents` (27); revision-bumped dependents are changed ports, which GitHub's CI builds, while unchanged extras (`--also`) stay Tart-only (23).

### Broader selectors and multi-target intake

Names and indexed subports work now; `assess` and `outdated` also support maintainer/category selection, and `assess` can scan the tree. Several ports in one changeset is Next items 6 and 9. What remains here is batching independent bumps, one changeset each: expose one result per requested target and preserve independent failures, admission rules, and attachment behavior. Do not add a generic batch interface merely to implement one shared release.

### GitHub verification refinements (done 2026-09-20; see completed capabilities)

Two of the three are done. Broader workflow coverage: the provider no longer pattern-matches `main.yml`, since a contribution confined to one port directory above an upstream base guarantees the workflow is upstream's own; it reads the file only to refuse a push trigger that would start no run, and judges the run by the jobs it carried ([note](activity/2026-09-20-workflow-read-not-matched.md)). Controlled reruns: a run that finished without succeeding is run again rather than adopted, which is what makes retrying a stopped verification work on this provider at all ([note](activity/2026-09-20-github-reruns.md)). Safe updates of already-pushed verification branches: a correction now authorizes replacing the commit it corrects, not only a published contribution's pull request head, which was the gap that made verifying an amended but unpublished contribution on the fork refuse ([note](activity/2026-09-20-correction-replaces-what-it-corrects.md)). The provider still compares before writing, so an unrecognized head is left alone. All three parts of this item are done; what is left here is the refinements the item began with as open-ended: broader workflow coverage beyond MacPorts' own file, and whether a refusal that a person can fix should close the request permanently or leave it retryable. With changesets (Next item 6) the provider must accept several commits and port directories above the upstream base, where it now assumes one. After a local branch rename, forge verification now pushes to the PR's recorded head branch while the local name only locates the commit; see the [remote branch report](activity/2026-09-17-remote-branch-identity.md). Shared-run cancellation, missing-run diagnostics, delayed-run recovery, offline cancellation, and log-cache retention already exist; see the [GitHub exercise](activity/2026-09-15-xplr-github-exercise.md).

### Expiring credentials

Add access/refresh-token storage, expirations, and cross-process refresh rotation before enabling an authentication flow that requires expiring user tokens. Preserve the selected identity and require login again only after revocation or unusable refresh credentials. This is separate from the implemented device login and registered OAuth client.

### Reads that the state-boundaries review wants narrower

`loadExecution` reads every attempt and resource of a job under the write transaction, and the live table's two-second poll assembles full contribution history each time. The review calls these structural scaling concerns and made no measurement; extend the state performance probe with large cohorts and full live-status reads first, and narrow the working set or add a summary query only where it shows.

### Shared-release coverage on GitHub

Absorbed by changesets (Next item 6): targets are every subport of a changed Portfile, less MacPorts CI's exclusions, and GitHub's CI builds them all. Locally this becomes the default, so a stub's bump builds every versioned subport unless `--only` narrows it, and `--all-subports` retires. Until then, local verification of a shared release builds the newest subport by default and every subport with `--all-subports`, and the GitHub provider reports multi-target coverage as unsupported.

A main port's bump moves the subports sharing its version without a flag, since the Portfile makes them one release ([note](activity/2026-09-22-main-port-authorizes-shared-release.md)). Holding one such subport back is not a flag's job: a subport that inherits the main port's `version` has no version of its own to keep, and one that must stay behind pins its version in the Portfile, which the release scope already protects.

## Needs design

### Review and unattended-publication authority

Settled by Design v3 (§6.11, §9, §11). `review` posts on someone else's PR only after showing the text and asking. Publication always comes from a person's decision: `submit`, `submit --check`, `submit --passing`, or `serve --submit-passing` (or its config key), which is limited to the branches `serve` prepared that passed with nothing held, at most a daily limit.

### More permissive human-edit capture

Settled by Design v3: authoring edits files without committing, `check` captures working files as snapshots, and `tidy` makes the commits with checkpoints and `restore`. The staging preconditions of v2's `amend` retire with it.

### Instance coordination

Settled by Design v3 §11, built in step 4: sessions with pid and start-time liveness and a heartbeat, fenced leases void when their session dies, one `serve` leader with standbys, controls applied by whoever can, an event journal in the database, a registration marker under the checkout's `.git`, and a Tart capacity lease file under dockhand's own Tart home. A socket client and service stays unbuilt. The [coordination note](instance-coordination.md) keeps the discussion.

### Evidence across repository registrations

One database supports multiple repositories, but evidence is currently scoped to one registered clone. Decide whether identical tree/build inputs may share evidence across registrations and what repository trust checks are necessary. Per-target reuse by recorded inputs (decision 28) keys evidence by content identity, independent of the registration, so what remains is the trust question. This is distinct from preserving identity within one contribution.
