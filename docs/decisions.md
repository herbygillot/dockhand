# Decisions

What dockhand decided and still holds to, and what it declined. Each entry gives the rule, the date, and the reason in a line or two. A change that would cross one says so and argues for reopening it. Released versions, release candidates, and the order work was done in are left to Git's history; docs/ as it stood before this file existed is at tag `docs-archive-2026-10-25`.

Code comments cite entries here by number: "decision 28" is a contract decision, "D9" a decision of the 2026-09 plan. Both keep the numbers they were given.

## Contract decisions

From the contracts walk-through of 2026-09-23. Numbers missing here were superseded by v3 and dropped (2026-10-27).

- **4. A check builds each port's oldest and newest macOS unless told otherwise** (amended 2026-11-04, the person's "Oldest and newest" at 02:25Z; v0.8.0, cd68e1ac6). It was this Mac's release, the platform an update's evaluation reads natively, until v0.8.0 made minmax the default; `--build host`, or `build.default = "host"`, is the quick check on this Mac's release. Other releases are asked for (`--on`, build profiles).
- **6. A release with no image is refused, naming the command that makes it.** Xcode is an add-on (amended 2026-09-26): only a release without its base image is refused. A port that needs Xcode on a release without its Xcode image is unmet, not built, and the check names the command that makes the image.
- **7. A build on another release records its evaluation and build platforms apart.** The build platform must fall inside what the update's evaluation covered, and each release's image choice comes from that release's modelled `use_xcode`, not the host's.
- **9. Each macOS release has a facts table**, and a modelled context answers toolchain questions from it rather than from the host: Xcode and Command Line Tools versions, the developer directory, compilers and their versions, and SDK paths and versions.
- **10. The facts table is checked in and harvested from real images.** An update models releases this Mac has no image for and must stay fast, so it reads the table; a check, where an image exists, builds against the image's real facts. The guest reports drift from the table without changing a verdict.
- **11. The Tart guest runs what MacPorts CI runs, in its order.** `port lint`, then the dependencies installed and activated in a command of their own, then fetch, checksum, and install; tests after install, advisory as in CI unless `check.tests = "required"`. Each target starts from a guest with everything deactivated.
- **12. The facts table is keyed by Darwin, architecture, and profile, and each entry records its source and date.** (An amendment adopted 2026-11-05, a row as one toolchain of a release keyed also by its Xcode and tools versions, herbygillot/dockhand#86, was unplaced on 2026-11-10 until a consumer asks, with the right-sizing of the modelled context. GitHub's runners (#85) are a source after Tart. Amended 2026-11-09 at the person's choice: a Mac probed once, such as an AWS Intel Mac, is a `host` source after the runners, its probes committed with the generator since they can't be made again; and a runner's or host's row stands for its builder when its tools are the builder's release, the trailing build stamp aside. Amended 2026-11-10 at the person's ask: readings of Apple's Xcode and Command Line Tools installers, made without installing them, are an `installer` source after the hosts and before the buildbots; with no live Base view, an installer's row takes its release, macOS, and versions from the buildbot whose Xcode and tools it read.) Harvested Tart images win for what Tart can boot; MacPorts' buildbot logs cover the other releases and architectures from Darwin 10; Base's own tables cover Darwin 8 and 9. The harvesters are checked-in tools, so the table is regenerated, never hand-edited.
- **13. Setup installs a pinned Command Line Tools generation per release.** The table holds the generation; setup installs the newest tools of it that Software Update offers and refuses, naming what's offered, when there's none, never falling back to the newest. The generation follows MacPorts' CI pin where CI covers the release and the buildbots elsewhere.
- **15. dockhand has one configuration file, `~/.dockhand/config.toml`.** Precedence is flags, then environment, then the file, then defaults; a list flag replaces the file's list; an unknown key or malformed value is refused with the key named; reading the file creates nothing; values are frozen when work is accepted; `DOCKHAND_CONFIG` names another file. Nothing is added without a use.
- **16. Portfile evaluation is independent of the host's own state.** The installation is modelled as MacPorts CI sees it at its second evaluation: a first pass with nothing installed gives the dependencies, and the second, whose fetch plan counts, has their closure active. The evaluator launches with Base's kept environment only. A prefix path's existence is evaluated both ways, conclusive only when the fetch inputs agree; reading a prefix path's contents or a prefix program's output is inconclusive.
- **17. Pre-fetch hooks are judged statically, never run.** The question is over every branch a builder can take, which one run can't show, and static judgment needs no values and costs nothing. Running a hook inside the oracle stays a possible cross-check if refusals remain.
- **18. Programs built into macOS are profiled per release in the facts table.** Their presence and fixed behaviour (`sw_vers`, `uname -m`, `sysctl` keys, `xcrun --show-sdk-path`, `java_home` with nothing installed) are harvested per release; behaviour that depends on installed state is evaluated both ways. The fetch guard admits an `exec` of such a program whose output only lands in a variable the effect rule already judges.
- **28. A result is reused per target, by the identity of what its build read.** The guest records each activated dependency, each tree and `_resources` file the evaluation sourced, and each name's resolution; a result is reused when every recorded input is unchanged by content identity in an environment of the same origin (source image digest, tools, MacPorts version, setup protocol). Build-time reads are bounded, not traced: distfiles by checksum, `files/` by tree, dependencies, and the environment. A passing target's archive is kept so dependents install rather than rebuild. Tart only: a GitHub Actions result is never reused (D21). `port -t` trace mode is set aside. An inert difference, a change to metadata no build reads, carries a result over only where the Portfile reads none of the changed options elsewhere than another inert option's line; one a phase reads, as a destroot hook writing `${description}`, is rebuilt (narrowed 2026-11-04, Codex's sixth review, #70).
- **29. No provider fallback.** The provider is chosen when work is accepted, and at capacity the work waits; nothing does "this is busy, so that", since a result would then mean two things. Switching providers is the person's explicit act. Build, lint, install, and fetch failures are never retried.
- **30. Infrastructure failures are retried; verdicts never are.** Three attempts in all, 1 and then 5 minutes apart, only for attempts that ended as infrastructure failures; a retry covers only targets with no verdict yet. A target mid-build during two infrastructure failures stops and needs attention, since exhausting memory or disk looks like infrastructure.
- **32. dockhand depends only on interfaces its external components document; an unavoidable exception is flagged.** For Tart: its CLI, `--format json` output, `TART_HOME`, and its documented locations, never anything inside a VM directory. Existence and running state come from `list` and `get`; a delete is confirmed by absence from `list`. Tests pin the JSON fields read, so an upgrade that changes them fails a test. Knowing exceptions are named where they're taken: the recovery-partition edit (38), MacPorts' log lines (a failed check's detail, and Base's `-d` header in a GitHub runner's job log for Tested on, #100), xcodes' sign-in, MacPorts Base internals in the evaluator, and ports.macports.org's `port_name` filter on its documented builds endpoint, which its browsable API offers and its ENDPOINTS.md doesn't name (build history, 868a208c, 2026-11-01).
- **35. One repository per engine.** Each engine is bound to one registered checkout, `serve` drives one, and only cleanup reaches across. An edited pull request body is kept whole, `status` reads only what dockhand recorded, and each forge has one client.
- **36. Cleanup is automatic.** Nothing guarantees a person runs `clean`, so bounded pruning runs at most once a day, during `serve` or after an attended command's own work, and at once when free space falls below `cleanup.min_free`. `cleanup.after` bounds everything it reaches (D6); `cleanup.automatic = false` turns it off. Open work and anything a live branch's evidence reads are never touched; a kept archive goes only when nothing references it (44).
- **38. Two Tart findings, settled by testing.** The host-side recovery-partition edit that makes an image's 100 GB disk usable is an approved exception to 32: it runs only during setup, on dockhand's own stopped clone, as the route Tart's FAQ points to does. Everything dockhand reads back from a guest goes over SSH/SFTP and is checked against a size and sha256 computed on the other side, since `tart exec` loses output from macOS 12 to 15 guests while reporting success (openai/tart#1347).
- **41. No direct use of Apple's Virtualization framework.** It would mean owning images, cloning, networking, disk growth, and the guest channel through every macOS release, plus an entitlement and cgo, and its vsock channel fails as `tart exec` does. Fixes go upstream to Tart, and the provider seam stays open. Reopened if Tart becomes unmaintained, a blocking bug stays unfixed across releases, or dockhand needs something Tart can't give.
- **42. dockhand has its own Tart home, and SSH is a check's only guest channel.** A Tart home of its own (`TART_HOME`) keeps the person's VMs out of dockhand's view; the Mac's VM limit stays machine-wide, so the person's running VMs still count.
- **43. Guests are reached through Apple's `/usr/bin/ssh`, with a dockhand key pair.** Local Network privacy can block a Go binary's dial to a guest depending on which app launched it. Apple's own binaries were taken to be exempt; they aren't where the launching app is denied Local Network access, as Ghostty was on macOS 27.2 (herbygillot/dockhand#89). The choice stands: `/usr/bin/ssh` still escapes the Go-specific blocking, and dockhand tells the person to allow the app. One multiplexed connection per guest; files through `pkg/sftp` over it; setup records each image's host keys and checks guests against that record.
- **44. The plan and evidence model.** A target is revision-only only when its Portfile diff touches nothing but `revision` and no file under `files/` changed; unknown is substantive. A check's plan separates the changed ports, CI's eligibility per platform with a reason for each exclusion, the selection (`--only`, `--also`), and the prerequisites that selection needs; a changed prerequisite is always built, never substituted by an old binary. A result records the queries evaluation made, negative ones included, and the digest of every archive it consumed, so an amended library with unchanged coordinates is never reused through. An archive is ready for dependents only once its transfer and checksum are recorded. A baseline never unblocks submission by itself; the person accepts.

## Plan decisions, D1 to D21

From the 2026-09 plan's questions for the person. D15, D19's taking, and D3 are settled facts now and stay for their numbers.

- **D1. A result keeps the test policy it was checked under** (2026-09-27), and is read under it, naming its check where that differs. A later `--tests required` check of some ports doesn't bind the others.
- **D2. Modelled contexts default to the Xcode profile** (2026-09-29), as MacPorts' builders are set up. A context that states its tools is modelled with them.
- **D3. Tahoe's Xcode image has its buildbot's Xcode** (2026-09-27), under "Xcode images follow MacPorts' buildbots" below.
- **D4. What an update couldn't check holds a submission nobody reviews** (2026-09-27). `bump`'s and serve's submissions wait for a person's look when the update couldn't check something a passing build can't catch: archives the comparison couldn't pair or fetch, and a Go toolchain minimum left below go.mod's requirement. A patch it couldn't check is shown, not held, since the build applies every patch. A person's own `submit` shows these and doesn't hold.
- **D5. Tidy, rebase, and restore stay in the engine** (2026-09-27). Mechanisms they share can live in `history`; the verbs don't move there.
- **D6. How long history is kept** (2026-10-01). One setting, `cleanup.after` (15 days), bounds caches, kept archives, events, logs, and build history. Logs are gzipped when their check ends and read in place. Open branches keep everything their evidence reads. An ended branch, `cleanup.after` past its end, keeps one light row for `status --all`. Reuse is bounded by count: only the newest passed result per port, environment, and variant set keeps its archive. Assessments of a tree a branch has moved past go after 7 days.
- **D7. `update --plan` on a branch dockhand doesn't track** (2026-09-29) plans on master unless what's checked out changes the port, and refuses only then, naming `adopt` and `--new --plan`.
- **D8. The GitHub CLI marks a pull request ready when an organization refuses dockhand's app** (2026-09-29), where `gh` is installed and signed in, and says it did; otherwise it says how to finish.
- **D9. The dependencies dockhand writes don't hold** (2026-09-29). `update` writes `go.vendors` and `cargo.crates` and a check builds with only what the port declares, so: Go's changes hold nothing (the `go.toolchain_min` check stays); a new Rust `-sys` crate is listed for attention without holding; a Node `package.json`'s dependencies are counted and hold nothing. A Python dependency is another port, and holds.
- **D10. A failure's summary gives the first compiler error in the port's log** (2026-09-29), beside MacPorts' `Error:` lines, marked as read from the log.
- **D11. `ship --passing` asks once over one plan** (2026-09-29, amended 2026-10-13): every passing branch with its holds on one plan, one answer on a terminal; a script passes `--yes`.
- **D12. How far the comparison reads a build file** (2026-09-30, extended 2026-10-01). Holds are scoped to the build systems a port uses. A build file whose change is only the version it names doesn't hold. A CMake option off by default, and a change under an `if()` that can't be taken with every off-by-default option OFF, hold nothing; an option on by default, a flipped default, or a removed option holds. Comments and a version set in parts aren't changes. Any other change to a build file holds.
- **D13. Failed tests hold nothing under `declared`** (2026-09-30), the default and MacPorts CI's: tests that ran and failed pass, unattended or not, and the pull request says so. `check.tests = "required"` or `--tests required` makes them fail the check.
- **D14. An assessment assesses the net change from the base** (2026-09-30), never the edits that made it. Only what the candidate introduces, or what couldn't be checked, holds; a concern the base already had is said. A Git-fetched port is compared through its forge's archive of each commit.
- **D15. A trailer naming a build nobody can find** (2026-10-02): submit warns of a `Generated-By` naming a build GitHub doesn't have; nothing more. Reopened only if a release build is reported unfound.
- **D16. How long a build may run** (2026-10-01): a Tart build, the guest's install, and a GitHub Actions run end at 6 hours, GitHub's own cap on a job, set per provider in the configuration. Lint ends at 10 minutes; a stalled fetch is MacPorts' to drop.
- **D17. Which checks make a branch ready** (2026-10-01, amended 2026-10-13 and 2026-10-29): where the person names where a check builds, with `--on` or `--build`, exactly that, `--on local` meaning the local provider even where Tart is set up; where neither is named, the build profile in effect, `build.default` when a person runs it, Tart on this Mac's release where Tart is set up, and `build.unattended` for `ship --yes` and serve. dockhand never chooses local itself: the person's "It should pass on the environment that the user _specifically_ requested." (2026-10-29 17:35Z) and "If Tart is installed, and the user does not explicitly specify a provider, then we should default to Tart as before." (18:19Z), built before v0.7.0 rc1. What's needed is what the newest check of the branch's files was asked to build on, so asking again replaces an earlier ask (the person's "Newest ask", 18:28Z); a check narrowed to some of the changed ports, with `--only`, or a baseline, adds its results and sets no ask. serve's own checks and submissions keep `build.unattended`. Each environment takes its newest result from any check of the branch's files as they are, so a narrowed check adds to the others; and whatever the newest ask, a failed cell in any check of those files still blocks while its environment stands, or is accepted explicitly, so a narrower ask never un-requires a failure; one whose environment was remade since stands for nothing, pass or fail.
- **D18. A kept archive is signed from a read-only map** (2026-10-02), whatever its size, once when it's kept; its `.sig` and `.rmd160` are stored beside it and removed with it.
- **D19. `cargo.update`** (2026-10-02): update takes a port that sets `cargo.update yes` where its source ships a Cargo.lock and refuses one without; dockhand never adds or removes the line.
- **D20. On GitHub, `logs --port` starts at the port's own steps** (2026-10-02), by the `::group::` headings of MacPorts' workflow; without them, the whole log, saying so.
- **D21. Only Tart's results are reused** (2026-10-02). A GitHub Actions check's runner image floats and its dependencies are live. Revisited only if GitHub names an image digest and the workflow pins what it installs.

## Standing decisions

- **A pull request's discussion is read with `dockhand discussion` and answered with `dockhand comment`** (adopted 2026-11-13, not yet built, herbygillot/dockhand#245, v0.10.0, docs/designs/pull-request-discussion.md; the person's "there isn't really anything in dockhand that lets you read comments to begin with" and his choice of `dockhand discussion` over `status --comments` on the architecture thread's card; architecture and Codex each wrote a proposal apart, one pass). It is for an agent driving dockhand, so that reading and answering reviewers stays inside dockhand's permission table, preview and at-most-once rule. The reader shows the whole discussion live, inline review threads included, stores none of it, and never calls a partial reading complete. Other people's text is marked as untrusted data and dockhand never acts on it. A comment goes to the conversation or into one existing inline thread, singly and never through a review; threads are never resolved. `Comment` is a new effect on `Made`, `Invited` and `Named`, the basis established where it is used. A comment is sent at most once per attempt: an attempt of unknown outcome is never sent again and is settled before the next. Not taken: resolving threads, new inline comments, applying suggestions, a stored transcript, automatic replies, a comment-only first version.
- **`submit --no-check` names the branch's last passing check as history, never as evidence** (adopted 2026-11-13, the person's "246 now", herbygillot/dockhand#246, v0.9.0, after one outside design read). Where no check of the current files has passed and an earlier check of the branch passed on other files, the description and the preview name that check, what it checked, and which of the branch's files changed since; where the source comparison finds a different or moved source it says so. Where the current files have a passed check, or no earlier check passed, the words are as before. The earlier check is carried in its own field, apart from evidence: it ticks no item, answers no question, fills nothing into "Tested on", and changes nothing `status`, `submit` or `ship` judge. Not taken: a statement that the branch was rebased; counting the earlier check as coverage. The rules are on the issue.
- **What an update holds for what it couldn't do belongs to the branch and the port** (2026-11-12, herbygillot/dockhand#242, from probing #229's hold on main at f9a7e049: one more commit dropped it). `crates-unlocked` and `manifest-hook` are carried from the port's latest update into every assessment of the branch's files, whatever their tree or base, until a decision or `holds.allow` accepts them, a later update of the port to another release replaces them, or the branch goes. A move followed at the same release replaces nothing. Upstream's own changes stay a revision's net change, assessed afresh.
- **A Cargo port whose new source ships no Cargo.lock is updated, its crate list left as it was, and held** (2026-11-12, the person's "update, and warn" on herbygillot/dockhand#229, from field testing's watchman, whose `cargo.crates` in `+rust` was resolved by hand). With `cargo.update` off, `update` writes the version, checksums and refreshed patches and leaves `cargo.crates` and `cargo.crates_github` byte for byte; where the current source has no lock either, the old block isn't checked, there being nothing to check it against. The update records one upstream change under `crates-unlocked`, which holds as `manifest-hook` does and which `holds.allow` may name; it says the list may not match, the directories holding a `Cargo.toml`, and, for a block in a variant's body, the variant and whether the default variants include it. A passing check doesn't clear it, since a check builds the default variants only. A current source without a lock and a new one with one regenerates the block whole, saying why the old one wasn't checked. Unchanged: `cargo.update` on with no lock refuses (D19), and a lock only elsewhere in the source, such as below worksrcdir, refuses naming each, since nothing in the Portfile points the build at one. D9 is untouched: it concerns dependencies dockhand writes, and here it couldn't write them, which is why it holds.
- **`--set` applies to every port a check builds, and a build under a setting is never a port's coverage** (adopted 2026-11-12 as an amendment to docs/designs/canary-checks.md, not yet built, herbygillot/dockhand#50, v0.10.0: the person's "Why wouldn't `--set` apply to every port Dockhand is looking at, including the targeted checked ports?" at 17:00Z, "`--set`, like variant, changes the way the port build behaves. So you have to consider that when doing comparison between build results internally" at 17:04Z, and "Adopt" at 17:26Z, on architecture's draft after one review by Codex, every finding taken). A build is a port in a configuration, its variants and its settings; a variant is a configuration the Portfile offers and can cover its port, a setting is one the tree does not have and never does. So such a build is an extra everywhere, reused only for the same settings and the same in-check dependencies, accepted by its full name, compared only with master's port under the same settings, never given GitHub's verdict, and never the source of an edit `tidy` writes; a changed port's coverage is owed whether or not a plain build ran. The earlier scope, `--also` ports alone, is replaced. Two faults the review confirmed for variant builds today are their own bugs, herbygillot/dockhand#235 and herbygillot/dockhand#236.
- **v0.9.0 builds its contracts before it moves code, the publication record first** (2026-11-11, the person's "I think "contracts before moves" makes sense" at 05:46Z, "Agreed on the publication record" at 05:48Z, and "File it" at 06:10Z on architecture's and Codex's plans for the release, written apart and then compared). Where the five core issues change code (submit, ship and the check runner), each one's record or value lands before a package there is moved. A move that has a design and lies elsewhere still goes early (herbygillot/dockhand#16, #152); one with no stated contract or list of callers waits (#39's subpackage). The order: the ownership rule (#144) and the fault sweep's foundation (#129); the publication record (#191); the source comparison (#192), then the check's lifecycle (#193); the preparation result (#194), then the resolved change request (#195); the account and the measures last (#196). Settled with it: a new submit replaces an unfinished one once that one is accounted for, with no command to abandon it; serve reads its settings at each new action, and a check or publication it has accepted keeps what it was accepted with; providers keep their optional interfaces, with no contract every provider must implement.
- **Tart 2.41.1 is the minimum from v0.9.0** (2026-11-11, the person's "Yes on raising the Tart minimum version" at 05:44Z; #38, not yet built). The two workarounds kept for older versions go with it, and the checks that a machine is dockhand's own and is stopped stay. It is the one requirement v0.9.0 changes, and its release notes say so.
- **A check's resolved source is compared one way** (adopted 2026-11-11, not yet built, herbygillot/dockhand#192: the person's "Adopt" at 08:23Z, on architecture's design, docs/designs/source-comparison.md, which Codex reviewed twice against the code). Joining, finished coverage, evidence, reuse and submit read one judgment in `internal/model` with five answers: same, moved, other, unresolved, not known. One table says what each reader does with each answer, and a table test holds the readers to it. Four readers change, each where it disagreed with the reader beside it, and each builds where dockhand reused a result or reported a pass: a finished check whose Git source couldn't be resolved no longer stands for another request; an earlier result built when a tag named another commit no longer fills in evidence; a result built with Git no longer counts where the newest plan builds that target another way; and a result on a release that only an earlier check built doesn't count where that check resolved the ref to another commit than the newest did. In the last, the release stays required and the result reads as not checked. None builds less, and no stored record or flag changes. It is built after the publication record (#191) and before the check's lifecycle (#193), whose reuse reads it.
- **A submission records what it set out to do before its first remote effect** (adopted 2026-11-11, not yet built, herbygillot/dockhand#191: the person's "Adopt" at 08:53Z, on the design architecture merged from its own proposal and Codex's, docs/designs/publication-record.md, which Codex reviewed twice against the code; its check of the last revision was still out, and what that breaks comes back to the person as an amendment). A branch gets one publication: the commit, the destination, the text it meant to write, what the person asked, and the steps still owed. It is recorded before the push and ended when nothing is owed. A later submit settles an unfinished one by reading the fork and GitHub, and does nothing again that the reading doesn't show undone; there is no separate resume. Eight choices came with it. A reviewer request that may have been sent is never sent again. A dockhand that hangs while submitting blocks that branch until it is stopped, under an operating-system lock that is never taken from a live process. A pull request found after a lost answer is not treated as dockhand's own. The upgrade waits until every earlier dockhand has stopped, and on that day serve opens nothing. `--rewrite-description` is not carried to a continuation. A reviewer request on an adopted pull request is made after a yes. A pull request recorded before the upgrade keeps today's rights unless GitHub names another author. A create whose answer was lost keeps one of each day's places until GitHub shows its pull request or its branch is gone from the fork. serve's count moves from events to a small table, which closes #155. The text a submission meant to write is recorded before it is written, so a description GitHub took whose record was lost is read as dockhand's own and not as a person's, which closes #157. No command or flag is added. It is the first of the core items built. Amended the same day after Codex's last look, at the person's "Take it" (09:34Z): a pull request already known for the branch when a create is sent never settles that create, and only one numbered above it does; and the upgrade finds earlier dockhands in the Mac's list of running processes, since a plain submit opens no session, and is refused where dockhand can't read that list. Amended a second time the same day after Codex's two checks of that amendment, at the person's "Take it" (15:50Z). At serve's first pass after the upgrade, a pull request found not open is read by the day GitHub made it against the upgrade's day: made after it, it is that branch's opening on its own day; made on it or before, it is only a number that a later create must exceed. The list of running processes is read once, inside the migration's own transaction where today's guard runs, and the second reading is gone. A create whose branch is gone from the fork frees its place only at serve's second look, ten minutes after the first, with no later pull request found. That is a way out and not a proof: where GitHub had opened the pull request and doesn't list it by then, that day goes one over the limit. Codex recommended that a branch's removal free nothing, and the person took the release.
- **A check's lifecycle is decided in one place for each of four things** (adopted 2026-11-11, not yet built, herbygillot/dockhand#193: the person's "Adopt" at 08:56Z, on architecture's design, docs/designs/check-lifecycle.md, which Codex reviewed three times against the code; its check of the last revision was still out, and what that breaks comes back to the person as an amendment). How long a command stays with a check becomes one value, `Stay`. `logs`, `artifacts` and `shell` ask one resolver which check, attempt, port and phase they mean. An environment's identity has three answers, known, none, or unread with its cause, which closes #190. A cancel is finished only when each provider has seen its work end, by whichever path the cancel is applied; launching and stopping an attempt exclude each other by a lock that every child able to start work holds, and what a provider launched is kept apart from the reference a person looks at. Five choices came with it. serve holds a submission when it can't read what an environment is now. A GitHub check's branch in the fork is named for the check as well as the commit. A cancel of a GitHub check stays unfinished while GitHub lists no run for a push it accepted. A cancel stops a local build and a script's shell and puts a local prefix back, for which dockhand starts each through a small process of its own. A dockhand that hangs while it launches keeps that check's cancel unfinished until it is stopped, and processes left by a starter that was killed are named and never signalled. Local's stop is written only after a test with real processes shows what a signal does to a build under sudo; the rules are written so that either answer fits. #189 and the Tart minimum (#38) close with it, and #199 is fixed ahead of it. No flag or command is added. It is built after the source comparison (#192).
