# 2026-10-03: the full stage's sandbox for pull requests (batch 75)

Batch 75 of the [roadmap](../roadmap.md): step 2a's H7, finished with the person's "Sandbox plus few" (03:55Z, the project's plan/acceptance-harness.md): the full stage's repeatable pull request rows open their pull requests in a sandbox the test account owns, and only the few the person approves go to MacPorts.

## What changed

- **`engine.Options.PullRequests`**, set from `DOCKHAND_PULL_REQUESTS`, names the repository pull requests go to and are read from, MacPorts' unless set (`Engine.PullRequestRepository`, `Engine.Sandboxed`). submit, adopt `--pr`, review, and `--pr` branch selection use it. Master is still fetched from MacPorts (`DOCKHAND_UPSTREAM` is unchanged).
- **The sandbox is the test account's own fork, with pull requests within it**, head and base in the same repository. One account holds one fork of a repository, and a pull request's base must be in its head's fork network, so a separate non-fork copy couldn't take the fork's pull requests without a second account. With a sandbox, `Fork` takes the remote that pushes to the sandbox itself, and still requires it to be a fork of MacPorts' repository; no other remote stands in for it.
- **It's an environment variable, not a build tag,** since the full stage tests the release binary as MacPorts builds it. It's documented in usage.md, `serve --install` keeps it, and submit's preview says "a sandbox, not macports/macports-ports, as DOCKHAND_PULL_REQUESTS says" under `To` whenever it's set.
- **The harness:** `full.sh` sets it to `ACCEPT_SANDBOX`, the test account's `macports-ports` unless named; the guard refuses a full run without a sandbox, or with MacPorts' repository as one; `submit_pr` sends a real pull request to MacPorts by clearing it for that call alone; H3 counts the account's pull requests in both repositories; and `reset-user.sh` closes leftover `[testing]` pull requests in both, deletes `dockhand/` and `dockhand-check/` branches, and syncs the sandbox's master with MacPorts', so a pull request within it shows only its own commits.

- **The Intel job's prepare step** cloned the ports tree where macports.sh had made root's source directory, and planned a check with no branch; it clones to `ports-tree` and checks a branch it starts.

- **filelock's fork grace is a second, not 250ms:** on the Intel runner, with commands spawning on four goroutines, a released lock was still held by a forked child past 250ms, and TryExisting called it busy. A lock that's really busy is now said so a little later.
