# 2026-09-25: `tidy` and `restore`

Roadmap step 5, part 6: shaping a branch's commits for review (Design v3 §6.9, §8). It comes before part 5, `check`, because `check` needs a Mac to prove the Tart guest and `tidy` can be built and tested here.

## The commands

- **`dockhand tidy`** proposes the commits a reviewer should see, and every uncommitted edit is included in them.
  - **One commit per port directory** by default. Files outside any port, such as a PortGroup, get a commit of their own, placed first.
  - **Subjects** come, in order, from:
    1. what dockhand's authoring commands wrote (the last update's subject);
    2. one of the branch's own commits whose subject already names the port;
    3. the files: a new Portfile gives `port: new port`, and a changed version gives `port: update to X`, per §8's subject table.

    Otherwise the commit needs a subject, which dockhand doesn't invent.
  - **Trailers** from the combined commits are kept: `Closes:`, then `See:`, then the others. `Generated-By:` is added only to a commit made entirely of dockhand's own edits.
  - **Authorship** is kept. A commit combining several people's commits needs `--author`. Edits not yet committed are attributed to you.
  - **"Also noticed, for you to fix"** lists Portfile problems. For now that's a revision that isn't 0 after a version change. tidy never changes a file.
- **Unambiguous plans** are the only ones applied without review. A plan is unambiguous when every commit is one port directory's changes, exactly as `update` and `checksums` wrote them, one after another from the base with nothing changed in between, under the subject they wrote. Two differences from a strict reading of §8:
  - A chain of dockhand edits, such as `update` then `checksums`, counts as unambiguous. Both edits are dockhand's, and the chain check proves nothing else touched those files in between.
  - A combined commit with a message body makes the plan need review, because the body would be dropped.
- **Where a plan is applied:**
  - In a script, an unambiguous plan is applied and anything else is refused.
  - On a terminal, the plan is shown with `Review diff [d] · Edit message [e] · Apply [a] · Cancel [q]`. `--yes` skips the question only for an unambiguous plan.
  - `--plan` shows the plan and changes nothing.
  - `--squash --message "…"` makes one commit of the whole branch.
- **`dockhand restore tidy-N`** puts the old history back when the branch is still where that tidy left it; otherwise it refuses, since the newer work would be lost. The files aren't touched, so edits that tidy committed read as uncommitted again. A checkpoint is restored once.
- **Refusals:**
  - A merge commit is refused, with a pointer to rebase ("never flattened without a specific, reviewed choice").
  - A branch whose head or working files changed after the plan was made is refused as stale, with nothing written.

## How applying works

1. The working files are captured again and must match the plan exactly: the same head and the same tree.
2. The series is built on the base with a private index. Each commit's tree is the previous one with that commit's paths taken from the final tree. The last tree must equal the working files' tree, or nothing is changed.
3. The checkpoint number is taken, the ref `refs/dockhand/checkpoints/tidy-N` is created at the old head, and the branch is moved, conditional on its old head, all inside one database transaction. If recording fails, the refs are moved back.
4. The index is reset to the new head. The working files already hold its tree, so nothing on disk changes.

## Changes by package

- **Schema 2 in `store/sqlite`:**
  - Tables for authoring records (`edits`), checkpoints, and acceptances. Acceptances are for `submit --accept`.
  - Columns for the pull request's publication state: the commit last pushed, the description last written, and draft.
  - Schemas are now applied in order, so a schema-1 database from `init` is upgraded in place rather than refused.
- **`update` and `checksums`** now record each file's blob before and after, and the subject. `tidy` reads these records to tell dockhand's edits from a person's.
- **`macports/commitrules`** is new, holding the §8 rules that can be checked from messages and Portfile text:
  - the subject names the port, is specific, and is at most 60 characters;
  - the body wraps at 72;
  - tickets are cited as full URLs;
  - there are no follow-up commits and no merges;
  - the revision is 0 after an update.

  `submit`'s preview applies them too. Lint, version order, other open PRs, and maintainer information need MacPorts or GitHub and come later.
- **`git`** gains `History`, `ComposeTree`, `FileBlobs`, and `ResetIndex`.
- **`command`:**
  - One line reader serves a whole command, so a series of prompts no longer loses input.
  - The command tests' home, and the engine tests, have their own Git identity. Before this, tidy's tests passed here only because this machine has a global identity.

## Tests

- **Engine tests:**
  - an update then a checksum refresh, tidied unambiguously and restored;
  - three hand commits squashed into `jq: update to 1.8.1` with their `Closes:` kept, their author kept, and the revision finding shown;
  - a good two-commit history left alone, then two ports ordered by history;
  - a missing subject and two authors blocking until `--squash --message --author`;
  - a stale plan refused;
  - restore refused after new work;
  - a merge refused.
- **Command tests** cover the script and terminal paths, subject editing, the diff, `--plan`, and `restore`.
- **Store tests** cover the upgrade from schema 1, and the rules for edits, checkpoints, and acceptances.
