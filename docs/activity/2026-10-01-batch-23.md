# 2026-10-01: saying what was checked (batch 23)

Batch 23 of the [roadmap](../roadmap.md): what the fluent-bit run found ([#35071](https://github.com/macports/macports-ports/pull/35071)), and what rust 1.99.0's assessment didn't say ([#35084](https://github.com/macports/macports-ports/pull/35084)), the first redesign [directions](../directions.md) proposes, taken as far as the batch's items go.

## What changed

- **Patches that apply are said.** fluent-bit's six patches applied, and nothing said so, so the person dry-ran them by hand. `update` now says "6 patches apply to 5.1.3's source" (`Update.PatchesApplied`, `--json`'s `patches_applied`), and a revision's assessment records each patch that applies in its coverage.
- **What an assessment read is said, not only what it found.** rust's said only a `package.json` note, so the person couldn't tell "Cargo read, nothing found" from "Cargo not read". Coverage now records each file of the new version's that was read, with whether the base had it, and each patch that applies. `update`, `submit`, and `review` say it in one line below what was found (`engine.CoverageWords`): "Read Cargo.lock, Cargo.toml, LICENSE; 9 patches apply; set apart: package.json (node)", naming five files and counting the rest.
- **Another build system's file is set apart, said in that line alone.** rust's "package.json: 1 dependency changed; rust builds with cargo, not node, so it holds nothing" was accurate and noise, its in-tree tidy tooling's; flatbuffers' `package.json` and `Package.swift` are the same. A change to a file of a build system the port doesn't use is coverage, not a note.
- **What Cargo.lock changes is counted.** It was read only for crates new to it that link a native library. What it changes of the crates it pins from crates.io or Git is now counted in one line, "Cargo.lock: 3 added (libgit2-sys, onig_sys, tokio), 2 moved (openssl-sys, serde)", holding nothing, as a Rust project's dependencies don't (D9). A workspace's own crates, which move with its release, aren't counted.
- **A CMakeLists.txt's change says what it does.** fluent-bit's "CMakeLists.txt changed; the build may need the Portfile to follow" sent the person to the diff, where nothing concerned the port. `project.ReadCMake` reads a CMakeLists.txt's `option()`, `cmake_dependent_option()`, and `find_package()`, each with the `if()` it sits under, as CMake writes its commands, and the comparison says what changed: "option FLB_KAFKA added, off by default; option FLB_TLS's default moves from ON to OFF; find_package(RdKafka) added, under FLB_KAFKA", or "changed, though no option or find_package did".

## Decided along the way

- **A Cargo workspace's members aren't read.** The roadmap asked for them, as a Node project's workspaces are. Cargo.lock pins what every member resolves to, so its count says what the members' manifests change, once; reading each member's Cargo.toml would cost a second walk of the archive, rust's 3.5 GiB of it, and a line for each of dozens of members.
- **What holds is unchanged.** The CMake summary says what changed; any change to a build file but its version still holds, as D12 decided. An option added off by default, or a `find_package` under an option the port doesn't set, holding nothing, as the roadmap suggested, would revisit D12, which is the person's.
- **No policy bump of its own.** Batch 27's `assess.Policy` 10, merged beside it, has assessments recorded before made again, with what they read and checked.
