# ship (v0.4.0 part 2, item 4)

The command-line UX second look's §6: one verb carries a change as far as
`--to` says, commit, check, or submit, from wherever it is now. Built in
slices, each committed on its own.

## The verb

- `ship <port>...` takes each port as a version update from fresh master,
  in a branch of its own, or, where an open branch already changes it, that
  branch, resumed where it stands; `-b`, `-p`, and `--pr` name a branch,
  and with neither, the one checked out here. Run again, it resumes: a head
  a check already passed for isn't checked again, and a submitted one goes
  through submit's own rules.
- One plan, a row a change, "jq  a version update from master, to submit",
  and one question on a terminal; `--yes` skips it, and without a terminal
  running it is the decision. Answered by `--yes` or by nobody there,
  nobody looks along the way, so the guardrails serve keeps hold: the
  majors hold before the edit, a tidy plan that isn't dockhand's own edits,
  what holds a submission, and `build.unattended`'s profile for the check.
- Its stage flags are update's edit flags and submit's, defined once in
  `versionUpdate.flags`, with `--build` beside `--on`.
- `tidyBranch`, the commit stage, split out of `tidyAndSubmit`;
  `checkHead`, ship's check stage, check `--head` with the profile in
  effect; `submitChecked` takes an `engine.WhereRequest`, `--build` among
  it.
- The batch exit rule: 1 where no change went through, 3 where some
  stopped and the rest went on; a single change's own error is its exit.

## ship --mine and --passing

- `ship --mine` takes outdated --mine's report through PlanOutdated: each
  port it plans ships at the release outdated found (no second upstream
  look), and each it leaves is said with why.
- `ship --passing` ships the branches PassingBranches finds ready: checked
  and passed, with no pull request of their commits yet.
- Ports, --mine, --passing, and a branch are one choice each; naming two is
  refused. "Nothing to ship." where a choice finds none.

## serve.ship_to

- `serve.ship_to = "list" | "commit" | "check" | "submit"` replaces
  `serve.for_outdated` and `serve.submit_passing` (the second look's §6
  table): how far serve carries your outdated ports each day, as ship
  --to does. `commit` is the old `draft`; `submit` is the old `check` plus
  `submit_passing = true`, with the same guardrails and daily limit.
- The old keys are refused with what replaces them, as check.on was, with
  no alias.
- `serve --submit-passing` / `--no-submit-passing` became one
  `--ship-to <stage>` for one run, which `--install` writes into the
  agent's command line. The design table named no flag; the old pair's
  one-run override is kept in the new setting's terms.
- engine: `ServeOptions.ShipTo` replaces `SubmitPassing` and
  `ServeOutdated.Mode`; `PrepareOptions.To` (a ShipStage) replaces `Check`.
  serve's hint for passing branches a person started now names
  `ship --passing`.
- README, usage (prose and settings table), and acceptance row S1 follow.

## The composite flags go; bump on ship

- Deleted: `update --submit`, `--outdated`, `--check`, and update's
  submission flags (`--on`, `--tested-*`, `--title`, `--note`,
  `--skip-notification`); `submit --check`, `--passing`, and `--on`. With
  them `submitPassing`, `updateOutdated`, `writeSkipped`, `writePrepared`,
  `batchNotes`, `preparedJSON`/`preparedView`, and `outdatedOptions`,
  deleted rather than moved (the roadmap's ≈105 judgment lines): a batch
  now runs each port's single update, so it says what a single update says.
- `versionUpdate.flags` is the edit's flags (update, ship, bump);
  `stageFlags` the later stages', defined once (ship, bump), `--build`
  among them.
- `update --mine` stays as the edit-only batch: one branch a port from
  fresh master, nothing committed, asking once (`-y` without). Its plan and
  ship --mine's share `outdatedBatch`: what the plan skipped is said by
  name, and the rest counted from `OutdatedReport.Summary` by class, less
  what was said by name (`restWords`).
- `bump <port> [version]` is ship's single-port front: `ship <port>
  --yes` with the version pinned. It now resumes an open branch changing
  the port rather than refusing, and its JSON is ship's.
- ship resumes a port's branch by running the edit stage again on it, so a
  branch at neither the pin nor the newest release is brought there, and
  its plan row says so ("its branch, updated again where it isn't at …");
  already there, the update says so and changes nothing. The roadmap's
  open rule, at its default.
- ship's plan shows, under each branch going on to submit, its submission
  as it stands (title, checks, pull request, upstream lines, holds), as
  submit --passing showed each: decision 2's one plan with every branch's
  holds. PlanSubmit runs with PendingCheck, since ship checks first.
- ship --plan shows the plan and changes nothing.
- One JSON shape for ship and bump: `batchJSON`, `changes` (each an
  update's shape with tidy, check, and submit inside) and `skipped`.
  `batchExit` is the batch exit rule, shared by ship and update --mine.
- Docs: README, usage (a ship section; bump, batch, submit, JSON, and
  check-refusal lines), and acceptance rows A10, B3, C5, D-T4, S2 follow.
  C5 now checks that ship's batch says each single update's notes.
