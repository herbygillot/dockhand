# 2026-09-30: someone else's pull request, and a port's dependents (batch 11)

Batch 11 of the [roadmap](../roadmap.md): `review` doing less than Design v3 §6.11 says, `impact`'s alphabetical next step, and dependents that link a port only under a variant.

## What changed

- **A revision's patches are checked against its source,** as an update's are. libuv's #34620 commented out `patch-libuv-legacy.diff`, which no longer applied to 1.52.1 in five files, and a second patch; `update libuv --plan` said the first didn't apply, and `review` said nothing of either (the libuv run's finding 2).
  - The revision assessment checks the revision's own patches, and each the base applied that the revision drops, against the revision's archives (`engine.revisionPatches`).
  - The archives are those `readPlans` fetched for the comparison, kept in a directory `assessPort` owns until both are done. One a kept reading spared fetching is fetched for the check, so no archive is fetched twice in one assessment.
  - A patch is read from its own version's tree, where `filespath` names below the port's directory (`macports.PortInfo.FilesPath`), so a dropped patch is read from the base. One the check can't reach is unchecked, with why, as coverage.
  - `assess` says them: `patch-rejected`, the revision's own that doesn't apply, which fails the build at its patch phase; and `patch-dropped`, one the revision drops, with whether it still applies. Neither holds: a check catches the first, and the second is its author's to explain. `assess.Policy` is 6.
  - The request MacPorts would patch with, `worksrcdir`, `extract.rename`, `patch.dir`, and `patch.pre_args`, moved from `portedit`'s private `checkPatches` into `patchcheck.Port`, which both now use. `macports.PortInfo.Patchfiles` reads `patchfiles` as a typed fact.
  - An update's own comparison doesn't carry these, since its preparation reports its patches itself, as it did.
- **`review` says what `update` would of someone's pull request.** It applied the commit and Portfile rules only, so it passed #34620 with "The commits and Portfiles follow the rules dockhand checks".
  - It now assesses each port the pull request changes against the base it leaves master at, as a branch's revision is assessed, patches included, and reads their dependents from the index at that base. Both are in its text, its Markdown, and so what it posts.
  - The assessment is `makeAssessments`, the loop `revisionAssessments` ran, which now records nothing itself: a branch's revision records what it makes, and a review, which no branch holds, records nothing.
  - What couldn't be assessed or read is said, never an error, so a review without MacPorts' evaluator still applies the rules. An engine that can't plan archives is `errNoPlanner`, which a branch's revision reads as before: what's recorded stands.
  - The lines are `submit`'s, through `comparisonLines`, which both now use; the posted Markdown leaves out `!` and `·`, which say what holds an unattended submission, a reader of the pull request's business.
  - The patch messages say what's dropped without "the candidate", dockhand's word for the revision assessed: "patch-libuv-legacy.diff, which the base applied, is dropped, and no longer applies to 1.52.1's source".
  - `port lint` and `review --check` aren't taken: lint would be dockhand's first use of `port lint`, and `adopt --pr` then `check` builds a pull request today. "Not checked here: `port lint` and the build" stays.
- **`impact` suggests one dependent of each kind,** not the first three by name. It suggested `check --also aria2,bind9,bind9.18` for libuv, among the heaviest of its dependents to build (the libuv run's finding 3). Nothing sizes a build, so `Impact.OneOfEachKind` takes one of each way a port depends there is, library first, then build and runtime where a dependent taken doesn't already cover them, and the line says how many of how many: "builds one of each kind of dependent against the branch, 2 of 20; name others with --also". Where that's all of them, it says it builds them.
