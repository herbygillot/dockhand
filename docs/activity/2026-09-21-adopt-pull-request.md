# Adopting a pull request

Herby's reviewer's-eye use of adopt: contributors open a pull request, cannot squash, and the pull request grows commits whose messages are not what the port wants. Everything dockhand needed for that existed but the entry point.

**`adopt --pr <url|number>`.** The pull request is read from the forge, refused unless open, and its head fetched from the head repository's clone URL into a local branch: the pull request's own branch name when the head is on the person's fork, judged by the authenticated login, and `pr/<number>` when it is someone else's, so a stranger's branch is not presented as the person's. A local branch already at the head is reused; one at another commit is refused rather than moved. The head is checked against the pull request's recorded commit, and the base against fetched master as for any adoption. A head of several commits, the case that matters, is adopted as it stands with its merge base recorded and the port directory derived from the whole range; the contribution is recorded with the pull request attached and its head as the published revision, so `sync` follows it and a publication updates it. A refused or dry-run adoption deletes the branch it created.

**`amend --squash`.** The branch's tree as committed becomes one commit on the contribution's base, which the correction path already did by construction; the subject is the pull request's title, prefixed with the port name when the author left it off, `--subject` overrides, `--closes` adds trailers, and `--edit` opens the composed message in VISUAL or EDITOR, comment lines removed, with an empty result stopping the amendment. The bound correction now carries its message so the editor has something to open. The amend then verifies and updates the pull request as any amend does.

**The body.** An existing pull request body without a Tested on section gains one at the end on the next update, since a person's pull request adopted by dockhand should show how it was built; the description and the checklist stay theirs; `--update-body` rewrites the section; and `--keep-body`, recorded on the contribution in a new column, leaves the body entirely its author's and refuses `--update-body`. Two publication tests that expected a hand-written body to stay byte-for-byte now expect the section beneath it.

**Pushing to someone else's fork.** Herby's call: allow it by default and let GitHub refuse when the person lacks the permission. A contribution with a pull request attached now derives its publication destination from the pull request, its fork as the push target and its base repository and branch, whoever owns the fork, instead of from the checkout's remotes, and the ownership check that guards the remotes-derived destination does not apply to it. GitHub allows the push when the pull request permits edits by maintainers and the account has write access to the base repository, which is what a reviewer's `amend --squash` of a contributor's pull request needs; when it does not, the push fails and the job says so. The fake forge gained a second remote standing for a contributor's fork, and the test squashes a stranger's pull request and finds the folded commit on that fork. Multi-target pull requests remain refused by naming their directories. The evaluation of a stranger's Portfile happens on the person's machine when the target is bound, which the help states and leaves to their judgement, as agreed.
