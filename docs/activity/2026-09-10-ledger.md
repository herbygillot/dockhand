# Ledger implementation report — September 10, 2026

Implemented the ledger storage boundary needed by the driver's claim/action/record cycle. This pass implements persistence and concurrency mechanics; it does not implement request intake, claims, cycle scheduling, providers, or CLI commands. The module and external Go dependencies are unchanged.

## Implemented

- `ledger.Read` returns a caller-owned snapshot from one captured state commit, without acquiring or creating the writer lock. Missing state, invalid state, unsupported schemas, and Git failures remain distinct.
- `ledger.Update` serializes writers through the Git common directory, rereads current state, invokes its callback once, and commits records with guarded ref changes. Callback errors and canceled callbacks do not commit. No-op updates avoid unnecessary state commits, and callbacks are not automatically retried.
- Writer lock acquisition and storage operations have configurable context deadlines. Nested writes using the callback's context are rejected. A callback that has not returned continues holding its lock even after its deadline expires.
- The initial format is one schema-versioned `state.json` per state commit. The decoder checks the envelope, collection presence, record IDs, unknown fields, and trailing JSON. This is structural storage validation; workflow transition and cross-record business rules belong to the workflow implementation.
- Each ledger commit parents the previous state commit. Source commits, base commits, trees, and desired publication heads receive Git pins. Existing pins are verified and new pins are created with the state/ref update; pins and history are retained indefinitely pending an explicit retention design.
- Git mechanics now include typed ref reads, guarded multi-ref updates, object-type batch reads, blobs, flat tree construction, and commits with explicit identities. They leave HEAD, the index, and working files alone.
- Plumbing commands disable hooks and signing locally, suppress replacement objects, lazy fetching, and credential prompts, and request object/ref fsync. These settings do not rewrite the user's Git configuration. Ledger commits and reflogs use a Dockhand identity, so a configured user identity is not required.
- A canceled or abnormally terminated final ref command returns `ledger.ErrCommitUncertain`, preserving the underlying Git/context error. Callers must inspect durable request or action records before deciding whether to retry.

## API and ownership

The constructor is now `ledger.New(repo, ledger.Options{}) (*ledger.Store, error)`. Zero-valued options select a five-second lock timeout and a thirty-second operation timeout. An earlier caller deadline still applies.

The write API is `Update(ctx, func(context.Context, *Transaction) error) error`. The callback receives the current records and captured version. It must use the supplied context for nested calls and keep external work outside the transaction. Go cannot forcibly stop an arbitrary callback; substituting an unrelated context also bypasses the explicit nesting check. The API does not promise otherwise.

`ledger` owns format, state history, writer locking, source pins, and the transaction boundary. `git` owns Git command execution, objects, and refs. No workflow state machine, provider operation, or process-residency mechanism was placed in either package. The writer lock uses the common-directory path `.dockhand-ledger.lock`.

## Validation

`go build ./...`, `go vet ./...`, and formatting checks passed. A newly authored, temporary Go integration harness ran with the race detector against disposable SHA-1 and SHA-256 Git repositories. No test files or harness were installed in v2.

The runtime checks covered:

- Missing-state reads without lock-file creation; round trips, schema/shape errors, mismatched IDs, and trailing JSON.
- No-op updates, callback errors, callback panics, nested transaction rejection, and cancellation before commit.
- Reads while another process holds the writer lock; bounded lock waiting; recovery after killing the lock-holding process.
- Concurrent writers from the original checkout and a linked worktree, with readers checking consistent related collections and no lost writes.
- Capturing a state ref, pausing the reader, advancing the ledger from another writer, and finishing the original snapshot read.
- Guarded ref create/update/delete/verify operations, multi-ref refusal without partial changes, and a deliberately injected state-ref race without callback replay.
- A callback continuing beyond its deadline while retaining its lock, followed by rejection of its late result.
- Git completing the ref update before an injected cancellation: the caller receives an uncertain outcome and the committed state remains recoverable.
- Broken refs, dangling symbolic refs, wrong state-object types, and refusal to invoke a mutation callback over corrupt state.
- Source pins retaining an otherwise orphaned source through record removal and `git gc --prune=now` in an idle disposable repository.
- Operation with a rejecting reference-transaction hook, signing enabled, and no configured user identity; preservation of HEAD, index bytes, and the working tree.

These are focused implementation checks, not a permanent test suite or a proof of all filesystem/crash behavior. No real ports tree, VM provider, remote Git repository, or forge was changed.

## Remaining work

The driver cycle, durable request intake, claims, status projection, and provider execution remain unimplemented. Derived notes, pin/history compaction, full model invariants, and application/CLI wiring are also pending. Remote observations do not imply that the corresponding Git objects are present locally.

This storage format does not import or migrate the v1 ledger. An incompatible existing state ref is rejected rather than overwritten. Independent live branch reads are separate observations from a ledger snapshot; Git's multi-ref writer transaction does not provide atomic cross-ref visibility to readers.

Git 2.55.0 and Go 1.27.1 on macOS were used for validation. There is no compatibility fallback for a Git executable lacking the plumbing options used here, and no claim of validation on other operating systems. The write lock uses Unix `flock`.
