# macOS 27, Golden Gate

Added to the release table in `internal/macos`: Darwin 26, macOS 27, Golden Gate, slug `golden-gate`. The slug is not a guess. Cirrus Labs publishes the vanilla image dockhand provisions from, and the registry has `cirruslabs/macos-golden-gate-vanilla` with tags `27.0` and `latest`, while the hyphenless spelling does not exist; the same query confirms the product version this release carries. So `--os golden-gate` or `--os 27` provisions `dockhand-base-golden-gate` from that image, and `Describe` words a Darwin 26 platform as "macOS 27 (Golden Gate) arm64".

The table was already the single location, but two places restated it and only one entry made that visible. `ParseRelease`'s refusal listed the releases by hand, so it would have offered five names while the table carried six, and `tart.ReleaseForPlatform` decided what was provisionable with a literal `darwin < 21 || darwin > 25`, which would have refused Golden Gate however the table was edited. Both now read the table: the refusal is composed from a new `macos.Known`, oldest first, and the provisionable set is whatever `ReleaseForDarwin` answers to. The next release is one line.

Tests hold that to it. One walks every entry in the table and asserts it resolves by Darwin version, by slug, and by macOS version, that the refusal names all of them, and that the list is ordered; another asserts image and vanilla-source names for every known release, so a release added to the table is provisionable without touching the Tart package. The bound that was hardcoded is now tested at the table's real edge, Darwin 27, rather than at Darwin 26, which is a release.

Being in the table makes a release selectable, not the one dockhand uses. `tart.DefaultDarwin` names the release built unasked, and it stays Tahoe. It lives in `internal/tart` rather than beside the table, because it is not a fact about macOS: `internal/macos` is reference data, the Darwin, product, name, and slug of each release, while which of them a build defaults to is Tart's policy, and the GitHub provider does not consult it at all. The reasoning: MacPorts adds a macOS to its own CI well after Apple ships it, and local verification should prove what a pull request is built on. A host newer than that is asked rather than assumed. `setup` with no `--os` on such a machine names both spellings instead of provisioning one, and Tart verification with no `--image` reports no suitable image, which is the error `--provider auto` already falls back to GitHub on, so a contributor on a brand-new macOS gets their build from the runners MacPorts supports rather than from an untested local VM.

Worth recording because it constrains the next question: Tart verification builds on the image's own release and nothing else. The job validator refuses a preparation and build platform that disagree, `guest.tcl` asserts the guest's `os_major` equals the platform the spec names, and the image capability check compares the image against that same platform. So "verify on Tahoe from a Golden Gate host" is not a default to change; it is cross-release local verification, which does not exist and would be a design item.

Nothing has been provisioned on Golden Gate. `--os golden-gate` makes it selectable; whether the provisioning recipe works there is unproven, and the first run will say.
