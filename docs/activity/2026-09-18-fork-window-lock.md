# A closed lock that still looks busy

`TestLogCacheRetentionChecksIdentityAgeAndRequestLock` failed in a full-suite run after vendoring, at its first prune: the log cache was reported busy with no holder. The test had flaked before, and the earlier fix was about the order of the identity and lock checks, not this.

The cause is `fork`. A child process forked while some goroutine held a `flock` inherits the descriptor, and the lock stays with it until the child execs, however soon the holder closes its own copy. Go's `os/exec` forks and then execs, so every `git` the test suite spawns from another goroutine opens that window, and on a loaded machine it lasts milliseconds. A probe made it plain: with four goroutines spawning `/usr/bin/true`, one try in ten at a lock its holder had just closed came back busy; with none, none did. The non-waiting `TryExisting` was the only path that could see it, since `Acquire` retries.

`TryExisting` now keeps trying for a quarter second before calling a lock busy: longer than any fork-to-exec window, far shorter than any real holder, which keeps a cache lock for the length of a download or an index build. Its three callers, the log-cache prune, the PortIndex retention sweep, and the PortIndex cache guard, all tolerate the wait. The lock package tests that a lock released inside the grace is acquired, that a holder who keeps it is still reported in about the grace, and that two hundred close-then-try rounds succeed with commands spawning alongside. The GitHub provider package passed four rounds under two and eight CPUs, where it had failed before.
