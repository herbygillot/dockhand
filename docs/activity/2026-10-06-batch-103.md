# 2026-10-06: serve restarts on an upgrade (batch 103)

From the v0.3.0-rc3 full stage's A7, and the person's "stop, fix serve, reset for rc5". After `port upgrade` from rc3 to rc4, serve's launchd agent went on running the replaced rc3 binary: its log said nothing, and rc4's `status` said "serve: running (pid 3761)" with no word of the older build.

## What changed

- **serve watches the file it runs from.** It notes its executable when it starts, and between checks, never during one (Design v3 §11), looks again: a new file at that path, as port upgrade installs, or the same one rewritten, is an upgrade. serve says "serve: dockhand was upgraded; stopping once its checks end, so launchd starts the new build", starts no more checks, and once those running end says "serve: stopped for the upgrade" and exits 0; launchd's KeepAlive starts the new build. A drain watches nothing, since it ends by itself.
- **status says when serve runs another build.** serve records its build in serving.json, and `status` and `queue` say "serve: running (pid N) · on dockhand v0.3.0-rc3, where this is v0.3.0-rc4" when it differs from their own; `--json` has it as `serve_state.build`.
- **A database a newer build migrated is refused at the next transaction.** The schema was checked only on opening, so an old serve went on with its own code against a newer schema. Every transaction now reads `PRAGMA user_version` first and refuses a newer one as opening would, so a serve that missed the upgrade, or met a migration from a build elsewhere, fails its next read, exits, and launchd starts the new build (the person's question).
- **serve --install's hint** no longer says to reinstall after an upgrade, and the README says the agent starts again on the new build.
- **A7 checks it.** It notes serve's PID and log before the upgrade, waits for a new serve to lead, and passes only when the log says the upgrade and the stop, the PID changed, and status names no other build.

## The pull request serve didn't report closed

The same run's serve.log still said herbyg-test/macports-ports#1 was open 40 minutes after it closed. serve's follower reads every followed pull request each five minutes, and says a state change against the observation stored in the database, so a closing another dockhand process recorded first, as `status`, `watch`, or `clean --closed` do, or a branch cleaned away, is never said by serve. That's the likely cause, unconfirmed: the branch's `pull_request.observed` in `status --json` says which.

## Verification

- Tests: a serve whose executable is replaced stops, saying why, and returns no error; status names a serve's other build, and nothing for one that didn't say; serve's state carries its build; a database migrated past the build while open is refused at its next transaction.
- The full checks: fmt-check, vendor-check, vet, lint, deadcode, and the suite under MacPorts (port-tclsh).
