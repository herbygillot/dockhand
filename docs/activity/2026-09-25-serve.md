# 2026-09-25: `serve` and `serve --install`

Roadmap step 5, part 8's last piece (Design v3 §11), built on the coordination primitives from part 2.

## The command

- **`dockhand serve`** takes the repository's leader lease and runs the queue:
  - first, a run left running by a driver that is gone;
  - then queued runs a person asked for;
  - then `serve`'s own, oldest first.

  It keeps looking for new work. A run a live session holds, such as a foreground `check`, is left to it.
- **Standing by.** A second `serve` says which process leads and waits, taking over when the leader dies. A leader that finds its lease taken, because a standby judged it dead, stops rather than drive work twice.
- **What it says when it starts:** the providers it builds on, and that it opens no pull requests. `--submit-passing` doesn't exist yet, so today it only checks.
- **Stopping loses nothing.** When `serve` is stopped, the run it was driving is left running. The next `serve` picks it up first and builds only the targets without a verdict. The interrupted execution counts as one of its three attempts: `model.MaxAttempts` bounds attempt numbers, and a restart is a new attempt. A foreground `check` interrupted with Ctrl-C is still canceled, as §11 says.
- **`--drain`** runs what is queued now and exits, for scripts and for a Mac that isn't on all day. With another `serve` leading, it says so and does nothing.
- **`--install`** writes a launchd agent, `~/Library/LaunchAgents/io.github.herbygillot.dockhand.serve.plist`, and bootstraps it into the GUI domain.
  - It runs this binary as `serve --tree <clone> --db <database>`.
  - It keeps the installing shell's `PATH`, since launchd's lacks git and MacPorts.
  - It starts at login, restarts if it stops, and logs to `serve.log` beside the database.
  - `--uninstall` boots it out and removes the file.
  - Anywhere but macOS it refuses and says why.
- **Handing off.** `check` and `wait` hand a run to a leading `serve` and follow it. If `serve` starts between `check` enqueuing a run and driving it, `check` sees the run taken and follows it rather than failing.

## Found by the tests

`serve` stopped with its context canceled returned "context canceled" as an error. Race runs of the hand-off test found it: a failing assertion left a `serve` goroutine running into the test's cleanup. Being stopped is now how `serve` ends, and it prints "serve: stopped".

## Tests

- **Engine tests:**
  - a stopped resumable driver leaves the run running;
  - the next session picks it first and finishes it on attempt 2;
  - people's queued checks come before `serve`'s.
- **Command tests:**
  - `serve --drain` runs two queued checks in order and empties the queue;
  - a `check` handed to a running `serve` and followed to its result;
  - `check -d` naming the leader;
  - a second `serve` standing by;
  - `--drain` deferring to the leader;
  - `--install` and `--uninstall` with a stand-in `launchctl`, checking the plist's arguments, `KeepAlive`, and the bootout and bootstrap calls;
  - the refusal off macOS.

  Each concurrent test was run nine times under the race detector.
- The full suite passes with `TMPDIR` behind a symlink, as on macOS, and so do the race runs, `go vet` (Linux and `GOOS=darwin`), `make vendor-check`, and `make fmt-check`.

**Not proven here:** launchd itself, which needs a Mac: `serve --install`, then log out and in, and `dockhand queue` should show serve running.
