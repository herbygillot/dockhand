# Completing the structural review

The remaining items from the [structural review](../reviews/2026-09-16-bump-machinery-structure.md), each landed as its own commit. Sections are added as items complete.

## Checksum refresh through the observed archive plan

`refresh-checksums` used the plain declaration path, which requires the evaluated distfiles to cover every checksum exactly once. Ports that declare per-platform distfiles, deno among them, declare checksums for every platform while evaluating only the native one, so the refresh was refused with "checksums must cover every source distfile exactly once". The version bump already handled the same Portfiles by observing every modeled context.

`prepareChecksums` now plans through `planObservedChecksums` whenever the reader can observe: every modeled context is observed on the unchanged Portfile, each bound archive is planned once, and the existing `applyObservedArchives` downloads, rewrites the checksum tokens, and checks fidelity per context. Since nothing but checksums may change, every context is a protected context. `archivePlan` carries the commit subject so the apply path no longer composes it from a release, and it returns early with the downloads when the refreshed contents equal the original, which is how "already current" is reported. The plain path remains for readers without observation. `Result.Coverage` lists the observed contexts as it does for bumps.

Checks: a new test refreshes a Portfile with `build_arch`-conditional distfiles, downloads both archives, rewrites both checksum groups, preserves version and revision, restores the workspace, and reports no change on a second refresh. The existing preparation checksum tests now run through the observed path unchanged. On the real tree, `refresh-checksums deno --diff` observes darwin 25 arm64 and x86_64, downloads both archives, and reports the port current in 19 seconds.

## A policy leaf under workflow

`verification_reuse.go`, `publication_coverage.go`, and `publication_policy.go` were read-only questions over a `state.Reader`: which recorded evidence applies to a build question, whether evidence covers a publication's whole cohort, and whether a publication action still matches its job. They depended on `workflow` only for `ErrInvalidRequest`, the `preparationAction` predicate, and one `Engine` method that opened a state view. The decisive test was `publicationEvidence`, called from both submission and the publication runner; it needed nothing from the cycle.

They now form `workflow/policy`, with `SelectVerification`, `SelectRecordedVerification`, `PublicationCoverage`, `DescribeCoverage`, `PublicationEvidence`, and `ValidatePublicationAction` exported and the package importing only `record`, `state`, `verify`, and `publish`. `workflow.ErrInvalidRequest` is an alias of the policy error, so callers see the same identity. The unnamed revision-and-source pair `publicationInput` became `record.Job.EffectiveSource`, and `preparationAction` became `record.Action.Prepares`, both of which the review had asked for by other names. `verification_select.go` stays in `workflow`: it selects among an `execution`'s attempts and names a runner action, which is driver mechanics, not policy. The intake-versus-drive split remains possible but is not needed now that the shared questions have a home.

Checks: the workflow suite is unchanged in behavior; a record test covers the effective source before and after preparation and which actions prepare. `go test ./... -count=1` and `go vet ./...` passed.

## One subprocess runner

Git, Tart, launchctl, the dependency generators, and both portindex invocations each built an `exec.Cmd` by hand with different wait delays (one second, two, or none), different error wrapping, and inconsistent joining of the context error. `internal/subprocess` runs one command with the shared conventions: a two-second default wait after cancellation, captured output that is returned even on failure, an optional extra sink, combined streams on request, a byte limit per stream, and one `Error` naming the tool, the command, the cause, and what the tool wrote to stderr. The exit status stays reachable through `errors.As`, which the portindex incremental-coverage check and the launchd service probe rely on. Each caller keeps its environment policy; git's blocklist is untouched because the runner takes a complete environment and never adds to it.

`git.CommandError` is now an alias of `subprocess.Error`, so the one caller that inspected its cause is unchanged. Git names the subcommand rather than its leading `-c` flag through the spec's `Command` field, which the CLI tests caught. Tart's messages read `tart clone: ...` instead of `tart: clone: ...`, and its test expectation follows. The dependency generators' bounded buffer embedded `bytes.Buffer`, which promoted `ReadFrom`; `io.Copy` prefers that over `Write`, so the manifest limit had never been consulted. The runner wraps the buffer instead and its test proves the limit trips.

Checks: runner tests cover capture, failure shape, the reachable exit status, combined streams, the extra sink, input, working directory, environment, output limits, and cancellation joining. The git, Tart, host, provision, dependency, portindex, and preparation suites pass, and `outdated deno` on the real tree runs git, the Tcl probe, and portindex through the runner.

## The version-input set

The carrier slice was passed to four functions with a source version and a fidelity flag, and the loop that turned carriers into candidate Portfile edits was interleaved with evaluation. `versionInputs` names the set, and its `edits` method proposes the distinct edits that could select a source version: applying each relation's prefix, suffix, numeric, or separator mapping, refusing non-literal or unchanged values, and collapsing relations that predict the same edit, since ambiguity is between distinct edits, not between ways of deriving one. `evaluateVersion` now only evaluates those proposals and applies the selection rules. No behavior changed; the portedit, preparation, upstream, assess, and outdated suites pass.

## Counting waits

Expected waiting reset the failure count and scheduled the flat wait interval, so a wait that never resolved, such as a forge that never observes a pushed branch, looped forever at that interval with nothing recorded. `record.Lease` gains `ConsecutiveWaits`; `await` increments it and stretches the interval by doubling up to a five-minute ceiling, `fail` and settled outcomes reset it, and `finishJob` clears it. Schema 18 adds `consecutive_waits` to jobs, attempts, and resources, and the migration contiguity test covers it. Status prints "waiting: N consecutive waits; next look ..." on a job or attempt after the second wait, so an unresolved wait is visible without escalating to a terminal state; whether a long wait should settle as needs-attention remains a policy decision the review left open.

## A fidelity package

The comparators that decide whether an evaluated edit changed only what it was meant to, `revisionFidelity`, `versionFidelity`, `checksumFidelity`, the scoped variants, `releaseScope`, `comparablePort`, `comparePortMetadata`, `CheckEquivalent`, and `checkSnapshot`, were pure functions over snapshots with no `Service` dependency, and `workflow/preparation` already imported one of them across the package boundary. They now form `macports/fidelity`: `Report` is the comparison result, `ErrMismatch` its refusal, and `Revision`, `Version`, `Checksums`, `ScopedVersion`, `ScopedChecksums`, `ReleaseScope`, `Equivalent`, `Compare`, `ComparablePort`, and `CheckSnapshot` are the questions. `portedit.Fidelity` and `portedit.ErrFidelity` are aliases, so `Result.Fidelity` and every `errors.Is(err, ErrFidelity)` outside the package are unchanged. `checkSharedArchiveOwners` stays in `portedit` because it binds archives through the service. No behavior changed.
