# An advisory test failure stalled verification

Found by bumping `py-cssselect` while exercising dockhand on ports that are not Herby's. The port declares tests, the default policy runs them as advisory, and they fail. The guest script records that faithfully: the test step's verdict is `failed`, `TestFailure` says why, and the overall verdict is `passed`, which is what advisory means. The host judge then refused the result as "passing observation contains a non-passing step", the provider returned that as an error from every observation, the driver retried the observation on its schedule, and the VM stayed up for fifteen minutes with nothing left to do. Every port with declared tests that fail would have stalled the same way; the ports bumped before it had none that failed.

Two changes. The judge, and the reuse rule that repeats its check, accept exactly one non-passing step under a pass: the test step, failed, with the advisory failure recorded. The step keeps its failed verdict, since that is what happened. Any other disagreement between the guest's result and the judge is now settled by the provider as an errored, finished observation whose detail quotes the judge, with the build log kept and the VM released, rather than observed again forever; a disagreement between two programs is not something another look changes. Tests cover the accepted case, the two refused shapes, reuse of a pass with an advisory failure, and the provider settling an inconsistent result.
