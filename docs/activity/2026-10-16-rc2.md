## High 1: --yes approved plans it never showed

- **The command's ship** set `linked.yes = true` on every run, which
  tidy read as `AnsweredYes`, and `AppliesUnasked` lets AnsweredYes apply a
  plan that isn't dockhand's own edits: a hand-edited branch was committed
  unreviewed by `ship --yes`, and by ship with no terminal at all, against
  its own help. `tidyBranch` now takes no yes: a plan of dockhand's own
  edits is applied unasked, one with the person's is reviewed on a
  terminal, and held where nobody looks, `--yes` or no terminal, since
  --yes skips ship's question and approves nothing shown after it.
- **The engine's ship** had the same gap at its commit gate (`goOn`),
  passing AnsweredYes through: it now judges an unattended commit as
  nobody's. `ShipOptions.Unattended` reads model.Answered as the command's
  `shipAll` does, anything but AnsweredAsked.
- **Serve's preparation** built its UpdateRequest without `Unattended`,
  so the early gate for another open pull request, or not knowing, never
  ran: an update was prepared and checked before submission held it. It's
  now held before its edit, as bump's and ship's are.
- A held update's hint named `update --new --submit`, which v0.4.0
  removed; it names `dockhand ship <port>`, on a terminal.

## Medium 4: a pass stood for checks it didn't cover

- ship skipped a check where the branch's latest passed, whatever `--on`,
  `--build`, or `--tests` asked, and followed any running check of the same
  files. `engine.Covered` judges the finished checks of a tree against the
  plan the ask proposes: every target it builds, in every environment it
  builds there, passed under tests at least as strict (unmet cells
  standing). `engine.PlanCovers` asks the same of a running check's plan:
  ship follows one that covers the ask, and otherwise says so, naming the
  cancel. `prepareSubmit` takes the check path whenever `--on`, `--build`,
  or `--tests` was given, so a pass of the default doesn't stand for one
  of them (`WhereRequest.Explicit`).

## A Git rename onto an archived branch's name (the rc1 full stage, D-S5)

`git branch -m dockhand/ds5-before dockhand/ds5-after`, where an archived
record (its own Git branch gone) still held ds5-after, made every status
fail: followRenames carried ds5-before's record over to the new name, and
the update tripped the index of one not-merged branch a name. v0.3.1 has
the same path; it wasn't reproduced there.

- `carryRename` reads the name's holder in the same transaction. An
  archived or closed one without a pull request is renamed aside,
  `<name>-archived` (`-2`, `-3` where taken), with an event, as start
  renames one (b717dbad), and the record carries over. An open one, or
  one with a pull request, keeps the name: `RenameHeldError`, and
  followRenames leaves the branch untracked, as it leaves one two records
  could be, rather than failing status.
- TestStatusFollowsARenameOntoAnArchivedBranchsName reproduced the
  failure without the fix ("UNIQUE constraint failed: branches.repository_id,
  branches.name") and passes with it.
