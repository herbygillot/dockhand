# Running a GitHub verification again

Run discovery matches a run by commit, branch, push event, and workflow, and deliberately ignores the attempt number, which is how a run rerun by hand is picked up. The same property made retrying inert. A test already pinned it: two independent jobs verifying one commit both adopt run `10:1`. So after a GitHub verification stopped for a reason beyond the change, the retry the status table now offers re-read the same finished run and reproduced its verdict, having run nothing. The contract document said as much and told the reader to rerun it themselves on GitHub first.

The provider now asks. When the run it finds for the accepted commit has finished without succeeding, it requests a rerun of the unsuccessful jobs, re-reads the run to learn the attempt that produced, and observes that attempt. `RerunFailedJobsByID` is the call, so a matrix costs one runner rather than three, and GitHub adds the attempt to the same run rather than creating another, which keeps the run identity discovery already relies on. Earlier attempts stay readable, so a job watching attempt 1 keeps reading attempt 1 and its verdict is unaffected.

When this is allowed is the part worth stating. A rerun is a write to someone's fork, and the line drawn is that it happens when a person asks for a verification and never on a driver's own initiative. That is not a new authority: the command that reaches here already pushes their branch to their fork and runs that workflow, and this re-runs the same workflow on the same commit dockhand pushed. The engine also asks this provider for a verdict only when recorded evidence failed to satisfy it, so a request arriving at a finished failure is someone who wants a fresh answer, not someone who would be content with the old one.

Asking is bounded without anything being written down, which matters because an execution row's payload is immutable after acceptance by design and only its state, occupancy, and result may change. A run that accepts a rerun is no longer finished, which is the condition that brings anything here, and the caller admits a run either way in the same pass, so the path is not re-entered for that request. A refusal is not fatal: a run GitHub will not repeat, because its logs expired or it has no unsuccessful job to repeat, still carries the conclusion it reached, and that is observed.

The adapter has its first write. It had five methods and all five were reads, which was worth preserving until there was a reason; this is the reason, and it is one method. Tests cover the rerun and the attempt it produces, a refusal and an attempt not yet published both falling back to the finished run, one ask per request, and a run that succeeded or is still going being left alone.
