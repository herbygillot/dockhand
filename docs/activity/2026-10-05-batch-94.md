# 2026-10-05: field testing's batch 13 (batch 94)

Batch 94 of the [roadmap](../roadmap.md): field testing's batch 13, run at 73b659da. It comes after v0.3.0-rc1 (6fec2ac8), which the full stage tests; none of it is in that candidate.

## What changed

- **A new llvm-sys is said with the LLVM it links.** perry 0.5.1159 to 0.5.1520 added llvm-sys 221.0.1 to its Cargo.lock, and the update said nothing of it: the crate links "llvm", and MacPorts has no port of that name, so it was set apart as a library MacPorts lacks. llvm-sys's major version is LLVM's major and minor together, 221 for LLVM 22.1, which MacPorts has as llvm-22. A crate whose version names its library's (`project.CargoPackage.NativeLibraryVersion`) is looked for at that series first (`macports.LibraryPortsAt`): "Cargo.lock adds llvm-sys 221.0.1, which links the native library llvm 22, which MacPorts has as lang/llvm-22: the Portfile may declare it". A Portfile's dependency on llvm-22 is taken as one on llvm, for a crate that's gone. It holds nothing, as D9 decided of every new -sys crate (2026-09-29); field testing asked for a hold, which is the person's to change.
- **Cargo's target/ isn't taken for a source path that's gone.** perry's 0.5.1159 tarball carried a target/ directory and 0.5.1520's didn't, so the comparison held on "upstream's source no longer has target/". target/ is what Cargo builds into, for a port of the cargo or rust PortGroup (`macports.PortInfo.BuildsInto`).
- **A library-only workspace member isn't a binary added.** mise's new mise-dotenv, with no [[bin]], was held as a binary added. A package with no [[bin]] builds a program only where it has src/main.rs or a .rs file in src/bin, by Cargo's conventions. The reading now keeps which package directories do (`project.Reading.Programs`, reader version 7), and the others are libraries, counted with the members' dependencies rather than held.
- **fnox updates.** It was refused, "fetch customization or vendored source requires a dedicated preparer", and bumped by hand twice. A port of the cargo PortGroup that declares no crates, as fnox, whose empty `cargo.offline_cmd` has Cargo fetch them as it builds, was still taken for one whose crates to regenerate, through the source downloader that refuses a Git fetch. One that declares none and builds online, its `cargo.offline_cmd` empty, has nothing to regenerate, and its version line is the update, as for any Git-fetched port; one that builds offline still has its crates added, as before.
- **`edit --no-open`** brings a port's directory into the worktree and prints its Portfile's path without running an editor, where `EDITOR=true dockhand edit` stood in for it.
- **A Rust failure's cause is rustc's placed error.** perry's failure named Cargo's command and "build failed, waiting for other jobs", not llvm-sys's "No suitable version of LLVM was found", at its lib.rs:542. The log's reading now takes the first `error:` or `error[E…]:` line that rustc places on the next with `--> file:line:col`, and says where: Cargo's own "error: could not compile" places nothing, and isn't taken.
