# 2026-10-08: serve writes its login's state before saying it (batch 119)

From the rc9 full stage's D-C3. serve said "GitHub rejected its login" once, and that it was logged in again on the new login, as it should; but `queue --json`, run right after the rejection's line, read serve as acting, with no `not_acting`.

## The cause, and what changed

serve said a change of its login's state, then wrote `serving.json`, which status and queue read. A reader that follows serve's line, as D-C3 does, can read the file between the two. The login gate (`loginGate.set`, and `unread` for a login it can't read) now writes `serving.json` first and says the change after, so whoever reads it on the strength of serve's line finds it.

Prime-time's other suspects hold on reading: `ServeState` takes `serving.json` where its PID is the leader's, and serve writes its own PID, which a launchd agent's is too; and the file is kept beside the database by repository, which queue resolves as serve does. If D-C3 still reads serve as acting, the M1's `serving.json` beside its queue output will say which.

## Verification

- Test: a serve whose login is rejected, then back, has `serving.json` saying it isn't acting when it says the rejection, and acting again when it says it's back.
