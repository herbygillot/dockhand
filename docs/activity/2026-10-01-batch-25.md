# 2026-10-01: what the limits sweep and the SQL rescan found (batch 25)

Batch 25 of the [roadmap](../roadmap.md), taken at the person's word after a sweep of every size, time, concurrency, and retry bound in dockhand, which the person asked for on learning of the download cap, and the SQL review's rescan of the same day. The sweep's whole list is now [limits](../limits.md); what it found that can wait is batch 26.

## What changed

- **A heartbeat goes on after a failed write.** Each process records every 5 seconds that it's alive; a session silent for 2 minutes may be judged hung, and its leases taken. `KeepAlive` returned on the first failed beat, and its caller discarded the error, so one write that waited past SQLite's 5-second busy wait or 30-second transaction bound stopped that process's heartbeat for the rest of its life. Two minutes later another session could take a live serve's lead, or the lease on a run a foreground check was driving. A failed beat is now tried again at the next; a run of failures is said once, with how long another dockhand waits before it may take over, and so is the beat that ends it.
- **A request waits a minute for a response, not forever.** Every HTTP client was Go's default, which bounds connecting at 30 seconds and a TLS handshake at 10, but not the wait for a response: a host that accepted a request and never answered held `outdated`, and serve's daily look, as long as the command ran. `fetch.Transport` is Go's default with the response's headers bounded at a minute (`fetch.ResponseWait`), and `fetch.Client` carries it; the GitHub client, PyPI, the Tart registry, the device flow, the mirror's index, upstream discovery, and archive downloads all go through it. A body that stalls after its headers is still the caller's to bound, as a download's two minutes are; the rest is batch 26's.
- **A migration's copy is kept only once it's whole** (an agent's work, reviewed and merged; the SQL review's rescan). Before migrating, dockhand copied the database with `VACUUM INTO` straight to `dockhand.db.schema-N`, which it writes as it goes. A copy cut short, by the open's 30-second bound, a read error, or the process's end, left an empty or partial file there, which the next open took for the copy and migrated past; an empty one even opens, as an empty database, so nothing said it was bad. Two opens at once could each copy to that name, and `VACUUM INTO` refuses one that holds a database, failing the later open. The copy is now made under a `.partial-` name, synced, and renamed into place once whole (`keepCopy`); where another process's copy is in place first, it stays. A partial file never counts as a kept copy, and one left over an hour by a process that ended is removed at the next migration. A truncated copy already in place from a build before this one is still taken as the copy.
- **A revision's assessments are read by its key** (the same agent and review). Every check, serve candidate, and submission read and decoded every assessment its branch had ever recorded, only to keep its revision's. `Reader.Assessments` takes a filter, as `Runs` does, and a revision's are found by branch, tree, and base through the table's primary key; the engine still applies assess's policy. Narrowing the query alone wasn't enough: ordered by `at`, SQLite walked the branch's `assessment_branch` index to spare itself a sort, every row the branch had; ordering by `+at`, which no index holds, makes it seek the key and sort the revision's few, and a test asserts the plan.
- **The limits are written down.** `docs/limits.md` lists each bound by area, with its value, what happens when it's reached, and where it lives, the seven config keys that are the only knobs on any of them, and the guards that refuse input. `docs/usage.md`'s settings point to it.
- **D6 says what the rescan found.** Logs come first by weight, 780 MB across 62 checks and never removed; a build's inputs are about 6 KB, not 3.6, and have three readers since batch 20, so pruning them needs a deliberate answer in each.

## Decided along the way

- **Bound the wait for headers, not the whole request.** A total timeout on a shared client would cut short a large download or a long job log as readily as a host that never answers; the response's headers are the one wait every request has, and the one that hung.
- **Say a failed heartbeat; don't stop for it.** A process that can't record its heartbeat is still doing its work, and stopping the heartbeat makes certain what a slow write only risked. The message says what's at stake, since a person may want to free the database.
