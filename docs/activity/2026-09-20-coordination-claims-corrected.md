# Two races that were not there

The [instance coordination note](../instance-coordination.md) of 2026-09-18 ended with two concrete items: that `setup` takes no lock while provisioning or rebuilding, so a rebuild could race a verification clone, and that Tart capacity is a database count, so two databases on one machine could both believe a slot is free. This morning's reconciliation put both at the head of the roadmap's candidate list, as small fixes to behavior that was wrong today. Reading the code found neither claim true.

`internal/tart/lock.go` has kept three locks per image name under the selected Tart home since 2026-09-14. `Adopt`, the single step that replaces an image, takes an exclusive write lock. `Machine.Clone` takes a shared read lock before cloning a base image into a per-attempt VM, and the image inspection path takes the same. `provision.Run` takes a third, exclusive lock before it lists anything, so two setup recipes for one image serialize end to end. A rebuild racing a clone is excluded, and has been for a week.

Capacity is not a database count either. The admission check unions `machine.Running`, which asks Tart which VMs are running on that home, with `Occupied` from the database, and compares the union against the limit. A second database sees the first one's VMs because they are real VMs with names, and it sees one a person started by hand. The residual gap is narrow and worth stating at its real size: a VM is recorded occupied, then cloned, then started, and cloning a macOS image takes minutes, so during that window a reservation is in neither the other database's records nor `tart list`, and two databases sharing one Tart home can each overshoot by one. A lease file would close it, for whoever actually runs that way.

The mistake was inferring absence from a search that did not cover the right packages: a grep for `filelock` across `verify/tart` and `app` found nothing, and the locks live in `internal/tart` and are called from `internal/tart/provision`. The [setup report](2026-09-14-tart-setup.md) of 2026-09-14 already said, in one sentence, that the locks live under the Tart home so processes using different databases still coordinate access to the same VM store. The answer was in the repository before the question was asked. The note, the roadmap's Next and Needs-design sections, and this morning's reconciliation note are corrected.
