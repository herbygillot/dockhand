# 2026-10-01: what the rust and cargo update found (batch 24)

Batch 24 of the [roadmap](../roadmap.md), from the dogfood session's hand update of rust 1.99.0 and cargo 0.100.0 ([#35084](https://github.com/macports/macports-ports/pull/35084)). The archive sizes it found are their own [note](2026-10-01-archive-sizes.md), and the patch check's overlay its [own](2026-10-01-vendored-port-patches.md); the pull request's two items are an agent's work, reviewed and merged.

## What changed

- **The crates declaration that ran is the one edited.** cargo's Portfile declares `cargo.crates` in each branch of an `if` on the platform, current crates for newer systems and a frozen list for older, and `update cargo --plan` refused it: "cargo.crates requires one explicit declaration", since only the Portfile's top was read. Declarations are now found wherever MacPorts runs them (`portfile.RunCommands`, from the traversal that tells a body from data), and of several, the one whose literal list is what MacPorts evaluated is the one that ran: an update edits and strips it, laid out as it was, and leaves the other as it is. Two at the top, which both run, the later replacing the earlier, are still refused; several in bodies that are each, or none, what was evaluated can't say which ran, and say so.
- **A refusal is said once, plainly, with the way on.** `update rust --plan` stopped with "fidelity: evaluation does not match the intended change: [fidelity: evaluation does not match the intended change: rust-src has independent distfiles; shared-source preparation is required]" and no next step. A fidelity report's changes are said once and joined (`fidelity.Report.Err`), not printed as a list inside another; the release scope's refusals say what the person sees of the Portfile, "rust-src, another port of the same Portfile, fetches its own source (its distfiles differ from rust's), which updating rust doesn't move"; and one that named an `assess` command v3 hasn't names `--shared-release`. `update` refuses such an edit as one it can't make (`engine.ErrFidelity`), with "Edit the version yourself; dockhand checksums rust then fills in the rest".
- **tidy says what the commit rules warn of.** It said "nothing to tidy" where `submit` warned of a body line over 72 characters, and saved no plan to fix it in, so the person restored a checkpoint and applied a plan by hand. Where the commits break no rule but one warns, tidy says the warnings as `submit` does, keeps the commits, and `--plan --out` saves them as they are, to rewrite a message and `--apply`; `--json` gives them under `warnings`.
- **A result's reason is said in the pull request.** Tested on read "tests failed (advisory)" for rust on both Tart releases, where its bootstrap had panicked on a permission error before any test ran, and nothing said so. The guest's `why` kept the last Error lines of the whole log, and quoted lint's "Line 120 hardcodes /opt/local, use ${prefix} instead", which lint says and goes on; it now reads from the latest mark, where the failing step began. Under the table, each reason a result gave, a failed build or failed tests, advisory ones included, is a note, its cells marked: "¹ rust on macOS 15, macOS 26: `tests: Failed to test rust: command execution failed`", once for every port and environment that gave it. Only the wording changes, so `VerifierProtocol` stays 2.
- **A person's note in the pull request.** dockhand writes the whole description, so a person couldn't say in it why rust's tests failed. `submit --note "text"` records a note with the branch (schema 27, `branches.note`), and the description gives it under Description, after dockhand's part, as a quote led by "Author's note:", kept whenever dockhand writes the description again. A new `--note` replaces it, updating the pull request through the Description refresh submit already makes; `--note ""` takes it out, and `--plan` records nothing. A Description edited on GitHub stays the person's, without the note, which the preview says; someone else's pull request takes no note, nor does `--passing`.

## Decided along the way

- **Which ran, by what was evaluated.** The evaluator could say which declaration it ran, but the evaluated list matched against each declaration's literal one says it with nothing new, and a list that matches none was already refused as calculated.
- **`cargo.update` stays refused.** Past the two lists, cargo stops at `cargo.update yes`, which `docs/dependency-preparation.md` refuses: the upstream lockfile wouldn't describe what the port builds. MacPorts runs it `--offline`, against the crates the Portfile declares, and cargo's are upstream's Cargo.lock byte for byte, but allowing it, where the archive ships a lock, is the person's call; six ports set it.
- **Results recorded before keep their reasons.** Reuse carries rust's old one, lint's line, forward; a check of rust with `--fresh`, or a `--note`, before #35084's description is written again, keeps it out. A host reading the reason itself from the log, from the last step's line, would mend older results and other providers' too; that, and the permission panic, which no `Error:` line carries, are the `why` command [directions](../directions.md) proposes.
