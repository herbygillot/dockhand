# 2026-09-25: review

Design v3 §6.11: `dockhand review <pr>` says what a reviewer would about someone's pull request, and posts only when asked.

## What changed

- **`Engine.Review`**:
  - reads the pull request from GitHub;
  - fetches its head from MacPorts' repository into `refs/dockhand/reviews/<n>`, with the new `git.FetchPullRequest`;
  - finds where it leaves a freshly fetched master;
  - applies the same commit and Portfile rules as `tidy` and `submit` to its commits and Portfiles.

  The summary names the commits and ports, and says MacPorts asks for one commit per logical change when there are more commits than ports, with how to squash.
- **Resolved findings.** Every review is recorded, posted or not, in schema 5's new `reviews` table. The next review of the same pull request lists which earlier findings no longer hold. A commit finding is matched by its code and message, since a rebase changes commit IDs.
- **Posting.** The text is Markdown. It names the head it reviewed and says `port lint` and the build are left to MacPorts CI. A finding on a Portfile line is also posted as a comment on that line, through the forge client's new `PostReview`.
  - On a terminal, the prompt is `c comment · r request changes · e edit first · n don't post`.
  - `--comment` and `--request-changes` post without asking, and `--markdown` prints the text only.
  - Without a terminal and with no flag, nothing is posted.
- **Requesting changes** is offered only with write, triage, maintain, or admin access, read with the forge client's new `Permission`. Otherwise dockhand says why, and the engine refuses it too.

## Pushback

The roadmap names the flags `--comment` and `--review`. `--review` doesn't say what kind of review it posts. The flag is `--request-changes`, matching the design's own prompt.

## Tests

- **Store:** reviews round-trip, newest first, and an unknown way of posting is refused.
- **Forge client:** the permission's role name, and a review requesting changes with an inline comment.
- **Engine**, on a contribution with a bad subject, a follow-up commit, and a revision left at 1:
  - the three findings and the inline comment;
  - requesting changes refused for no access, then allowed and posted with triage access;
  - after the contributor squashes and fixes the revision, a second review finds nothing and lists all three as resolved.
- **Command:**
  - a bad number is refused;
  - the preview posts nothing without a terminal;
  - `--markdown`;
  - on a terminal with read access, `r` is refused and `c` posts;
  - `--request-changes` is refused.

**Not yet:**
- `review --check`, which also builds the pull request.
- Lint, which needs MacPorts.
- The design's "by @author" line, since the forge's pull request record doesn't carry the author.
