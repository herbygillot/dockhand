# 2026-10-07: bump and serve stop on the same conditions (batch 110)

The architecture review's M3, asked for before rc7: nobody looks before bump or serve submits, so each should stop where the other does. A test only; no behaviour changes.

## What changed

- **`TestBumpAndServeStopOnTheSameConditions`** (internal/command/bumpserve_test.go) runs each case through bump in one world and `serve --submit-passing` in another, from the same update, and asserts both open a pull request or both stop. Its preparer (`concerned`) is the command tests' `bumper` with what an update can find that a check can't:
  - nothing to look at: both open one;
  - upstream changed its license: both hold;
  - a new archive that pairs with no old one, so it couldn't be compared: both hold;
  - a Go minimum go.mod's requirement leaves low: both hold;
  - a patch the update couldn't check: both open one, since it's coverage, which the check's build settles;
  - other pull requests that couldn't be looked for: bump stops before its edit, serve holds after its check;
  - a change outside any port: serve stops before its check, since tidy's plan isn't unambiguous, and bump finds the commit has no subject to take.

## What it found

No case where bump submits what serve holds. One difference remains in the code, which the test couldn't reach: bump's tidy takes `--yes`, which applies a plan as shown (`decideTidy`, internal/command/review.go), where serve stops on any plan that isn't `Unambiguous` (internal/engine/outdated.go's prepareOne). A fresh bump branch has only dockhand's own edits, so its port groups come from them with no notes, and a change outside any port blocks on its subject. A plan with notes and no blocker would need a person's edit in the new worktree between the update and tidy. Reported to the prime-time thread for the person, not changed.
