# 2026-10-01: speed, and finding one's way in a log (batch 14)

Batch 14 of the [roadmap](../roadmap.md): three things [the hugo exercise](../reviews/2026-09-28-hugo-bump-exercise.md) and [the ov run](../reviews/2026-09-28-hugo-bump-exercise.md#ov-through-adopt-edit-retry-and-submit---passing) met.

## What changed

- **`logs --port` starts at the port's own build** (an agent's work, reviewed and merged). hugo's own phases began near line 46,400 of 47,000, after its dependencies' installs, which `logs --port` printed first.
  - The Tart guest program records where each step of a target's build begins in its log, the line its output starts on: `deactivate` (where ports are active), `clean`, `lint`, `dependencies` (where there are any), `fetch`, `checksum`, `install`, and `test` (where tests run). It counts the log's own lines before each step it runs, reading each log once from where its last count ended; nothing reads MacPorts' progress lines, which aren't an interface it documents. A step whose place can't be read is left out, and the build goes on.
  - A result keeps them (`model.TargetResult.Steps`, schema 26, `results.steps`), validated as known steps at lines that never go back, and only beside a log. `OwnBuild` is the step after `dependencies`.
  - `logs --port` lists the steps with their lines, then prints from the port's own build, saying how many lines `--all` adds. `--all` prints the log alone, as before, and a result with no steps, recorded before this or by another provider, prints whole. The JSON keeps `text` whole and adds `steps` and `own_build`.
  - `VerifierProtocol` stays 2: the guest builds as it did, and only says more.
  - A failure's cause, read from its log (`withCause`), is now read from where the step that failed began, the last one recorded: an error a dependency's build printed and went on from is no longer taken for the port's (`buildlog.FirstFrom`).
- **`outdated` for named ports materializes only them.** `outdated hugo` took 7.4 seconds, 6 of them in the kernel. Timed step by step, the survey's whole-tree materialization took 4.8 seconds and its removal at the end most of the rest; fetching master took 0.5, staging master's index 0.07 from the cache, the port's probe 0.2, and hugo's tags 1.1.
  - `survey.OpenAt` no longer materializes the whole tree. After the index places the names, it brings each selected port's directory and `_resources`, in one materialization (`workspace.EnsurePorts`, which `EnsurePort` now calls). A name the index couldn't place widens the tree as it's resolved, which walks the categories, and an index built rather than found widens it first, as each did already.
  - It no longer checks that the materialization looks like a ports tree, which a sparse one doesn't until a port is in it: the repository was checked when the engine opened it, as the index's stager already reasons for a workspace.
  - No Portfile in the tree reads another port's directory, or sources Tcl from outside its own, while it's evaluated, and a branch's worktree is sparse the same way, so this is the projection dockhand evaluates in every day.
  - On the real checkout, `outdated hugo` went from 8.4 seconds to 2.0, and fifteen selectors (subports, `category/port` and `category/port/Portfile` paths, and a name with no port) from 10.0 to 3.2, with the same output.
- **A path that names no port says so.** `outdated textproc/jq/Portfile` (jq is in `sysutils`) said "lstat /private/var/folders/…/textproc/jq: no such file or directory", the snapshot's temporary directory. `macports.Tree.Select` now says "no port at textproc/jq".
- **A check's index derives from its base's.** The engine had one index stager, name lookup's, which builds a tree's index from the nearest cached generation and ignores the tree's base. The stager's own comment said verification keeps the base, but the wiring gave Tart that same stager. So a check's index came from whatever generation of that release was nearest. A snapshot, which has no commit, couldn't be bracketed against the mirror's index, and a release with no recent generation fell to a full pass of several minutes, as check-23's macOS 15 index did. The branch's tree also moved the cache's `latest` pointer, which the cache's comment says a candidate never does.
  - `Engine.PortIndex`, which Tart stages with, is now a stager of its own that keeps the base (`checkIndex`). A check's index then derives from its base's for the release, by the ports the branch changes. The base's generation is found in the cache or, where there is none, from the mirror's index bracketed by the base's commit, which a snapshot has too. A candidate no longer moves `latest`.
  - The candidate is indexed strictly, every port it changes, as the cache was designed to: a branch port that doesn't parse fails staging, rather than going unindexed. Two cases aren't strict:
    - A tree that is its own base, as a baseline check's is, is upstream's, and a port of master's that doesn't parse is no contribution's.
    - A candidate whose change reaches `_resources` needs a full pass, which a strict request fails on any port that doesn't parse, the base's included. These cases were never strict in production, since no check kept its base before, so each stays as it was. A check still requires its targets of the index (`requireIndexedTarget`).
  - Seeds still come only from the same release's generations: an index is a function of the platform it was told, so another release's would be wrong.
  - `Config.Mirror`'s comment said nil keeps indexing offline, "which assess and outdated rely on", though the engine always sets it. It now says what the mirror is for and that the engine sets it.
- **Each release of a check gets its own index.** Tart builds two environments at once, and both stage the same revision through one shared workspace. The stager remembered what it staged by root and tree, not platform, so the second release was handed the first's index. It also installed its own into the root while the first packed it, so the archive could hold either release's index, or fail on a file being installed.
  - `portindex.Stage` now returns the generation it installed. The stager keys what it staged by platform too, and opens that generation, which is immutable, rather than the root's copy.
  - The archive packs the index from that generation (`Index.Files`) and leaves out the root's index files (`portindex.IsIndexFile`), including a temporary one being installed. So each release's guest gets its own index, whoever shares the root.
  - The guest builds from the Portfiles themselves and reads the index mostly for names, which no release changes, so a wrong index there would rarely have shown.

## After the dogfood run

The dogfood session ran 2030b626 on real work. `outdated hugo` took 1.65 seconds warm; the first run after master moved took 22, building master's index once, which every later command reuses. `check --branch pr-34620 --on tart:15,26 --fresh` (check-64) staged without errors, each release with its own index, macOS 26's derived from its base's by 1 changed path in 5 seconds. macOS 15 had no generation, and #34620's base, fd44713 of 2026-09-11, predates the mirror's index, so it indexed in full, in 3m42s. Its `-v` output needed tidying:

- **Lines didn't say which release they were about.** Two releases stage at once, and only the run's kept lines named theirs. `progress.Within` now has every report made under it say what it's about first, and the runner gives each environment's work its name, so the verbose lines carry it too.
- **The kept lines showed twice at `-v`,** bare from the command's reporter and named from the run's record, which the command prints. `progress.Keep` is `Observe` for an observer that keeps a run's info reports: a command driving it Quiet lowers them to debug, not verbose, since it shows them through the run.
- **Three IDs named the source,** the branch's tree, the base's tree, and the base's commit, with nothing saying which was which. The index's lines now name the tree they index: "base fd44713349eb's tree ed48c589f778", "the revision's tree 6c8a4f210dee", or a commit's tree, and one changed path is no longer "1 changed paths".
- **Reusing the base's index said nothing at `-v`:** "Using the cached PortIndex for …" was debug, and is now verbose.

A second run, check-65 on the same branch and releases, confirmed these, each release reusing check-64's index, and found two more:

- **The index's lines began at the margin,** among the provider's lines, which the check prints indented as the run's. A report made within something now carries what it's about (`progress.Update.About`), and the terminal indents it under the command's own.
- **`logs check-65 --port libuv-devel` opened macOS 26's log,** where it passed, the last build of it, while its tests had failed on macOS 15, whose run ID had to be found by hand. `logs --port` now opens the build that failed, or whose tests did, before one that passed, the latest of those, and names the others with the `logs <run> --port` that opens each: beside the steps, or on standard error where the log is printed alone, so `--all` stays the plain log. `--json` gives the build's `execution` and the others under `elsewhere`.

The dogfood session also asked whether the mirror's index could seed a base older than it, by diffing backwards. It could, soundly: the paths changed from the base to a commit after the mirror's time cover what changed between. But any change to `_resources` in that span forces a full pass anyway, and in this checkout a base a week old has one, three weeks old (fd44713) nine. It would spare the full pass only for a base a few days old checked on a release with no generation, once per base and release, so it's on the roadmap with that measure rather than taken here.

## Decided along the way

- **The whole tree only when something needs it.** A filter (`--mine`) selects through the index and brings the ports it selected, in one materialization, as named ports are brought.
- **GitHub Actions' logs have no steps.** Its log is the runner's whole job log, shared by every port on that runner, and its `::group::` headings are written by MacPorts' own workflow, not dockhand's; the provider already reads them for its verdicts, an existing exception to depending on documented interfaces only. Reading them for positions would widen it, and the steps would belong on each builder's result rather than the target's. Left for the person to decide.
- **A migration for the steps.** Results keep their fields in columns, so the steps take one, as `builders` did; a build older than this can't open the database afterward, which dockhand says when it migrates, keeping a copy.
- **Strict where it's cheap and meant.** A full strict pass fails on any port of master's that doesn't parse, which no branch can answer for. Applying it there would have turned a check of a PortGroup change into a staging failure the day checks began keeping their base.
