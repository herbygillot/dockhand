# 2026-09-30: the GitHub provider (batch 12)

Batch 12 of the [roadmap](../roadmap.md): two findings of [the sshuttle run](../reviews/2026-09-28-hugo-bump-exercise.md#sshuttle-through-paths-not-yet-taken) about the github provider.

## What changed

- **A check's `dockhand-check/` branch is removed from your fork once the check is done with its run** (finding 7). `dockhand-check/e15ced625514` stayed on herbygillot/macports-ports after check-12 finished, and `clean` removed it, with check-13's, only once #35011 merged: they lingered for the life of the pull request.
  - "Done" is known in the provider, which pushed the branch, and not in the engine's driver, which knows an execution ended but not what it left on a fork. `ghactions.Provider.Execute` removes the branch once it has read the run and recorded its results, whether the ports passed or failed, or once the check's last attempt (`model.MaxAttempts`) has ended: no attempt runs the run again after that. A run cancelled or timed out on GitHub is read the same way where it built a port; where it built none, a later attempt runs it again, as before.
  - It removes it as `clean` does, through `git.Repository.DeleteRemoteBranch`, a push deleting the branch with a lease on the commit pushed, to the remote that pushed it. A branch that has moved is left, as `clean` leaves one.
  - A branch it can't remove is said once ("couldn't remove dockhand-check/… from ada/macports-ports, which dockhand clean removes once the branch is merged: …") and never fails the check. `clean`'s removal is unchanged, and is the backstop.
  - `check --plan`'s Pushes line says it: "…, where MacPorts' workflow builds it, and removes the branch once the run is read". A write to your fork isn't hidden behind "only checking" (Design v3 §9), and a deletion is one.
- **A push waits for the run it starts.** GitHub lists a branch's runs after the branch is gone, so a later check of a commit whose branch was removed, `dockhand retry` among them, would have found the earlier check's run, completed, and read it again, while the push started another. The provider now notes the newest run of the branch and commit before it pushes, and waits for one newer. Where the branch is still there and nothing is pushed, it takes the newest run, as before.
- **Tested on gives the GitHub runners' macOS releases** (finding 8). #35011's GitHub line said only "Developer tools not recorded · github: MacPorts' CI workflow in the author's fork". It would now read "macOS 14, 15, 26" above that line.
  - The provider already listed the run's jobs through GitHub's "List jobs for a workflow run attempt" (`ListWorkflowJobsAttempt`, vendored go-github v91), whose job objects are those of "List jobs for a workflow run", with `labels` and `runner_name`. `RunnerJob` now carries both, and `RunnerJob.Release` reads the release the labels name: `macos-15` is 15, as are `macos-15-xlarge` and `macos-15-intel`. `macos-latest`, other labels naming no release, labels naming two, and a job no runner took say nothing.
  - It's recorded as the Tart provider records what its guest reported, through `buildenv.Build.Observe` into the execution's `model.Observed`, which now has `Builders`: one `model.BuilderObserved` for each runner, its name and its release, as a result has `Builders` for each runner's part. The provider records them in one order, by name, once the jobs are listed and before the results; nothing where no runner's labels name a release.
  - `Observed` holds a slice now, so it no longer compares with `==`: `Observed.Equal` and `IsZero` stand in where evidence groups the reports and the store leaves an empty one out. It's kept as JSON, so the store's schema is unchanged.
  - `testedOn` gives the releases the builders reported, each once, in their order: "macOS 14, 15". The tools line stays "Developer tools not recorded".

## Decided along the way

- **The branch stays while the check may need its run.** An attempt that ends as the environment's trouble, such as a run that failed without naming a port, leaves it: the next attempt reruns that run (`Rerun`), which runs at the run's branch, and GitHub doesn't document what a rerun does once it's gone. So does a driver that stops with the check left for the next (`Resume`, a `serve` stopping): the next finds the branch, pushes nothing, and waits for the same run. Nothing is removed while the context is done.
- **Logs and results don't need the branch.** Each runner's log is fetched by its job's ID (`JobLog`, from the jobs of the run's ID and attempt) as the run is read, and kept in the check's log directory; results are recorded as it's read, and `dockhand logs` reads both from here. A run is found by its URL, recorded as the execution's reference. Nothing reads the branch after the run is read.
- **A retry builds again.** Before, a later check of the same commit, a retry included, found the branch and the completed run, and read that run again: its result was the earlier check's, unless the run had stopped short, which reran it. Now the branch is gone once read, a retry pushes, and the workflow runs again, as `retry`'s help says ("the whole plan is built again"), and as GitHub's results, which carry no environment identity, are never reused.
- **A canceled check leaves its branch.** `dockhand cancel` and `check --replace` cancel the run, which isn't read; a retry then finds the branch and reruns the cancelled run, as before. `clean` removes it once the branch is merged.
- **Each runner's release, not one for the environment.** The GitHub environment is one environment of the plan, with no platform, and its run has a runner for each release of MacPorts' matrix, so one `MacOS` can't say it. The runners are reported as `BuilderObserved`, named as their parts of results are, rather than as a list of releases, so a later report can say which runner was which.
- **Only the release, and only from the labels.** The labels are what a job's `runs-on` asked for; a job runs only on a runner that has them all, so a job a runner took ran on that release. The architecture isn't recorded: GitHub's labels imply it only by its documentation's table (`-intel`, `-xlarge`), which moves. Xcode, the macOS build, and the runner image's version are only in the log's text, which isn't a documented interface (`ReadLog` reads only the workflow's own markers), so the tools line keeps "Developer tools not recorded", the words already used where nothing was recorded, rather than "Xcode not recorded", which would state what the environment has.
- **No identity from the labels.** `macos-15` names a release whose image GitHub replaces every week or so, so it isn't an identity by origin, and GitHub's results stay unreused (the roadmap's item 6).

## Left open

- **A canceled check's branch stays until `clean`,** and only `clean` of a merged branch removes it. Removing it as the run is cancelled would make a retry push again rather than rerun the cancelled run; whether that's wanted is the person's.
- **The runners' architecture, macOS build, and Xcode aren't recorded.** None is in the jobs API; the log's text has them.
- **A branch dockhand couldn't remove for a check of a branch that never merges** stays: `clean --closed` and `--archived` take only worktrees, as before.
