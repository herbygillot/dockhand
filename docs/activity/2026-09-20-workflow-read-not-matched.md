# The run is the signal, not the workflow's shape

GitHub verification validated `main.yml` by pattern-matching its shape: exactly one job in the file, keyed `build`, with `name` and `runs-on` both the literal `${{ matrix.os }}`, no `if`, no matrix include or exclude, and a push trigger whose `branches-ignore` was exactly `[master]` with no other filter. Any departure failed `source()`, and a `source()` failure closes the request permanently, so an upstream edit would have turned into a durable rejection for every contributor rather than something to retry.

Those rules were upstream's decisions to make. The MacPorts matrix has changed about twice a year, most recently dropping macOS 13 and adding macOS 26, and the shape rules would refuse a second job, a renamed `build`, a condition on it, an `include:`-style matrix, or the `paths-ignore` already carried on the pull-request trigger. None of that affects whether the workflow builds the port.

The shape match was also the weaker guarantee. It never read a step, so a workflow could keep the expected skeleton and build nothing, and dockhand would record the green run as evidence that the port built. The real guarantee was already in place elsewhere and needed no parsing: a contribution is one commit whose every path lies under one port directory, above a base that is present in upstream master, so the workflow at the candidate commit is byte-for-byte the one upstream published, whatever shape it has.

So the file is now read for what it says about itself rather than matched against an expectation. One thing is still refused before a push: a trigger with no `push` key, or whose branch filters exclude the branch about to be pushed, because that run would never exist and waiting for it would be waiting for nothing. Branch patterns are applied the way GitHub applies them, with `*` spanning one path segment and `**` any number. Path filters are not read; a filter excluding a port directory is not a thing this workflow would say, and a push that starts no run is already diagnosed.

The verdict now comes from the run. It passes when the run carried jobs, every one concluded successfully, no name repeated, and every job that reported its `runs-on` labels ran on macOS; a job that reports no labels says nothing either way rather than blocking. The workflow's own prediction is kept where it is sound: when one job declares a runner matrix with no include or exclude and takes its name from the matrix value, which is what makes the predicted names match GitHub's, the run is still held to that list. Otherwise no prediction is recorded and the run speaks for itself. A blocked verdict now names the reason instead of saying only that the matrix was incomplete.

Tests: reading a workflow accepts an added runner, a second job, a renamed job, a condition, and a path filter, refuses the four trigger shapes that would start no run, and declines to predict when the job names would not match. Through the provider, a workflow dockhand never predicted passes on the three jobs it actually produced, a job on a Linux runner blocks it, a run with no jobs blocks it, and a predicted pair that arrives as one job still blocks.

One fixture is not synthetic: `testdata/macports-main.yml` is macports-ports' own workflow as of this date, all 289 lines, and the test asserts it is accepted, that it predicts `macos-14`, `macos-15`, and `macos-26`, and that `master` is refused as the one branch its push trigger ignores. Those predictions were checked against the fork's Actions API the same day, where a real run reported exactly those three job names with each name as its own `runs-on` label, which is what makes both the prediction and the macOS check land on real data rather than on the test double.
