# 2026-09-25: adopt --pr

Design v3 §6.11: "Adopting someone else's PR lets you inspect it and work on it locally. It doesn't assume permission to push to their branch. `submit` names that destination and checks your access before pushing anything."

## What changed

- **`adopt --pr <number>`**:
  - reads the pull request, which must be open;
  - fetches its head from MacPorts' repository;
  - makes a `pr-<number>` branch in a sparse worktree holding `_resources` and the ports it changes;
  - records the pull request with its current head as the last push, so a later push by its author is noticed as someone else's;
  - reports the title, author, commits, ports, and whether maintainers can edit it.

  A pull request already tracked is reported, not adopted twice.
- **Submitting to someone's pull request.** For a branch whose pull request someone else opened, `submit`:
  - pushes to their branch through a remote that already pushes there, else their repository's GitHub address in the form your remotes use;
  - blocks, and says why, unless their pull request lets maintainers edit it and you have write, maintain, or admin access to macports/macports-ports. Each block suggests `dockhand review` instead;
  - never rewrites their title or description (`SubmitPlan.Theirs`).
- **The forge client** now reports a pull request's author and whether maintainers can modify it.

## Tests

- **Engine:** a contributor's two-commit pull request with a stand-in for their repository:
  - adopt makes `pr-34905` with jq checked out and their head as the last push, and a second adopt finds it tracked;
  - after a local commit, submit is blocked while edits are disallowed, and again with read access;
  - with write access, it pushes to their `patch-1` without writing their pull request or opening one.
- **Command:** `adopt --pr` output, the refusal of a branch together with `--pr`, and a second adopt.

**Not yet:** following their pushes into the local branch, which is `git pull` for now.
