# 2026-09-30: what batch 21 left (batch 22)

Batch 22 of the [roadmap](../roadmap.md): what [batch 20's open ends](2026-09-30-batch-20-open-ends.md) and [batch 21](2026-09-30-batch-21.md) left.

## What changed

- **A blocked result stands only with what blocked it.** An earlier check's results fill in for what a later check of the same files didn't build (`fill`), each where it counts (`Counts`). After a Git-fetched port's tag moved, libharbor's earlier failure no longer stood, while harbor-cli still read "blocked" by it. The same happened without Git: a `check --only libharbor` that passed left the earlier check's harbor-cli reading as blocked by a failure the evidence no longer held.
  - A blocked result records nothing of what blocked it but, from Tart's guest, a detail in words. What blocked it is the rule a build is blocked by (`buildenv.Build.Blocked`): its own check's results there of what the plan says it needs that didn't pass, a blocked one among them. `Evidence.blockers` reads that from the check's own evidence.
  - `fill` now decides first which of an earlier check's results count, then takes a blocked one only where every result that blocked it is taken too, in turn (`standing`): a block by a block stands only while the first one's failure does. The evidence's cell for the blocker holds either that result, taken in the same fill, or another, so this is the whole rule.
  - What it no longer takes asks for a check, as a result that doesn't count does.
  - A blocked result whose check names nothing that blocked it, as a provider could record a block of its own accord, stands as it did.
  - The newest check's own blocked results needn't be judged: the driver records a block in the attempt that recorded what blocked it (`blockRemaining`), so a remade environment drops them together.
- **status says `release-moved`.** Only submit's plan said that an update's release named another commit when the update chose it than when the check planned it. It needs only the branch's edits and the check's plan, both in the store, so `BranchStatus` now carries it (`Moved`, from `preparedSources`), where the check is of the files as they are now.
  - A passed branch's attention row says it before "waiting for you to submit": "passed; held for a look: …" for a branch serve prepared, which the concern holds, and "passed; …" for a person's, whose submission shows it. Its next step is `dockhand submit --branch`, as a held branch's is.
  - The branch's own view marks it with `!` below its release line, as submit's preview marks it under Upstream.
  - `--json` lists it in each branch's `moved`: port, rule, subject (the commit the check planned), and detail.
- **status doesn't say `source-moved`.** Whether a tag names another commit now than the check planned takes the network, which status never reads, and nothing records it to read back:
  - submit's plan isn't kept;
  - serve says a hold on its own terminal, once, and keeps it in memory (`passingSubmitter.held`);
  - an assessment of a Git-fetched port reads the commit the tag names as it's made, and keeps it only as its coverage's path, in words, not as a field. It's made once for its files, at the end of the first check of them that collects it, so it can predate a later check's plan as well as follow it, and said as "moved" it would mislead where it predates.

  So status leaves it out, and `submit` alone says it. The doc on `BranchStatus.Moved` and the JSON's `moved` say so.
- **`check --plan` shows the Git sources of what `--only` left out.** Batch 20's open ends gave each left-out Git-fetched target an expected commit (`planning.OmittedSources`, in `EnvironmentPlan.Git`), but the plan's text and JSON walked only each environment's order.
  - The text's Git lines follow what it builds with each left-out target, marked: "libharbor (left out): git.branch v4 names 1a2b3c4 now, which an earlier check's build of it must have fetched to stand", or, unresolved, "…; no earlier check's result of it stands". `engine.LeftOutSourceWords` says it beside `GitSourceWords`, the two sharing one form (`sourceWords`).
  - The JSON gives each build an `omitted_git` beside its `git`, for the targets the plan's `omitted` lists.
- **The maintainer line suggested is the person's own** (the flyctl run, [#35069](https://github.com/macports/macports-ports/pull/35069)). serve said `set maintainer = "{@you example.org:you}"` while the ports it bumped carried `{gmail.com:herby.gillot @herbygillot}`, and `create` wrote `nomaintainer` for want of the setting, as txt showed.
  - `macports.Maintainer` gains `Names`, whether one of its spellings names whom a spelling does, by `MaintainerIdentity`, and `String`, the entry as a maintainers line writes it, braced where it has several spellings.
  - `portindex.Index.Spellings` reads the index's maintainers fields and gives each entry naming a maintainer, as written, with how many Portfiles write it so, most first. A Portfile's subports count once, and a field that can't be read is passed over.
  - The engine composes them (`SuggestMaintainer`): the GitHub login dockhand signs in as, the forge's `AuthenticatedUser`, and the port reader's index of a commit, asked for `@login`. An entry a maintainers line can't carry (`macports.CheckMaintainers`) isn't suggested. The port reader reads the index as it reads dependents; `evaluatedPorts.index` is now the one way both open it. `MaintainerWords` says it: `set maintainer = "{example.org:ada @ada}" in ~/.dockhand/config.toml, as the ports that name @ada write it`, or, where they write several, the most written with its count, and the others, each with its own, to choose from.
  - serve's daily look without a maintainer suggests the line from master as fetched. `create`, writing `nomaintainer`, says it below what it marked, from the branch's base: "maintainers: nomaintainer, as your config names none; set maintainer = …".
  - Where the login isn't known, master can't be fetched, the index can't be read, or no port names the login, the placeholder stays. Nothing writes the configuration.

## Decided along the way

- **The rule is in `fill`, not `Counts`.** `Counts` judges one result against its plan and its environment; whether a blocked result stands turns on what the evidence holds for the targets it needs, which only the evidence knows once it has taken the earlier check's results. `Counts`' doc names the rule and where it's applied.
- **status asks about release-moved only of a check of the files as they are now.** The update's release is compared with the plan that built those files; a check of older files planned other files, and its row already asks for a check of them.
- **release-moved keeps its own field, not `Held`.** `Held` is, for a branch serve prepared, what its recorded assessments hold it for, and the JSON's `held` says so. `moved` is said for every branch, a person's included, since their submission shows it too.
- **A left-out source has a map of its own in the JSON.** `git` is documented as what each build must fetch, and a reader taking every entry as built would have been told otherwise by a flag it doesn't know. `omitted_git` keeps that meaning, and follows the plan's own word, `omitted`, for what `--only` left out.
- **The suggestion is the entry naming the login, not a whole line.** A port's line may add `openmaintainer`, which is that port's policy, not the person; the suggestion is the entry that names them, which `create` writes as the new port's whole line. Ports are counted by Portfile, so a port with many subports, each indexed with the Portfile's maintainers, weighs as one.
- **Its index is master's for serve and the branch's base for create.** Any tree's index names the person's ports alike; serve has no branch, and fetches master for its daily look anyway, and create's branch has its base already. With no maintainer set, each stages that tree's index, from the nearest generation cached, once.

## Left open

- **`submit --json` doesn't carry a person's moved sources.** Its text shows `release-moved` and `source-moved` under Upstream, and its JSON has them only in `held`, for an unattended submission.
