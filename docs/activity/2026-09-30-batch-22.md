# 2026-09-30: what batch 21 left (batch 22)

Batch 22 of the [roadmap](../roadmap.md): what [batch 20's open ends](2026-09-30-batch-20-open-ends.md) and [batch 21](2026-09-30-batch-21.md) left.

## What changed

- **A blocked result stands only with what blocked it.** An earlier check's results fill in for what a later check of the same files didn't build (`fill`), each where it counts (`Counts`). After a Git-fetched port's tag moved, libharbor's earlier failure no longer stood, while harbor-cli still read "blocked" by it. The same happened without Git: a `check --only libharbor` that passed left the earlier check's harbor-cli reading as blocked by a failure the evidence no longer held.
  - A blocked result records nothing of what blocked it but, from Tart's guest, a detail in words. What blocked it is the rule a build is blocked by (`buildenv.Build.Blocked`): its own check's results there of what the plan says it needs that didn't pass, a blocked one among them. `Evidence.blockers` reads that from the check's own evidence.
  - `fill` now decides first which of an earlier check's results count, then takes a blocked one only where every result that blocked it is taken too, in turn (`standing`): a block by a block stands only while the first one's failure does. The evidence's cell for the blocker holds either that result, taken in the same fill, or another, so this is the whole rule.
  - What it no longer takes asks for a check, as a result that doesn't count does.
  - A blocked result whose check names nothing that blocked it, as a provider could record a block of its own accord, stands as it did.
  - The newest check's own blocked results needn't be judged: the driver records a block in the attempt that recorded what blocked it (`blockRemaining`), so a remade environment drops them together.

## Decided along the way

- **The rule is in `fill`, not `Counts`.** `Counts` judges one result against its plan and its environment; whether a blocked result stands turns on what the evidence holds for the targets it needs, which only the evidence knows once it has taken the earlier check's results. `Counts`' doc names the rule and where it's applied.

## Verification

- Tests:
  - `TestAnEarlierFailureAgainstAnOldCommitDoesntStand` now requires harbor-viewer, blocked by harbor-cli's failure against the old commit, to ask for a check with it once the tag moves; before the fix it stood as blocked;
  - `TestABlockStandsOnlyWithWhatBlockedIt`: libharbor fails, blocking harbor-cli and harbor-viewer; both blocks stand while the tag names what was built, and ask for a check once it moves;
  - `TestABlockDoesntOutliveALaterPassOfItsBlocker`: the same without Git, after a narrowed check's pass of libharbor;
  - `TestABlockStandsWithWhatBlockedItInTurn` and `TestWhatBlockedAResultIsWhatItNeedsThatDidntPass`, for `standing` and `blockers` directly.
- Mutation: each mutant run against the evidence tests, and the file restored from a copy and compared byte for byte after. `fill` skipping the rule, taking every result whatever the rule says, and judging blockers against the earlier check's results rather than what the evidence holds, are each killed by the three end-to-end tests; `standing` as one pass by the chain test; only a failure blocking, or a pass blocking too, by the `blockers` test; and an unmet cell made to stand by a blocker by `TestACellFilledFromAnEarlierCheckKeepsWhatItIs`.
