# 2026-10-04: the Vx port's field findings (batch 88)

Batch 88 of the [roadmap](../roadmap.md): from the field testing session's notes on writing a new port, Vx, by hand, and on py-pyaml (macports/macports-ports#35219).

## What changed

- **A hand-written new port's Portfile is named with the commands that take it.** Git doesn't track a new port's Portfile, so a check leaves it out, and the worktree's sparse checkout keeps `git add` from taking it. Under "Left out, not tracked", check now says, for each new port's directory, `dockhand check --include <dir>/Portfile` builds it and `git sparse-checkout add <dir>` lets git add take it. The capture says which directories are a new port's (`engine.Capture.NewPorts`).
- **A check that built nothing says whose results it took.** On an unchanged tree a check passes at once, reusing an earlier check's results, and said only "Passed", which looked like nothing happened. It now says "Passed for snapshot 4, reusing check-189's results: the same inputs, so nothing was built (--fresh builds again)." `cancel` on such a check says the same after "already passed". The evidence says which checks a check reused when it built nothing itself (`evidence.Evidence.ReusedAll`).
- **A failed check shows the last lines its failed step printed**, at most 15, where no reading of its log found the cause (D10's compiler error). `port -d`'s DEBUG lines and blank lines are left out; a build's error output is in the log beside the rest. The step ends where another target's step in the same log begins. `buildlog.Last` reads the lines, and `engine.FailureLines` finds the step.
- **`create pypi:NAME` works for a project with no GitHub release.** It refused one published to PyPI and only tagged on GitHub. The registry now gives the latest version too (PyPI's `info.version`, crates.io's `max_stable_version`), and create takes the tag `v<version>` or `<version>` where GitHub has no release (`registry.Client.Find`).
- **A Python requirement is matched to the port that provides it by the package the port names**, not its name alone. py-pyaml held on "pyproject.toml requires pyyaml, and no port the Portfile depends on is named for it", though it depends on py313-yaml, whose `python.rootname` is pyyaml. Where no dependency's name matches a requirement, the assessment now asks for each Python dependency's evaluation and matches the packages it may provide: `python.rootname`, the python PortGroup's name for its PyPI project, else its name's, and the project its forge setup names, as py313-protobuf3 fetches google/protobuf, PyPI's protobuf, which py-coremltools 9.0 depends on (`macports.PortInfo.PythonProjects`). The evaluator reads `python.rootname`. A matched provider is then judged on its version as any other.
- **The quick stage leaves B2 out where a fork is set** (the M1's run at d302e744). With `ACCEPT_GH_FORK`, bump doesn't refuse, as B2's header said it would; it runs a whole Tart check, whose macOS 27 guest built rust and cargo from source for dust, hours on two cores. The quick stage now reports B2 "not run" then, unless `ACCEPT_B2_BUILD=1` asks for the build, and its header says so. That a check builds a dependency from source without saying so first is the README's known issue and a roadmap item, which waits on the person's word about reading MacPorts beyond its documented interfaces.
- **Four larger findings are under the roadmap's Later**: create for a Cargo workspace's binaries, `check --keep` with a shell into the VM, `logs --phase`, and a local lint's slow indexing said.
