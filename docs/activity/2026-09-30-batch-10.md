# 2026-09-30: branches, done, never dockhand's, or rewritten more than they need (batch 10)

Batch 10 of the [roadmap](../roadmap.md): what `status`, `clean`, and `adopt` don't yet see, and what `tidy` rewrites that it could keep.

## What changed

- **`tidy` keeps the commits it wouldn't change.** Adding py-flatbuffers to #35044, `tidy --apply` wrote the pull request's first two commits again, with the same trees and messages and another committer time. So the next submit replaced the pull request's history rather than adding a commit to it (adding py-flatbuffers, finding 3).
  - A commit the branch has already, at the same place, from the same parent, with the same tree, author, and message, now stays as it is. Once one is written anew, those after it are too, their parents being new.
  - The message rule is `commitmsg.Unchanged`: the same, or the same but for the attribution line where both carry one, since Generated-By names the build that wrote each, and the one written stays true. One naming a build of uncommitted source isn't kept, since tidying again with a pushed build is what `submit` asks for to replace it. A commit without the line doesn't stand for one tidy would attribute.
  - `tidy` says "Kept 1 commit as it was, and created 1". Where every commit the pull request has is kept, it says the pull request gains the new ones when you submit, rather than that submit replaces its history. `--json`'s applied result has `kept`.
- **`status` says a branch's work is on master already.** duckdb-cxx14's one uncommitted edit, C++14 for macOS 12 and older, had landed on master as e5467392f89, and status still listed it under what needs you, "snapshot 1 passed; commit it for review" (cleaning up duckdb-cxx14, finding 1).
  - dockhand now keeps the master it last fetched, `refs/dockhand/master`, updated wherever it fetches master (`fetchMaster`), from the value it had. Status never fetches, so it compares a branch with that.
  - `BranchStatus.OnMaster` is that master where, for every path the branch's files change against its base, master's file is the branch's: committed or not, the branch's work is there. A branch that changes nothing, or that master hasn't caught up with, isn't on master.
  - For a branch with no pull request, the row is "its changes are on master already, as of e5467392", with `dockhand archive` as the next step. One with a pull request is its pull request's to say, which `status --refresh` reads. `--json` has `on_master`.
- **An adopted branch is checked out somewhere.** `adopt dockhand/bump/zola-…` said "It is not checked out anywhere; git switch … checks it out", which switches the person's own checkout. A worktree they then added with `git worktree add` wasn't found: `rebase` there said "not checked out anywhere", and adopting again inside it said "already tracked" (the flatbuffers, nuspell, zola, and alertmanager run's finding 3).
  - `placeWorktree` gives a branch with no worktree recorded one. Where it's checked out now, that worktree is recorded, as the person's. Otherwise dockhand makes one as `start` does, sparse, with `_resources` and the ports the branch changes, recorded as dockhand's.
  - `adopt` places a branch it finds checked out nowhere, and says where. Adopting a tracked branch again records a worktree the person added since.
  - `path`, and every command that needs a branch's worktree (`worktree`), places one first. `status` only reads, through `openWorktree`, so it never makes one.
  - Where dockhand's own directory for it already exists, adopting says why it couldn't check it out, and adopts it all the same.
