# 2026-09-30: branches, done, never dockhand's, or rewritten more than they need (batch 10)

Batch 10 of the [roadmap](../roadmap.md): what `status`, `clean`, and `adopt` don't yet see, and what `tidy` rewrites that it could keep.

## What changed

- **`tidy` keeps the commits it wouldn't change.** Adding py-flatbuffers to #35044, `tidy --apply` wrote the pull request's first two commits again, with the same trees and messages and another committer time. So the next submit replaced the pull request's history rather than adding a commit to it (adding py-flatbuffers, finding 3).
  - A commit the branch has already, at the same place, from the same parent, with the same tree, author, and message, now stays as it is. Once one is written anew, those after it are too, their parents being new.
  - The message rule is `commitmsg.Unchanged`: the same, or the same but for the attribution line where both carry one, since Generated-By names the build that wrote each, and the one written stays true. One naming a build of uncommitted source isn't kept, since tidying again with a pushed build is what `submit` asks for to replace it. A commit without the line doesn't stand for one tidy would attribute.
  - `tidy` says "Kept 1 commit as it was, and created 1". Where every commit the pull request has is kept, it says the pull request gains the new ones when you submit, rather than that submit replaces its history. `--json`'s applied result has `kept`.
- **`status` says a branch's work is on master already.** duckdb-cxx14's one uncommitted edit, C++14 for macOS 12 and older, had landed on master as e5467392f89, and status still listed it under what needs you, "snapshot 1 passed; commit it for review" (cleaning up duckdb-cxx14, finding 1).
  - dockhand now keeps the master it last fetched, `refs/dockhand/master`, updated wherever it fetches master (`fetchMaster`), from the value it had. Status never fetches, so it compares a branch with that.
  - `BranchStatus.OnMaster` is that master where, for every path the branch's files change against its base, master's file is the branch's: committed or not, the branch's work is there. A branch that changes nothing, or that master hasn't caught up with, isn't on master.
  - For a branch with no pull request, the row is "its changes are on master already, as of e5467392", with `dockhand archive` as the next step. One with a pull request is its pull request's to say, which `status --refresh` reads. `--json` has `on_master`.
- **An adopted branch is checked out somewhere.** `adopt dockhand/bump/zola-…` said "It is not checked out anywhere; git switch … checks it out", which switches the person's own checkout. A worktree they then added with `git worktree add` wasn't found: `rebase` there said "not checked out anywhere", and adopting again inside it said "already tracked" (the flatbuffers, nuspell, zola, and alertmanager run's finding 3).
  - `placeWorktree` gives a branch with no worktree recorded one. Where it's checked out now, that worktree is recorded, as the person's. Otherwise dockhand makes one as `start` does, sparse, with `_resources` and the ports the branch changes, recorded as dockhand's.
  - `adopt` places a branch it finds checked out nowhere, and says where. Adopting a tracked branch again records a worktree the person added since.
  - `path`, and every command that needs a branch's worktree (`worktree`), places one first. `status` only reads, through `openWorktree`, so it never makes one.
  - Where dockhand's own directory for it already exists, adopting says why it couldn't check it out, and adopts it all the same.
- **An older build's Generated-By is said.** A pre-v3 branch's commit carried `Generated-By: Dockhand v0.0.0-20260921.2.0.20260923041537-ec1997b8bc53`; a rebase kept it, a re-tidy would replace it, and neither said so (the flatbuffers, nuspell, zola, and alertmanager run's finding 4).
  - `commitmsg.OtherBuilds` names the builds messages' attribution lines name other than this one: a tag, or a legacy form's whole line.
  - `tidy`'s plan says "the branch's commits name an older dockhand in Generated-By, …: a commit tidy leaves as it is keeps it, and one it writes names this build" (`TidyPlan.OlderBuilds`), which keeping unchanged commits makes true either way.
  - `rebase` says its replayed commits keep it (`Rebased.OlderBuilds`), read from the replayed history, which also counts them now.
- **`clean --archived` cleans merged branches too** (the dogfood run with be3f3e06). Help says `--merged` defaults to true, but naming `--closed` or `--archived` dropped merged branches, unsaid: three merged branches stayed until a plain `clean`. The flags now add to what's cleaned, `--merged=false` leaving merged branches out (`cleanStates`), and the help says so.
- **A worktree is narrowed back once the branch's work is committed.** `edit jq` left sysutils/jq checked out in the ov branch's worktree, which nothing narrowed again (the ov run's finding 6).
  - After `tidy` commits, a worktree dockhand made has its cone set back to `_resources` and the ports the branch changes (`narrow`, through `git.Repository.NarrowSparse`), and `tidy` names what it left out.
  - Not before: an edit may be under way while other commands run, and taking its directory out from under an editor would lose the person's place.
  - A worktree the person made stays as wide as they made it. git leaves untracked files in a directory left out.
- **An archived branch with nothing master lacks goes with its worktree.** `clean --archived` kept `dockhand/duckdb-cxx14` ("dockhand path duckdb-cxx14 checks it out again"), though it had no commit beyond master (cleaning up duckdb-cxx14, finding 2).
  - Where an unmerged branch's worktree goes and its Git branch has no commit beyond the master dockhand last fetched, the Git branch goes too, "it has nothing master lacks" (`CleanStep.Why`), unless it's checked out elsewhere. One with work of its own stays, as before.
  - `BranchStatus.Cleaned` now covers any branch that isn't open whose Git branch is gone: clean removed it, or nothing of it needs anyone. An open one's is still lost, as to a rename.
- **Branches from before v3 are sorted, and those master has removed when asked.** The hugo exercise's checkout held 22 local `dockhand/bump/<port>-<id>` branches from earlier dockhand, which nothing reported or cleaned (the cleanup, finding 3).
  - `engine.PlanLegacy` sorts those no record tracks by what master, fetched now, has of each:
    - **on master**, where it has every commit, by patch-id (`git.Repository.Cherry`, `git cherry`), as MacPorts' rebase merges leave one;
    - **superseded**, where master declares one of its ports at another version than the branch started from, read as `portfile.DeclaredVersion` reads one;
    - **unfinished**, the rest.
  - `clean --legacy` removes those on master, each only while it holds the commit planned, with your fork's branch of the same name where it holds the same commit, and never one checked out anywhere (`RemoveLegacy`). It names a superseded one for a look, with `git branch -D`, and leaves the rest for `adopt`.
  - A plain `clean` says how many there are.

## After the dogfood preview

The dogfood session previewed `clean --legacy` on its checkout with fb2d195f, without `--yes`: 21 branches, 14 to remove, one to look at, and six left for adopt, each of which it confirmed master hadn't caught up with. It found:

- **The wording of a change master has** read oddly: "master has its 1 commit, by their changes". `git.Repository.Cherry` now lists each commit with its subject, and the line names it: `master has the same change as its "jq: update to 1.8.1"`, or "the same changes as its 3 commits, by patch".
- **An unfinished branch didn't say what it does.** It now says what it takes each port to: "takes semgrep from 0.14.0 to 1.178.0, which master still has at 0.14.0", so a person can tell which are worth adopting.
- **Branches only on the fork weren't read.** Two were on herbygillot/macports-ports with no local branch. `PlanLegacy` now lists your fork's `dockhand/bump/*` branches (`git.Repository.RemoteBranches`, one `ls-remote`), fetches those this checkout lacks to read them, and sorts them the same way. One master has goes from the fork, with a lease on its commit.
- **The adopted and archived pre-v3 zola branch** was skipped by `--legacy`, being tracked, and `clean --archived` kept its Git branch without a word, though master had zola 0.23.6 by another commit. An unmerged branch with work of its own now says, for a look, where master has its port at another version (`CleanBranch.Superseded`, the same reading `--legacy` uses).

A second preview, with bf711891, confirmed the first three: chezmoi's line names its change, semgrep's says what it takes, and rust-analyzer and xplr show as on your fork only. It found two more:

- **The zola line still didn't show.** `planCleanWorktree` returned before reading the Git branch whenever there was no worktree of dockhand's to remove, and zola, adopted before adopt placed worktrees, had none. A branch with no worktree is now read all the same: one master supersedes is said for a look, and one with nothing master lacks goes, unless it's checked out somewhere. `PlanClean` keeps a plan that only says a look, and `clean --json` gives it as `superseded`, with each step's `why`.
- **`status --all` didn't say a branch was archived.** Its row, "1 commit — —", read as an open branch's. The branch column now says "(archived)", as `clean` does.

## Decided along the way

- **"Already on master" reads the master dockhand last fetched.** Status never fetches, and dockhand had kept no master of its own; a ref updated wherever it fetches master is the one fact every command that reads shares, and a branch master hasn't caught up with is simply not on master yet.
- **A worktree is narrowed only once the work is committed.** Narrowing while an edit may be under way could take a directory out from under an editor; after `tidy`, nothing of the branch's is in what's left out, by definition.
- **A legacy branch is removed only where master has every commit, by its change.** A superseded one is very likely spent, but a version in master that moved on doesn't prove the branch's own work is there, so a person looks; an unfinished one is never removed.
- **`--legacy`, `--closed`, and `--archived` add to what `clean` takes,** as the help's default for `--merged` said all along.
