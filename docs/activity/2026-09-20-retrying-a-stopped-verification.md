# Retrying a verification that never judged the change

A verification can stop for reasons that say nothing about the contribution: the guest agent never comes up, a runner dies, a dependency fails to build, GitHub times a run out. Dockhand's advice in that situation was to fix and amend, or to verify again once fixed, both of which point at changing a commit that is not broken.

The capability to retry was already complete and only the advice was missing, which is worth recording because the first reading of this was that a retry would have to be built. Submitting the same preparation again is the retry. Acceptance finds the contribution's newest job of that action, refuses if the intent differs or the contribution has advanced or has pending work, and otherwise takes the new spec while adopting the old job's prepared branch and result revision. A job that arrives with a result revision starts active in the verification phase, so the branch is not built twice, and because the spec is the new one, the destination and publication the first job was going to make come with it. `dockhand bump jq` after an errored verification therefore verifies the branch it already prepared and publishes on success, which is what the original command promised.

That makes the command to offer the port's own action rather than `verify`. Verifying again also re-runs the build, but it produces a verification-only job that stops at a verified contribution, so a bump retried that way loses its pull request and needs a separate publish. The guidance now names the action the job was: bump, bump-revision, or refresh-checksums, with the requested version when one was named, and falls back to verify for a standalone verification or a correction, where re-running the action means recapturing a checkout rather than retrying a build.

What the failure was decides whether this advice appears at all. An infrastructure or dockhand failure, a dependency that failed while the target did not, an errored verdict, or a blocked one all say the same source is worth running again and name the command. A failure in the target port still says to fix and amend, because that is the change's own business.

A test now holds the whole path: a combined revision bump whose verification errors stops as needs-attention with its branch intact and nothing published, the same bump submitted again becomes a second job that starts in the verification phase with the first one's revision, branch, and publication destination, and when the retry passes it publishes once.
