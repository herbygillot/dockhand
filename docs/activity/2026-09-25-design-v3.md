# 2026-09-25: Design v3

After reading both proposals, the person chose the Codex proposal ([`reviews/2026-09-24-terminal-experience-reimagining.md`](../reviews/2026-09-24-terminal-experience-reimagining.md)) as the spine. They asked for four additions from the earlier draft, named the unit of work **branch** everywhere, retiring "changeset", asked for `dockhand serve` and `serve --install`, and asked for the instance coordination design to be included. The result is [`docs/design-v3.md`](../design-v3.md).

## What Design v3 is

- **The consolidated contract.** It is the document roadmap step 3 and decision 44 ask for, in the new vocabulary: branch, revision (a commit or a snapshot), verification plan, provider, run, guest execution, and target result.
- **The spine, from Codex:**
  - context comes from the worktree or `--branch`, and a port name never selects a branch;
  - authoring edits files without committing;
  - `check` works on unfinished work, as numbered snapshots;
  - `tidy` groups commits by logical change;
  - `submit` has an explicit preview;
  - honest behavior for foreground work and `serve`.
- **The four additions:**
  - MacPorts specifics: the commit rules, the PR template sections, CI's actual behavior, stealth updates, `[skip notification]`, and the 72-hour maintainer rule;
  - `create` from a URL;
  - `submit --passing`;
  - the needs-you list, as bare `dockhand` at the repository root and as `status --attention`.
- **Instance coordination, settled in §11:**
  - sessions with liveness from pid and start time, backed by a heartbeat;
  - fenced leases that are void when their session dies;
  - one `serve` leader with standbys;
  - cancellation applied by whoever can apply it;
  - an event journal in the database for observers;
  - no socket service.
- **The direction record.** §14 lists which decisions v3 changes: selection and continuation (19, 22, 25, 26), authoring that commits (22, 27), and renamed flags (21, 29, 37). The rest stand.
- **Pushback, in §15:**
  - no `--allow-incomplete` for substantive targets;
  - `update.then` dropped;
  - no `serve` setting that submits;
  - `create` rather than `new` for a new port;
  - `review` as its own verb;
  - no socket service;
  - sparse worktrees rather than full ones;
  - a branch identity separate from the ref name.

## `serve --submit-passing`

The person decided that `serve` may open PRs for whatever passed, as an opt-in flag, with building and testing only as the default. Design v3 §11 adds `serve --submit-passing` with these guardrails:

- **Scope.** Only branches `serve` created from new releases.
- **Pass rule.** A pass on the exact committed tree, with nothing needing `--accept`.
- **Held branches.** Branches with any upstream-comparison or commit-rule finding are held on the attention list.
- **Daily limit.** At most `serve.submit_limit` PRs a day, 10 by default.
- **Labels.** Each PR it opens is marked "opened by serve", in status and in its body.

The authority is a flag on the process, never a config key. `serve --install --submit-passing` records it in the launchd agent. Principle 7, the promises, §14, and the §15 pushback were reworded to match.

## Rebuild, a fresh database, and the roadmap

The person decided:

- the top layer is rebuilt, with full leeway;
- the database starts fresh, with no migration from v2;
- breaking changes are fine, so that building to the new model isn't slowed by compatibility;
- `serve --submit-passing` may also be a config key, `serve.submit_passing`.

Design v3 now says:

- the database is `~/.dockhand/dockhand.db`, and v2's `state.db` is left on disk untouched and never read;
- `serve` announces at startup, and in `queue`, whenever it opens PRs;
- decision 44's migration acceptance case is dropped.

The roadmap's Next queue was rewritten around the rebuild:

4. the v3 core: new `model`, `store`, `coord`, `engine`, and `command` packages, the narrow branch path, and v2's recovery rules ported as acceptance tests;

6. switching the binary over and deleting v2's top layer;
7. the oracle;
8. reuse and archives;

Three needs-design items are settled by v3: review and unattended-publication authority, more permissive human-edit capture, and instance coordination.

## `serve.for_outdated`

The person renamed `serve.updates` to `serve.for_outdated`, so the setting reads as what `serve` does for your outdated ports (`list`, `draft`, or `check`). Its schedule key, `updates_at`, became `outdated_at`. Earlier notes in this file keep the old name as history.

## v2 is retired early, and work moves to `main`

The person was willing to go without a working tool if that made v3 faster. Measuring the imports showed it does. The domain packages import v2's `record` for shared vocabulary, and `progress` for reporting. The providers are also built on v2's per-target `Attempt`, `BuildSpec`, and `ProviderExecution` records and its `state` provider store, which is exactly what v3's guest execution replaces. Keeping v2 compiling would therefore mean reshaping them twice.

The roadmap now:

- **Freezes v2 in step 4.** It tags `v2-final`, moves the shared vocabulary out of `record`, and deletes v2's top layer before the v3 core is built. Building `v2-final` as `dockhand-v2` keeps a working tool meanwhile; its `state.db` and v3's `dockhand.db` never touch.
- **Keeps the guest channel ahead of the freeze**, so `v2-final` has it.
- **Corrects an earlier claim.** The earlier roadmap said the providers carry over unchanged. They are reshaped to guest executions, keeping their idempotency and reconciliation rules.

The person also decided that work happens directly on `main`, as the handoff note said.
