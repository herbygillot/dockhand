# Repeating an unconfirmed pull request request

Found by the same `py-cssselect` bump, after the advisory-test fix: with the evidence reused and the branch pushed, GitHub answered the pull request creation with a 500. Dockhand treated the write as uncertain and observed the fork for a pull request on that branch without asking again, which is the right instinct, since a lost response can hide a pull request that exists. But when no pull request exists, that policy had no way back: it observed on a backoff, twenty waits of up to five minutes, and then settled as needing attention, and a person would then have to publish again.

Now an uncertain request is repeated once two looks since it show no pull request for the head branch and the branch is at the verified commit. The first look after the failure clears the write's error and records the observation as unresolved; the second finds nothing and clears the write intent, counting a refusal as the rate-limit path does, and the same pass asks again. The forge refuses a second pull request for one head, so the repeat cannot double up, and a lost response whose pull request does exist is found by the first look and never repeated, which the existing test still proves. A job asked to cancel stays observation-only, as before. The fake forge gained a way to fail before acting, and the new test walks the push, the failed request, the unresolved look, the repeat, and the confirmation.

The run that found this had already been asked to cancel, so it stayed observation-only under the new rule too, and was driven out by hand.

While that job waited, `status -v` printed its wait counter as `%!d(string=9)`: the verbose status line helper quotes every value to a string before formatting, so the two lines that used `%d` for the consecutive-wait count now use `%s`, and no other line in that file uses a numeric verb.
