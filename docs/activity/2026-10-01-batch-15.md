# 2026-10-01: provenance (batch 15)

Batch 15 of the [roadmap](../roadmap.md): a `Generated-By` naming a commit nobody can find, not only a `+dirty` build. In [the hugo exercise](../reviews/2026-09-28-hugo-bump-exercise.md) (finding 1), tidy ran a build of `14320eb7`, six commits ahead of origin; within the hour a rebase of `main` left that commit unreachable, and the trailer named a build nobody could find. Tidy and submit already said a `+dirty` build. Tidy reads nothing remote, so submit, which talks to GitHub anyway, now asks.

## What changed

- **submit's plan asks dockhand's repository on GitHub for each build its commits name.** `Engine.unfoundBuilds` (`engine/provenance.go`) reads each commit's `Generated-By`, and asks once for each build, in the order the commits first name them: by its commit, or for a release, by its tag. `SubmitPlan.UnfoundBuilds` lists the builds GitHub doesn't have, each with the commits naming it. `SubmitPlan.BuildsProblem` says why GitHub couldn't be asked.
  - A build of uncommitted source is `ModifiedBuilds`', and isn't asked about.
  - A `devel` or `unknown` build recorded no commit, so it's listed without asking, as one nobody can find (its `Source` is empty).
  - A missing login, the network, or a rate limit is one problem, said once. The builds after it aren't asked. Submit still goes ahead.
  - None of it goes in `Blocking` or `Concerns`, so it holds nothing for a person, for serve, or for bump.
  - It runs after `destination`, which has already required the GitHub login, beside the search for other pull requests.
- **What a build's tag finds is `version`'s to say.** `Info.FullRevision` is the VCS revision as the toolchain recorded it, all 40 characters. `Revision` stays the twelve that `Tag` and `String` show, so the trailer is unchanged. `version.SourceOf(tag)` reads a tag back to what finds its source:
  - a pseudo-version's commit, by `golang.org/x/mod/module`'s `PseudoVersionRev`, which dockhand already imports and vendors;
  - `devel+<revision>`'s commit;
  - otherwise a release, by its tag;
  - nothing, for `devel`, `unknown`, or a tag of uncommitted source.

  Where the tag is the running build's own and the toolchain recorded a revision, the commit is the whole one. That holds for a tagged build too, since a tag can move.
- **The build a message's `Generated-By` names is `commitmsg`'s.** `commitmsg.Build` gives its tag; `ModifiedBuild` now reads it there. A legacy form names none.
- **GitHub is asked through the forge repository.** `forge.CommitRepository` has `HasCommit`, a commit named in full or abbreviated. `forge/github`'s repository implements it beside `CommitTime`, with one GraphQL query, `object(expression:)` on the repository, asking for a `Commit`'s `oid`.
  - An object that isn't a commit isn't the one asked for, and nor is one whose `oid` doesn't begin with the name asked.
  - `git.ValidAbbreviation` exposes the pattern that `CloneCheckout` already used for gitrevisions(7)'s short names. A name of neither form isn't sent.
  - The engine's `Forge` gains `Repository(instance, name)`, which `*forgegithub.Client` already had. dockhand's repository is `version.ProjectURL`, read by `github.PageRepository`. A release's tag is asked with the repository's `Tag`.
- **The preview says each one with a `!`**, after the modified-build lines:
  - "commit 1a2b3c4's Generated-By names dockhand v0.0.0-…-14320eb7c0de, built from a commit dockhand's GitHub repository doesn't have, which nobody else can find until it's pushed there";
  - "commits 1a2b3c4, 5d6e7f8 name dockhand … in Generated-By, …" for several commits;
  - "built at a tag …" for a release;
  - "…names dockhand devel, which recorded no commit, so nobody can find what it was built from";
  - "couldn't ask GitHub whether it has the dockhand builds the commits name in Generated-By: …", once.

  `--json` gives `unfound_builds` beside `modified_builds`, each entry with `build`, `commits`, and the `commit` or `release` asked for, and `builds_problem` where GitHub couldn't be asked.
- `docs/usage.md` says it where submit's preview is described, and `docs/development.md` where the trailer is.

## Decided along the way

- **Abbreviated commits are asked through GraphQL, since only GraphQL documents them.** GitHub's REST "Get a commit" says its `ref` "Can be a commit SHA, branch name (heads/BRANCH_NAME), or tag name (tags/TAG_NAME)". The Git database's "Get a commit object" says `commit_sha` is "The SHA of the commit." Neither mentions an abbreviation. GraphQL's `Repository.object` takes `expression`, "A Git revision expression suitable for rev-parse". gitrevisions(7) defines `<sha1>` as "The full SHA-1 object name (40-byte hexadecimal string), or a leading substring that is unique within the repository."
  - So one documented query takes both the whole commit the running build knows and the twelve characters an older build's trailer has. An older build is checked, where it would otherwise have gone unchecked.
  - dockhand already uses GraphQL where REST can't (`MarkReady`). GraphQL takes only a signed-in request, which submit has by then.
- **The running build is asked by its whole commit**, which `version` now keeps. A build `go install` made from the module proxy recorded no revision, and its tag's twelve characters are asked, as for an older build.
- **The line says the commit isn't pushed, not "tidy again".** The modified-build line advises tidying again with a build of a pushed commit, and tidy does replace a `+dirty` build's line. A commit whose only change would be its `Generated-By` naming any other build is one tidy keeps (`commitmsg.Unchanged`; `TestACommitThatSaysTheSameIsUnchanged`'s `v2.9.0` case), so the same advice here would change nothing. Pushing the commit the build names to dockhand's repository settles it, which is the case dockhand's own dogfood runs meet.
- **A `devel` build is said without asking.** Nothing names its source, so there's nothing to ask GitHub, and nobody can find it either. A test binary is such a build, and so is `go run`, so every test's tidy writes `Generated-By: Dockhand devel`. That's why the tests write the builds they ask about by hand.
- **One problem stops the asking.** A rate limit or a missing login would fail every request the same way, and the preview says it once, as `SearchProblem` does for the search for other pull requests.

## Left open

- **Nothing replaces a `Generated-By` naming a build nobody can find, unless it was `+dirty`.** Tidy keeps the commit, as above. A commit rebased away, as `14320eb7` was, can't be pushed, and a `devel` build names nothing to push. Rewriting such a commit needs either tidy to treat these builds as it treats a `+dirty` one, which it can't know of without asking GitHub or a record of submit's answer, or a way to ask tidy to write a commit's message again. Which one is the person's call.
- **serve asks for each candidate's builds each time it plans one.** Usually that's one request, for its own build. A build GitHub has could be remembered for the process's life, as a pushed commit stays pushed.
