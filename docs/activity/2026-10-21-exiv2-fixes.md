# The exiv2 notes' fixes for main

The five fixes placed in 402b6ba4, taken while v0.4.0's tag waits.

## body-wrap beside a URL (note 9)

libextractor's commit as it stands (72e32cd7, field testing) has no line
over 61 characters, so the reported miss couldn't be reproduced from it;
its message was likely rewrapped after the lint ran. A synthetic
79-character line holding a URL reproduced the theory: `CheckCommits`
found nothing, since a line over 72 was spared wherever it held "://".
It now spares a line that is only a URL, or a trailer whose value ends in a URL, as Generated-By's does, or is
one, as `Closes:` with a ticket's (`urlTrailer`). A sentence holding a
URL is flagged. The rule's text in `explain` says so.

## Logs named by target (note 5)

The guest named each target's log for its place in the job, target-N.log,
so nothing in a multi-port check's directory said whose each was. The
host now names each in the guest's input (`logName`, tart/provider.go):
luminance-hdr.log, or s2n-tls+tests.log for a variant build. A character
a file name shouldn't hold is written _. The guest uses that name, and
falls back to target-N.log for an input without one. A lost guest's
interrupted target fetches its log by the same name. A result records
its log's name, so earlier checks keep theirs.

## A dependency's failure at its own phase (note 4)

The guest failed a target whose dependencies wouldn't install at
`install`, so status said "luminance-hdr failed at install" where
qt5-qtwebengine had failed to build. `model.PhaseDependencies` is a phase
of its own. The guest gives it MacPorts' line for its detail, as `why`
reads it: "Failed to build qt5-qtwebengine: command execution failed".
The grid reads "✗ a dependency failed" (`Phase.FailureWords`). status's
row, the check's report, and the run's event give the detail beside it:
"luminance-hdr: a dependency failed on macOS 27 (check-N): Failed to
build …". It stays a failure `--baseline` answers, as install's is.

guest.tcl changed for both, and only in wording and phase; a failed
result is no evidence a later check reuses. So VerifierProtocol stays 3,
and the pin is updated, its history saying why.

## A cell from another check names it (note 8, its second half)

A branch's table takes each target's cell from the newest check of its
files that has one, and a reused result from the check that built it.
No cell said which, so after an edit between checks the person couldn't
tell the newest check's cells from the rest. `Evidence.CellCheck` names
the check a cell's result came from where it isn't the newest's own:
the check that built a reused result, or the earlier check whose result
fills the cell. On the terminal, in status and check's report, the cell
says it, "✓ (check-440)", unless its tests' reading already named it.
The pull request keeps naming the runs behind each environment.

## Outside the profile, only what a check planned (note 7)

A branch's evidence is judged against every environment a check of its
files planned, beside build.default's (`evidence.Plan`). A target a
check's `--only` left out is a cell not run in each of that check's
environments. So one diagnostic `check --only ufraw` on 13 and 14 made
`submit --plan` ask for all six of the branch's ports there. `Judge` now
takes build.default's environments, and `outsideProfile` turns a cell
not run into "—" in an environment they don't cover (`Covers`), where no
check of the files planned that target. It's an exclusion with `Span`,
as a release a profile skipped, and counts for nothing. What a check
found there still counts, a failure included, and a target a check
planned there and didn't reach is still asked for. Naming that check in
submit's line is left undone. README and the v0.4.0 notes list it as a
known issue.
