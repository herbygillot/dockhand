# The ledger, finding kinds, and the decision record (v0.5.0 part 2, item 2)

## The reason a failure is accepted is a kind (R3-30)

`SubmitPlan.Accepted` held a sentence for each accepted failure, and words.go compared that sentence (`accepted == acceptedBlocked`) to decide how a blocked cell reads. It's now `engine.AcceptedFailure{Kind, Baselines}`:
- `AcceptedAtBase` carries the baselines that fail the port alike, the fact `AtBase` keeps.
- `AcceptedUnestablished` and `AcceptedBlocked` carry nothing more.

`Words()` says each kind as before, so the pull request's table, the preview's Checks line, and the terminal read unchanged. `submit --json` gains `accepted`, each port with its `kind`, `baselines`, and `words`. A standing acceptance of an environment failure is then one more kind.

## A commit-rule warning holds nothing (the first contradiction)

serve held a branch whose commits carried a commit-rule warning, such as a body line over 72 characters, while tidy kept those commits as already in good shape. The branch waited for a look that no command could act on. `SubmitPlan.Concerns` now holds only a commit-rule error, which tidy rewrites. A warning still shows in submit's preview and `--json` findings, and tidy's plan still says it, but it holds nothing. The pull request's "rules passed" answer still reads errors alone, as before.

This was a policy fork. The other way would have tidy rewrite commits over a warning. Herby took this one: "Go with the implementor's pick" (2026-10-22 03:28Z).

## The decision record (schema 35)

`model.Acceptance` becomes `model.Decision`: a person's answer to a finding, which a later command reads instead of asking again.
- A decision names the finding it answers, by its kind (`FindingFailure`, the one kind today) and its subject (the port).
- It names the evidence it rests on: the commit a failure was accepted at.
- It holds the answer (`Accepted`).
- It lapses when its evidence changes, because it's read only for that evidence.

The `decisions` table replaces `acceptances`, and schema 35 copies each acceptance across. `branch_id` may be null for a standing decision, which answers its finding on any branch while its evidence holds; the standing acceptance of an environment failure will be the first. Forgetting a branch deletes its decisions, as it deleted its acceptances, and standing decisions belong to no branch.

Not taken here: `--shared-release` as a decision that answers a finding. Siblings moving is a refusal until part 3's strict fidelity makes it a finding, and a decision needs a finding to answer, so it moves to that item.

## A dependency's failure names the dependency and its version (schema 36)

This is the first half of the standing acceptance. When a target fails installing its dependencies, the Tart guest reads the dependency from MacPorts' line ("Failed to build libgcc15: …"). It then asks the tree for that dependency's version and revision with `port -q info --line --version --revision`, both documented options of port(1). The result carries them as `model.TargetResult.Dependency{Name, Version}`, kept in two new `results` columns.
- Other providers leave the field empty, as GitHub Actions' log doesn't say which dependency failed.
- The guest still builds and judges ports as before, so `VerifierProtocol` stays 3 and only `guestPin` moves.
