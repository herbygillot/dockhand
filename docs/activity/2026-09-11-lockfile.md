# Lockfile simplification report — September 11, 2026

Removed the application config-directory concept. There is no `app.Config.ConfigDir`, `app.Initialize`, `DOCKHAND_CONFIG_DIR` lookup, or directory creation during CLI startup. Deleted `internal/app/config.go`. The repository's default `.` selection now lives in `app.Build`, where repository services are constructed.

## Path selection and initialization

Cobra owns the `$HOME/.dockhand/ledger.lock` default and the persistent `--lockfile` flag, now also available as `-L`. An initial `app.Config.Lockfile` can supply another default for embedded callers. Paths resolve against the invocation's working directory; explicit empty flag values are rejected. The selected absolute path passes through `app.Config.Lockfile` and `app.Build` to `ledger.Options.Lockfile`. No config-directory constant or additional configuration abstraction was needed.

`ledger.New` validates the repository and options, then creates any missing parent directories with mode 0700 and opens or creates the lockfile with mode 0600. It closes the descriptor before returning and does not acquire an advisory lock or create ledger records. Existing files are neither truncated nor replaced, and existing permissions are preserved. Filesystem errors are returned during initialization.

Writes open the initialized file and retain the existing bounded `flock` acquisition. If the lockfile disappears after initialization, a write returns an error instead of recreating it. Reads remain snapshot operations without writer locking. Help and completion construct no ledger and create no directories or files; help displays only the resolved lockfile path.

Updated the README, architecture, component map, and CLI design. Added follow-up notes to the earlier config-directory and Cobra activity reports to preserve their history while pointing to the revised behavior.

## Provenance

All changes were authored for v2, using the existing v2 flag validation, service wiring, and ledger locking code. The new lockfile-initialization helper moves filesystem creation from lock acquisition into store construction. No v1 code, comments, or tests were copied, and no dependencies were added or changed.

## Validation

`go build ./...`, `go vet ./...`, and formatting checks passed. Temporary checks used a compiled CLI and a Go harness with the race detector, operating only on disposable directories and Git repositories. They verified:

- Default lockfile selection, ignored `DOCKHAND_CONFIG_DIR`, relative overrides, paths containing spaces, and both global flag forms before and after commands.
- Root and nested help, the usage alias, completion for four shells, and invalid invocations without directory creation.
- CLI-to-ledger path propagation and constructor creation without ledger records or workflow execution.
- New-file permissions; preservation of existing contents, inode, and permissions; concurrent initialization while another descriptor holds the writer lock.
- Writer timeout on the configured lock, successful writes after release, snapshot reads during a held lock, invalid initialization paths/options, and failure if an initialized lockfile is removed.

The harnesses and binaries remain outside the repository. No permanent tests were added. Workflow commands still return their existing not-implemented errors.
