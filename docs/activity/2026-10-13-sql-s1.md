# SQL-S1: history's prune, through indexes and in chunks (v0.3.1)

The SQL study of 2026-10-13 ([review](../reviews/2026-10-13-sql-study.md))
found daily cleanup's `PruneHistory` quadratic in history. On its year-scale
synthetic database it passed the 30 s operation timeout and rolled back, so
`Cleanup` stopped before archive and journal pruning, and every later cleanup
met the same timeout. While it ran, other writers, a check's results among
them, gave up after the 5 s busy timeout.

- Schema 31 (`schema/031.sql`): `run_plan`, `run_revision`, `plan_revision`,
  and `result_reused`, the child columns pruning's deletes and NOT EXISTS
  read; `result_archive` dropped, with no reader since D6 (SQL-S3).
- The delete is one store-internal function over a set of branch IDs,
  `pruneBranchHistory`, in foreign-key order, which forgetting an archived
  branch (v0.4.0's part 3) is to reuse for one branch (SQL-S2). Its results
  step computes the keep set once, as a MATERIALIZED CTE, read by a row-value
  NOT IN; its executions step is two NOT EXISTS, one per column, where an OR
  had kept SQLite from either index.
- `PruneHistory(before, after, limit)` takes the ended branches a chunk at a
  time in ID order, says the last it took, and prunes inputs no result names
  in the call that finds none left. `Cleanup` loops one transaction per
  chunk, `historyChunk` = 10 branches.
- Tests: TestHistoryIsPrunedWithoutCorrelatedScans fails any statement whose
  plan scans a table under a correlated subquery; TestHistoryIsPrunedAChunkAtATime
  covers the chunks and the cursor. The existing D6 test runs over chunks.
- docs/development.md gains two rules: an index on every foreign-key child
  column of a pruned table, and no write transaction past about a second at
  year scale.

Measured with the study's probe on its year-scale database, on this Mac (M
series, F_FULLFSYNC): the whole first-time backlog of 200 ended branches
(130,395 results) in 16.8 s, each chunk of ten branches 0.70 to 1.03 s, and
`PruneArchives` 0.35 s. A chunk of fifty took 3.2 s. Most of a chunk is the
delete of its results, about 85 µs a row here, with the keep set 0.27 s. A
single branch with a very large history is still one chunk: chunking within a
branch was left for a measured need.

The roadmap's v0.3.1 line no longer says this batch keeps a dependency's newest
archive: that rule is part 1's, which extends the keep set.
