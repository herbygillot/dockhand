# 2026-10-02: a patch upstream merged is dropped (batch 59)

Batch 59 of the [roadmap](../roadmap.md): item 7's "files that preparation adds and deletes" (40), sized in v2's roadmap as the ports whose updates meet a patch upstream already merged: dropping it is the maintainer's chore, and update called it a patch that no longer applies.

## What changed

- **patchcheck says a patch the source already holds.** A patch that doesn't apply is tried in reverse, as `patch -R` in check mode; one that applies so, every hunk, is `Merged`: "is already in the source: it applies in reverse".
- **update drops it.** The patch's name comes out of the Portfile's top-level `patchfiles` or `patchfiles-append`, where it's a literal word, the line with it where it was the only one (`portfile.DropPatch`), and its file out of `files/`, found where the port's `filespath` puts it (`PortInfo.FilesPath`). The edited Portfile is evaluated, and the drop kept only where the port reads as prepared but for those patches. An edit can now delete a file (`portfile.Edit.Delete`), which editprep hands on as a deletion, and the engine already applied. update says "Dropped patch fix.diff, which the new source already holds; its file goes too.", for a batch too, and `--json` gives `patches_dropped`; a patch dropped isn't a patch problem.
- **A patch written otherwise stays**: in a variant, a condition, or a computed word, it's still a patch that no longer applies, for a person to drop.
