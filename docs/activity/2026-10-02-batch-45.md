# 2026-10-02: a GitHub login that renews itself (batch 45)

Batch 45 of the [roadmap](../roadmap.md), steps 2 and 3 of the "GitHub auth flow review" thread's plan: dockhand's login becomes an access token good for eight hours and a refresh token good six months from its last use, renewed by itself, in serve too. GH_TOKEN, GITHUB_TOKEN, and gh's login are unchanged, and never renewed.

## What changed

- **A login record** (`credential.Login`): the access token and its expiry, the refresh token and its expiry, the account, and the OAuth client it was made with. It's kept as JSON that `Encode` alone writes, versioned; `String` and `GoString` say whose login it is and until when, never a secret. A saved value that isn't one, the bare token earlier dockhands kept among them, reads as "the saved GitHub login is from an earlier dockhand; run dockhand auth login": nothing stays compatible, as the person decided, since dockhand isn't widely released.
- **The device flow asks for `public_repo offline_access`** and returns the whole login: the access token's expiry from GitHub's `expires_in`, the refresh token's from `refresh_token_expires_in`, a number or a string. A login without a refresh token or its expiry is refused, and nothing saved. Its endpoints take the client ID in the request's parameters, where auto-detection would first try Basic auth with an empty secret.
- **Renewal, safe across processes.** The Keychain source gives the access token while it's good for more than five minutes and isn't the one GitHub just rejected (batch 44's retry asks it as `Renewer`). Otherwise, where the refresh token hasn't expired, it takes `~/.dockhand/github-login.lock` (`github.LoginLock`), waiting at most 30 seconds, reads the login again under it, and returns one another process renewed meanwhile, so the one-use refresh token is never spent twice. It renews through the token endpoint, and saves, and unlocks.
- **Each way renewal fails, as the plan has it:** a refresh token six months unused, said without asking GitHub; GitHub refusing it (`bad_refresh_token`, `invalid_grant`), which ends the login; a network's failure or GitHub's 5xx, which leaves the login as it was; and a save the Keychain refuses after a renewal, the dangerous case, since the old refresh token is spent: the renewed login is used from memory, said once, and saved the next time the login is asked for.
- **auth login saves the whole login.** What the person sees of it, the status, logout's revocation link, the setup line, serve's one notice, and the docs, is batch 46.

## Verification

- `TestALoginIsKeptAndReadAndPrintsNoSecret`; the device flow's test with the refresh token's expiry as a string, and `TestALoginWithoutARefreshTokenIsRefused`; `TestTwoRenewalsAtOnceRenewOnce`, two renewals sharing a lock and a store making one request and both getting the new token; `TestALoginThatCantRenewSaysWhy`, expired without a request, refused, and a 500 keeping the record, no secret in any error; `TestARenewedLoginTheStoreRefusedIsUsedAndSavedLater`; `TestARejectedLoginIsRenewed`, a 401 renewing a token that hadn't expired.
- The full suite with `DOCKHAND_TEST_MACPORTS_TCLSH`; fmt-check, vendor-check, vet, deadcode, and lint, each read for its exit status.
- Not yet tried against GitHub itself: whether the OAuth app issues a refresh token for `offline_access`, and whether the Keychain asks for a password when a renewal writes the item. Both need the person's `auth login`, so this batch waits on a branch until then.
