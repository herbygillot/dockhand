# 2026-10-01: what the sand-runner port found (batch 28)

Batch 28 of the [roadmap](../roadmap.md): a dogfood session made a new SwiftPM port, `sysutils/sand-runner`, with `create`, and checked it on Tart 26 and 15. Each finding was checked against the code before it was placed; the person decided how checks make a branch ready (D17), and that a minimum Xcode an environment lacks is unmet there and still required.

## What changed

- **Each environment takes its newest check (D17).** `check --on tart:26` passed, then `check --on tart:15` failed, and status said "1 failed, 0 passed" and submit "did not pass", the pass on 26 gone: the newest check's plan alone said which environments counted, and earlier checks filled only its gaps. The other way, a check on one release alone could make a branch ready with nothing built on the others. A branch's evidence is now judged against the newest check's plan with each environment another check of the same files planned, by the newest that did, and the default environments, `check.on`'s (`evidencePlan`); earlier checks fill each one's cells as before. A default environment counts as checked where a check built on the same provider, on the same release where the default names one (`covers`). status reads it the same way.
- **A minimum Xcode the environment lacks is unmet, not a failed fetch.** sand-runner declares `minimum_xcodeversions {24 26.0}`, the xcodeversion PortGroup's documented option, and the tart:15 image has Xcode 16.4, so its build failed on the PortGroup's refusal. The evaluator reads the option against the Xcode it models for the release (`dockhand.minimum_xcode`), the plan records it per environment (`EnvironmentPlan.MinimumXcode`), and the target, and what it's a prerequisite of, is unmet there whatever the tools, "needs Xcode 26.0" (`model.RequiresXcodeVersion`). As the person decided, it's still required: submit waits for a check with that Xcode there, or `--draft`, and Tart's remedy says how to give the image it, `sequoia = "26.0"` under `[providers.tart.xcode]` and setup with that Xcode.
- **A new port's license is said, not held.** A port the base doesn't have was read against an empty archive, so "LICENSE was added; the Portfile's license line may need to follow" and "Package.swift is new; the build may need the Portfile to follow" were said of every new port, holding an unattended submission. As the assessment design has it, a new port's candidate is still assessed, license and requirements included: its license file is said with the Portfile's license line, "upstream ships LICENSE, and the Portfile says MIT", with what the project's manifest declares beside it, holding only where the line doesn't name that; its build files, all new to it, aren't said (`assess.Input.New`). `assess.Policy` is 13.
- **create refuses a taken name before it starts a branch.** `create --new` started `dockhand/sand-<id>` and only then found textproc/sand, leaving the branch behind, and said nothing of `--name`. It now asks master, fetched just now, first (`Engine.NameTaken`), a subport's name included, which the port index knows; where the index can't say, that's said and the directory check stands. The refusal names `--name`.
