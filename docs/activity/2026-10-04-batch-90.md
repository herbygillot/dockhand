# 2026-10-04: a guest-built toolchain builds once (batch 90)

Batch 90 of the [roadmap](../roadmap.md): from the M1's quick run at d302e744. B2's check of dust on macOS 27 built rust and cargo from source, since MacPorts' builder for the release hadn't archived them yet, 94 minutes on the VM's two cores. B3's `serve --drain` check of dust then started a fresh VM and built rust again from zero. Every Rust or Go check on such a release paid the toolchain's build.

## What changed

- **A check keeps the archives its guest installed dependencies from.** The guest already reported each port active as a target built, with its archive's digest; it now says where that archive is, and the Tart provider copies it out, checked against the digest, as it does a passed target's own (`buildenv.Build.KeepDependency`). It is recorded for the port and the environment, in schema 30's `dependency_archives`, beside the `archives` row that holds the file. A port the plan builds is the branch's, whose archive is its result's, and isn't kept this way.
- **A later guest is given the kept archives of its targets' dependencies.** For each target it builds, the check looks up its direct dependencies, as MacPorts evaluates it in the revision, and the ports its earlier builds there had active, and gives the guest the two newest kept archives of each in the archive site kept target archives already use (`driver.dependencyInstalls`). MacPorts tries that site first, takes an archive whose name is the one it would fetch, and fetches or builds the rest as before. So rust and cargo, built once, are installed by the next check of dust or of any other port that depends on them. The check says so: "the guest may install rust, cargo from archives earlier checks' guests here installed them from, rather than build them". One changed since it was kept isn't given.
- **They go with cleanup.** A dependency's archive is named by no result, so cleanup forgets it once it's older than its cutoff, and its record goes with the archive's.
- **Every kept dependency archive isn't given to every guest**, as the coordinator asked whether it could be: each is uploaded into the guest before MacPorts asks for any, rust's alone hundreds of megabytes, and the host knows from a target's evaluation which it needs directly, which reaches rust, cargo, and go. The roadmap item says so.
- **The guest program's pin** moves with a note: it reports one more field, and builds and judges nothing otherwise, so the verifier protocol stays 2.
- The README's known issue now says the toolchain builds once; saying before the first build that it will is still the person's decision.

## Verification

- New tests: the guest reports where each active port's archive is; the Tart provider keeps a dependency's archive and not a target's; the store finds kept dependency archives by port and environment, newest two first, and prunes them with their archives; a later check's guest is given the archive of a dependency an earlier guest installed.
- The full checks: fmt-check, vendor-check, vet, lint, deadcode, and the suite under MacPorts.
