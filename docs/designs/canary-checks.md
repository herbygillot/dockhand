# Canary checks: `check --also a,b --set name=value` builds unchanged ports against the branch under a Portfile or PortGroup option

A feature for v0.10.0. Its issue, and the roadmap's entry, say where it stands; this file is the design, moved here from docs/roadmap.md at 56e8045e on 2026-11-04.

Where it came from: the openssl4 new-port session's note 5, macports/macports-ports#36375 on v0.7.0, sent here through field testing on 2026-11-04 at 02:53Z, from Later; the person's "As shown" on prioritization's triage card at 02:58Z; architecture's design, sent here by the coordinator on 2026-11-04 at 03:14Z, /mnt/project-files/plan/canary-checks-set-2026-11-04.md, aimed at v0.9.0; not harm; about a batch, inferred.

- the author's words: "Canary or reverse-dependency testing against a new library branch was entirely manual: start a new branch, git sparse-checkout add five dirs, cherry-pick both commits, awk `openssl.branch 4` into four Portfiles, commit, adopt. --also builds unchanged ports but can't change a setting. Something like `check --also libssh2,socat --set openssl.branch=4` would cover it, and the same need comes up for python/perl/llvm/php version moves. This clearly needs design: how settings are injected, and whether results count as evidence for the main branch." The canary branch was dockhand/openssl4-canaries, four dependents on tart:26 (check-773), openssl4's own pass reused from check-772; the linkage audit ("iperf3 links openssl4's libraries, declared in depends_lib") was the evidence they built against branch 4.
- **for the person:** master's openssl PortGroup knows branches `no_version 1.0 1.1 3` (`default openssl.branch {[openssl::default_branch]}`, 3), so `--set openssl.branch=4` works only on the branch that teaches the PortGroup branch 4, the openssl4 branch, whose tree the canaries build in; on master it is the evaluation's error, "Invalid OpenSSL branch: 4".
- today `--also` builds unchanged ports against the branch: Also targets, Kind Unchanged, Role Also (engine/plan.go:122, `alsoVariants`), their directories looked up by name and added to the worktree's sparse checkout, each evaluated in each environment (`checks.PortReader.Ports`, service.go:128, the eval session's `mportopen "file://$portdir" $opts $args`, evaluator.tcl:255, with options `subport <name>` and the variants), ordered after the changed ports it depends on, and blocked in the guest where one of them didn't pass (`depends_on`). In evidence an Also target is an extra (`TargetEvidence.Extra`, evidence.go:202): shown where it ran, required nowhere, its failure accepted by name (`submit --accept`, the ExtraFailed row) and never fixed. The plan prints them on its "Also" line (view/writers.go); GitHub's workflow won't build them. A target's ID is its name and its variant spec, "jq +x11" (`model.Target.ID`, vocabulary.go:96); a build's inputs (`model.TargetInputs`, inputs.go) key the environment, directory, tree, resources, variants and active ports, and a build with identical inputs is reused. The guest (buildenv/guest/guest.tcl `build`, :911) opens the target on every port(1) line as `port -N -D <portdir> <action> subport=<name> +variant…`, the selection's `subport=<name>` itself a user option in port(1)'s syntax; it installs the dependencies `port -q echo depof:<name>` lists first (`install --unrequested`), then fetch, checksum, install from source, test; its own reads (`declares_tests`, `checkout`, `work_dir`, `portgroups`, `path_dependencies`, `links`) call `mportopen` with options `subport <name>`. In MacPorts (macports-base, read 2026-11-04) a `name=value` on port(1)'s line reaches `macports::worker_init` as `options`, which sets `user_options($opt)` and the variable before the Portfile is sourced; `handle_option` (portutil.tcl) leaves a user-set option as it is when the Portfile sets it, and `default` leaves a value already set; `options` declares each option as a Tcl command of its name, so `info commands ::openssl.branch` says whether a port declares it; PortGroup callbacks run after the Portfile and its variants and read the value in effect (the openssl group's `port:openssl<branch>` from `openssl::set_openssl_dependency`, flags, env and pkg-config paths from `openssl::configure_build`).
- after: `--set name=value`, repeatable, on `check`, beside `--also`: each `--also` port is built with the option set as `port install libssh2 openssl.branch=4` sets it, in the check's builds alone. No Portfile is edited and no branch is made: the library branch itself is checked with its canaries, `dockhand check --also libssh2,socat,iperf3,sslscan --set openssl.branch=4`, `dockhand impact` naming the dependents to choose from. A version move goes the same way with the option its PortGroup declares, `--set python.default_version=314` for python's, perl5's and php's default-branch options alike.
- scope: a setting applies to every `--also` port and to nothing else: not to the branch's changed ports, whose builds are what the pull request submits, and not to the dependencies the guest installs first, which install as the tree has them, from archives. `--set` without `--also` is refused: "--set applies to the ports --also names: name them, as --also libssh2,socat --set openssl.branch=4; a changed port under a setting is a line in its Portfile". On a branch that changes nothing, `--also curl --set openssl.branch=4` is an investigation, as `--also curl --variants '+gnutls +sectrust'` is (branches.md:240), ended by `archive`.
- declared, and evaluated under the setting: each `--also` port must declare the option in the branch's tree, under its variants, the plan's evaluation asking the opened port `info commands ::openssl.branch`, as `assumed` asks for a PortGroup's options (evaluator.tcl:214). One that doesn't is refused before anything is captured: "--set openssl.branch=4: socat declares no option openssl.branch (neither its Portfile nor its PortGroups), so the setting would change nothing there; leave it out of --also, or name an option it declares". The evaluation opens the port with the setting among its options, so planning reads the port under the setting: `check --plan -v` prints its dependencies and configure.args as they are with it, a canary whose `depends_lib` becomes the branch's openssl4 is ordered after openssl4's build and blocked where it fails, and a value the PortGroup rejects is the evaluation's error, unresolved in the plan with MacPorts' words ("Invalid OpenSSL branch: 4", master's PortGroup).
- identity: a build under settings is its own target, its ID the port's name, its variant spec, then its settings in name order, "libssh2 openssl.branch=4", "curl +gnutls openssl.branch=4", beside the port's default build as a variant build is, never in its place. Its inputs carry the settings (`TargetInputs.Settings`), so no default build's result stands for it and it stands for none; reuse is otherwise as it is.
- the guest: the settings join the selection, `subport=libssh2 openssl.branch=4`, on every port(1) line that opens the target (clean, lint, fetch, checksum, install, test, info), and the options of every `mportopen` of it (`declares_tests`, `checkout`, `work_dir`, `portgroups`, `path_dependencies`, `links`). The dependencies it installs first are read by opening the target under its settings too (`mportopen` with the options, and `mportinfo`'s `depends_build`, `depends_lib`, `depends_run` and `depends_test`, the port of each entry its last colon field, as `depof:` resolves `path:` and `bin:` entries), since `port echo depof:` evaluates the port with no option of the person's and would list openssl3; implementation confirms that reading against `port echo depof:libssh2` on one port before relying on it. The guest's `links` then says what the canary linked, "iperf3 links openssl4's libraries, declared in depends_lib".
- evidence and the pull request: extras, as `--also`'s are, shown where they ran, required nowhere, never evidence for the changed ports' own rows. Tested on names each by its ID, and the description gains one sentence where any build had settings: "Built against this branch with openssl.branch=4: libssh2, socat, iperf3 and sslscan (their Portfiles are unchanged)". A failure is accepted by its name, `submit --accept 'libssh2 openssl.branch=4'`; `--accept libssh2` keeps meaning the default build; status's ExtraFailed row names it the same way. The answer to the note's question: the results count as what they are, builds of unchanged ports under a setting beside the branch's own evidence; they never stand in for a changed port's build.
- providers: Tart, local and a command provider carry `settings` per target in the guest's request (the guest's `Target` gains `settings`; the command provider's request file the same field, said in its docs). GitHub: "Won't build … on github", as for every `--also` port.
- the plan and its JSON: the "Also" line names the builds by ID, "Also libssh2 openssl.branch=4, socat openssl.branch=4"; `--plan -v`'s evaluation block is each under its setting; `--json`'s plan gains `settings`, the options as given, beside `also`, and target IDs carry them. `--baseline` of such a check builds master's port under the same settings where it failed, as it keeps a variant build's variants (`alsoVariants`).
- the syntax: `name=value`, the name letters, digits, dots and underscores. Refused: no `=` ("--set openssl.branch: name=value, as --set openssl.branch=4"), an empty value ("--set openssl.branch=: give its value"), a name given twice ("--set openssl.branch is given twice"). A value with spaces is the shell's to quote, `--set 'python.versions=312 313'`.
- out of the design: a setting on a changed port (write the line; the pull request shows it), settings reaching dependencies (MacPorts propagates a user option to the dependencies it installs in one `port install`, but dockhand installs them first, as the tree has them, so a canary's mixed linkage is a finding, not a hidden rebuild), and a config default.
- implementation notes, architecture's: `check`'s `--set` as a `StringArray`, parsed to `map[string]string` with the refusals; `engine.CheckRequest.Settings` → `PlanRequest.Settings`; where the Also candidates are made, each gets `Target.Settings`; `--set` with no `--also` refused there. `checks.PortReader.Ports` takes settings; the eval session passes them in `mportopen`'s options after `subport`; the evaluator reports each option asked for that the port doesn't declare (`info commands`), which planning turns into the refusal. `model.Target.Settings map[string]string` (`settings,omitempty`), `ID()` appending `name=value` words in name order after the variant spec; `model.Plan.Settings` as given; `TargetInputs.Settings`; additive JSON, no schema bump; `CompareTargets` orders by settings after variants. guest/follow.go's `Target` gains `Settings`; guest.tcl takes them into the selection and every `mportopen`'s options, and a `dependencies_under` read replaces `depof:` for a target with settings (or for every target, one read: implementation's call, with the comparison above). `view.WritePlan` already prints IDs; engine/body.go adds the sentence; `AcceptName` already keys by ID; branchstate unchanged.
