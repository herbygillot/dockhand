## Amendment of 2026-11-12: `--set` applies to every port a check builds

The person's direction, 2026-11-12: `--set` should reach every port the check looks at, the checked ports included; and because a setting, like a variant, changes how a build behaves, every comparison the engine makes between builds must take it into account. A person using it on purpose to answer their own question is fine. Architecture's draft against main 2cdaf571, reviewed once by Codex, every finding checked in the code and taken; adopted by the person at 17:26Z.

### The one idea

A build is a port in a configuration. Today the configuration is the variant spec. It becomes the variant spec plus the settings. Two builds are the same build only when both agree.

There is one difference from a variant, and the rules below follow from it. A variant is a configuration the Portfile offers: anyone can install it from the submitted tree. A setting is a configuration the tree does not have. So a variant build can be a port's coverage; a build under a setting never is.

### Rules

1. **Scope.** A setting applies to every target of the check that declares the option: changed, `--only`, `--also`. `--set` no longer needs `--also`. A target that does not declare it is built as it would be without `--set`, and the plan says so by name. The check is refused only when no target declares it.
2. **It follows the dependency edges inside the check.** A target that builds on a target under a setting (the plan's own `Dependencies`, transitively) is built under that setting too, whether or not it declares the option, and its ID says so. Otherwise a plain-named build would have been made against a non-plain dependency, and nothing downstream could tell.
2a. **A build records what it was built against.** The ID is not enough: the same `a mode=x` can be built against the tree's `b` in one check and against `b mode=x` in the next. A build's inputs record the build ID of every target of its check that it consumed. Reuse (`reuse.Carry`), a pending check standing in for a new request (`checks.PlanCovers`), and one check's result filling another's row on the same tree (`evidence.fill`) each require those to be equal. Where they cannot be established, the build is made again and the row is not filled.
2b. **One resolver for "which build of that port".** A dependency is named by port; the build that satisfies it in a check is found by one function, used by ordering, blocking, minmax's and `--only`'s keeping of prerequisites, and the moved-source comparisons. Where two builds of the port are in the check and nothing says which one the dependent consumes, the plan is refused, naming them. No site turns an ID back into a presumed port name or a port name into a presumed ID.
3. **One setting selection per port per check.** Under `--set`, a port's builds in that check are all under the setting (`--variants each` builds each variant under it). A check never builds the same port both plain and under a setting, since installed images and archives carry no setting in their names. This guards that one collision; it is not the proof that the rest is safe. Rules 2a, 2b and 6 are.
4. **Identity.** ID = name, variant spec, settings in name order: `thrift openssl.branch=4`. The encoding is injective: a value holding a space, a quote, a backslash or `=` is quoted, so `--set 'a=1 b=2'` and `--set a=1 --set b=2` never share an ID. `Target.Settings`; `TargetInputs.Settings`. A new `Target.Plain()` (no settings) is the only way code asks the question; every site that today asks `VariantSpec() == ""` to mean "the port's ordinary build" is reviewed against the list below.
5. **Never coverage.** A build under a setting is an extra wherever it appears: shown where it ran, required nowhere. A changed port is covered only by a build with no settings (a variant build without settings still covers, as today). The obligation is derived from the changed ports, not from the rows a check happened to run: today publication looks only at rows that failed, so a table of passed extras would publish. Every reader of coverage uses the one obligation: `branchstate.PublicationBlocks`, `Evidence.Unfinished`, `evidence.AskOf` (an execution plan that omitted nothing is not full coverage), status, ship's passing selection, and the description's ticks. A branch checked only under a setting says "checked under openssl.branch=4 only" and names the plain `dockhand check` next. `submit --no-check` and `--draft` stay what they are, and say unchecked.
6. **Reuse.** A recorded result is reused only for the same settings (`reuse.Carry` compares them as it compares variants). There are two archive channels. A planned target's own archive, exact to its configuration, is still used for its dependents. The pool of unplanned dependencies' archives is shared by a whole guest, not by target, so a check with any build under a setting neither offers nor harvests that pool at all. A carried result's lint is read under the build's configuration, or the recorded lint is kept.
7. **Acceptance.** A build under a setting is accepted by its full ID only, never by the port's bare name, even where it is the port's only build.
8. **Baseline.** A failed build under a setting is compared only with master's port under the same settings. Where master's tree refuses the value (its openssl PortGroup knows no branch 4), there is no baseline, and that is said. A plain master build is never its base. `atBase` is keyed by build ID, not port name.
9. **Findings drawn from a comparison.** Link and installed-file findings for a build under a setting are judged against declarations evaluated under the same settings. The comparison with master's published archive is skipped for it, with words.
10. **GitHub.** GitHub's workflow builds the tree as it is, so its verdict is never recorded for a build under a setting (a guard where the verdict is recorded, not only the words): "Won't build ... on github", and `--set` with only GitHub is refused as `--variants` is.
11. **Providers that keep state.** A provider whose prefix outlives the build (local) must not leave a setting-built port installed where a later plain build could take it. `--set` on such a provider is refused, with no exception: today's cleanup uninstalls a left image only when the port is next a target, not when it is next a dependency, and `--keep` leaves it active.
11a. **No edit from an experiment.** `tidy` never writes a dependency line from a link finding of a build under a setting; it says which build found it and why it is left. `dockhand shell --test` on a kept guest carries the settings.
12. **Pull request.** The variants item is never answered by a build under a setting. The description's sentence stays, naming each such build.
13. **Dependencies the guest installs from archives stay as the tree has them.** Unchanged from the adopted design.

### Faults that exist today for variant builds (confirmed by the review's probes; herbygillot/dockhand#235 and herbygillot/dockhand#236, fixed ahead of this)

- `atBase` by port name: a baseline failure of one variant build of a port licenses accepting another variant's failure that no baseline reproduced.
- Dependencies resolved by bare port name: `Needs.resolve` drops ordering and blocking where two variant builds of a port are in the check and no default build is; minmax's `span` does not keep a configured prerequisite; a dependent is reused across a change to its dependency's configuration, and across a moved tag of a configured dependency.
Rules 2a, 2b and 8 are the fixes' shape; they do not wait for `--set`.
