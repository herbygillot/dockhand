# The facts table's Xcode key: several toolchains per release, and which one a context models

A small core item for v0.9.0, [#86](https://github.com/herbygillot/dockhand/issues/86), placed at the person's approval of this design ("XCode facts table doc seems fine to me", 2026-11-05 16:56Z, in the architecture thread); designed 2026-11-05 by architecture after the person's "Plan it for 0.9.0. Go ahead with the GitHub Actions capture" (02:46Z). The issue and the roadmap's entry say where it stands; this file is the design. Read on main 543ad194c: internal/macos/facts.go (Facts, Lookup, sourceRank, Check, BuilderXcode), internal/macports/platform.go (Toolchain, xcodeToolchain, fill), tools/facts/generate.go (newest), docs/decisions.md decisions 9 to 13.

## Why now

The runner capture will give seven to nine Xcodes per release, `send-facts` rows will arrive with whatever Xcode a person has, and a release's Tart Xcode image can carry CI's pin beside the builder's Xcode. Today a row's identity is its release, architecture and profile (decision 12): tools/facts' `newest` keeps one row per that key and source, so two Xcodes from one runner image collapse to the newest harvest unless the source's `From` names the Xcode; and `Lookup` ranks the rows of a key by source kind alone (Tart, then buildbot), so it would pick among Xcodes by accident. The table's `Check` also refuses any source kind but tart and buildbot, which the capture's `runner` rows and send-facts' `sent` rows meet first.

Adjusted on placement, 2026-11-05, on main 065c61d2: #85 has landed the `runner` kind already (f640b873, 065c61d2). `Check` accepts it, `Lookup` ranks tart, runner, buildbot, and generation keeps a runner's row only where its Xcode and tools are both the builder's, reporting the rest. What this item adds is unchanged: the key's two versions, so generation keeps those other rows; `Lookup` preferring the builder's Xcode before the source; `LookupToolchain`; and `Check` accepting `sent`.

## What changes

1. **A row's identity gains its toolchain versions.** Generation keeps one row per release, architecture, profile, Xcode version, tools version and source kind, the newest harvest of each; `Source.From` names the image or run and the Xcode selected. Decision 12's key is extended, not reversed: a row is one toolchain of a release, and the table may hold several.

2. **`Lookup` picks by policy, then by source.** For a release, architecture and profile, the row whose Xcode is the builder's (`BuilderXcode`: the Xcode MacPorts' arm64 builder runs, which the release's Xcode image installs) comes first, so the modelled context agrees with the guest a check builds in; among rows with that Xcode, the richest source first: tart (dockhand's own images), runner, sent, buildbot. Where no row has the builder's Xcode, the rows rank as today, by source kind then date. A `LookupToolchain(darwin, arch, profile, xcode)` answers an explicit ask, for a later scenario (below), and `Check` accepts the two new kinds.

3. **`fill` borrows by the version a fact belongs to.** Today a buildbot row takes its clang and SDK lists only from a Tart row with the same Xcode and the same tools version (platform.go `fill`). Xcode's SDKs and its developer directory are Xcode's: borrow them from any row with the same Xcode. The tools' SDKs and clang are the Command Line Tools package's: borrow them from any row with the same tools version. On today's table this alone gives the Darwin 23 and 24 x86_64 rows their Xcode SDKs from the arm64 Tart rows (Xcode 15.4 and 16.4, whose tools versions differ), as Darwin 22 and 25 already get theirs (both versions match there). `fill` also borrows from Tart rows alone; with runner and sent rows in the table it borrows from any row, by the same versions. Evidence (#85's first runs, 2026-11-05): for the same Xcode and tools versions, the Intel runner's tools SDKs, Xcode SDKs and clang equal the arm64 runner's and the Tart image's, field for field, so borrowing by version is sound. An improvement, a fiftieth of a batch, which can land now, not #86 itself: it serves #17's third bullet (said there on 2026-11-05); it corrects architecture's modelled-context data capture note's effort A(a), which exists in this form already.

4. **Not now: CI's pin as a second scenario.** MacPorts' CI pins Xcode 16.2 on Darwin 23 and 26.4 on Darwin 25 where the builders run 15.4 and 26.6 (bootstrap.sh:110-112). A `pins` section in the table, harvested by tools/facts (the README says dockhand doesn't parse the script yet), and a context that models the pin, come when a consumer asks: a check `--build macports-ci` that wants its evaluation modelled as CI's would be that consumer. Until then the builder's Xcode is the one modelled context, as the checks' images are.

## Tests

Generation keeps two Xcodes of one key and the newest harvest of each; `Lookup` picks the builder's Xcode over a newer runner row and a Tart row over a runner row of the same Xcode; without the builder's Xcode it ranks as before; `fill` borrows Xcode SDKs by Xcode alone and tools SDKs by tools alone; `Check` accepts runner and sent and still refuses an unknown kind; the table check in CI (`macos.Table().Check()`) passes on the regenerated table.

## Size and docs

About a tenth of a batch for the key, the lookup and the kinds; the `fill` change a fiftieth. No usage docs change (nothing a person types); docs/decisions.md's decision 12 gains the two versions in its key, and tools/facts/README.md says what a row's identity is. The capture thread reports the Xcodes it captured; this lands before its regenerated table does, or with it.
