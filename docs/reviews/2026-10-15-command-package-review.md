# The command package: what moves out, and what bridges it to the engine

2026-10-15, from the "Architecture and code organization review" thread, at main 5eb101a (143 commits after the 2026-10-05 review). Every path is under internal/command unless prefixed. Line numbers are the checkout's at that commit.

## The short version

**It is large, and about a quarter of it is not its job.** The package is 10,900 production lines in 34 files, with 7,423 lines of tests. By role: text wording ≈3,000 (28%), JSON views ≈1,500 (14%), Cobra wiring ≈1,400, engine orchestration ≈1,350, terminal and process IO ≈975, judgments made from engine records ≈680, finding the branch a request is about ≈525, settings and composition ≈390, test seams ≈75. Wording, views, wiring and IO are what doc.go:4-7 says the package is for, and they are 6,900 lines. The rest is what doc.go:7-10 says belongs in the engine: "anything that chooses what is eligible, enforces a guardrail or a publication rule, runs several engine operations as one with its own rule for a failure partway". Seventy-one places in command do that today; the ten largest are about 1,100 lines.

**Don't split it into packages.** Every candidate (the JSON views, the terminal and prompting code, the launchd agent, one package per command) would have exactly one importer, which is this package. The roadmap already says so (docs/roadmap.md:197, "command, whose size is its job", and :701, "don't split packages by size alone"). The intra-package graph agrees: 165 of 870 possible file-to-file references exist, eight files hang off root.go alone, and the hubs are five small files (root, settings, json, work, exit). It is already a kernel with leaf files; a Go split would export the kernel to itself.

**Move the judgments to the engine, and give them the types they lack.** The planned work takes some: typed holds (v0.4.0 part 1), the check pipeline behind `ship` (part 2), the selector flags (part 2), `engine.Dependencies` (part 3), and the `branchstate` package for attention, `Next:`, serve's passing branches, submit's blocking checks and tidy's verdict (v0.5.0). It leaves the rest: one rule for what a check proves, written differently in status and submit; three copies of the branch-choice policy; the hold mark encoded as a `"! "` prefix and sliced back off; outdated's classification counted four times; the baseline comparison, which no engine type owns; active-run replacement and leader election decided in two commands; capture mode and the check defaults merged in four; a tidy plan mutated by string match; the config defaults retyped as literals; exit codes chosen at thirteen sites.

**The concepts exist in embryo; they are command-private and untyped where the engine needs them.** `Streams` is the context, `settings` the composition root, `branchFlags` the selector, `ExitError` the outcome, `ask`/`confirm`/`yesTo` the consent, `gatherer`/`emit` the result record, `attention{mark, …}` the readiness row. Six of them should become shared, typed values: a selector the engine resolves, verdicts (check standing, baseline, outdated summary) the engine computes, exit constants now and a refusal type later, one consent value, the host half of the command context, and per-command records with typed kinds rendered once as text and once as JSON. None needs a new package or a new dependency.

**One sequencing change to the roadmap.** Build the check-standing verdict and the selector type before `ship` (v0.4.0 part 2), not in v0.5.0 with `branchstate`. `ship --passing` and the `-b`/`-p`/`--pr` rollout otherwise write a fourth copy of "what the latest check proves" and a fourth branch-choice policy against strings, which layer 1 then rewrites. The rest of readiness stays where the roadmap has it.

## 3. Don't split it

| Candidate package | Contract it would own | Importers | Verdict |
|---|---|---|---|
| JSON views (json.go, json_results.go; ≈1,435 lines, 67 types) | the `--json` vocabulary, version 1 | command only; the acceptance harness reads output, not types | fails: a split exports 67 types to one caller. ## 4. Concepts that bridge command to the rest

1. **A selector the engine resolves.** Exists as `branchFlags` (branchflags.go:17-72: `-b`, `--pr`, `-p`, else the checkout; the "not X, checked out here" notice at :68-70), `branchChoice` (author.go:33-43), and engine `Resolve`/`PullRequestBranch`/`PortBranches`/`Current`/`AmbiguousError`. Missing: one value, `engine.Selector{Branch, Port string; PR int; Policy Start|Ask|Refuse}`, resolved by one engine call that returns the branch, how it was named, and the candidates on ambiguity; command keeps only the terminal question over the candidates. Replaces `resolve`+`portBranch`, `chooseBranch`, `revbumpBranch`, create's switch (create.go:82-113) and four positional sites (status.go:86, work.go:340-344, verbs.go:294-298, review.go:454-458). About 60 lines in the engine, 120 fewer in command. The planned rollout adds the flags to more commands; defining the type first makes the rollout one change and gives `ship` its `-b`/`-p`/`--pr` for free.

2. **Verdicts, not strings.** Exists for the pieces (`Evidence.Missing/Failed/Tested`, `OutdatedReport.Unchecked`, `ActiveRunError`); missing for the composites in the table above: `CheckStanding` on `BranchStatus` and `SubmitPlan`, `BaselineComparison`, `OutdatedReport.Summary`, `Queue()` rows, `RunLogs.ForPort`. Each is a pure function of records the engine already returns, so each is a move, not a design; each lets the JSON carry a kind where it carries a sentence today. `CheckStanding` first, before `ship`.

3. **A typed outcome.** Exists as `ExitError{Code, Message}` (exit.go:8-16) with bare integers at thirteen sites and one site branching on the number (check.go:173). Now: named codes and `exitf` only, about twenty lines. With layer 1: `Refusal{Kind, Kept, Next}` rendered by one function, replacing the three "Kept:" composers (author.go:573-577, 613-616, 650-652) and the per-site refusal sentences; the exit code becomes a function of the kind.

4. **One consent value.** Exists as `streams.terminal()` consulted at seventeen decision sites, 27 prompt sites with five idioms, `unattended()` as a stream mutation (root.go:85-88), and `--yes` with four meanings across seven commands. Missing: `consent{mode: interactive|script|unattended; yes bool}` with one `decide(question, default)` that asks on a terminal, takes `--yes` in a script, and otherwise returns the one refusal ("nothing was <verb>: without a terminal, --yes <does what is shown>") with exit 1. About 60 lines, seventeen call sites. Do it before `ship`, which adds `--yes` and the `--passing` one-answer prompt, and because build profiles make "unattended" a mode the engine reads too (`build.unattended`), so the two layers should share the word.

5. **The host half of the command context.** Exists partially: `Streams` carries the mode, the status line and the reader; `settings` the file and the opened engine; `ctx` the reporter. X1 moves the twelve engine-facing seams into `engine.Dependencies`. The eighteen host-facing ones (clock, `open`, `osascript`, `launchctl`, the editor, `LookPath`, the executable path, the credential store) belong in a `host` value built in `Run` and carried beside `settings`; `serveOptions` (serve.go:149-180) takes its clocks from it. About 150 lines plus the test harness. It is what lets the tests run in parallel; X1 alone does not.

6. **Per-command records with typed kinds, rendered twice.** Herby's rule, one shape per command, is exactly a record built once from the engine's results and rendered as text and as JSON. Today the text path reads engine types directly and the JSON path recomputes: "skipped" twice with different rules (outdated.go:351-389 vs json_results.go:664-679), `Stopped` judged twice per run (queue.go:57,105), the serve line as words beside the serve fields (status.go:131-132), attention kinds from glyphs. Cheap per command as each file is opened by the renames; the typed kinds it needs are three PR observation enums in `model` (branch.go:85-97; eight sites), an `UpstreamChange` severity beside `Hold`, and `attention.Kind`.

Rejected: a workflow or pipeline type (the planned `ship` on `prepareOne` is the right shape: one engine function per unattended question, replaced by readiness later); a command-registry or plugin shape for the verbs (root.go's seven groups are the registry); a shared branch shape across commands (Herby's rule stands; the per-command record is its implementation, not its opposite).

## 5. Where it lands on the roadmap

- **v0.4.0 part 1, hygiene (all S):** the wording folds of 2b; the editor, TTY and refusal duplicates; `github.PullRequestURL` at understand.go:377; exit constants; the three PR observation enums; `CleanStep.Kind` exported; `config.Defaults()`; `TidyPlan.SetSubject`; `tart.Status.HasHostImage`; `Submitted.Edited` from `ApplySubmit`. These ride beside the hygiene items already listed there (C4c, C4d, X4, X5, A-H1, A-H2).
- **v0.4.0 part 2, before `ship` (the counter-proposal):** `engine.Selector` (concept 1); `CheckStanding` (concept 2's first verdict); the consent value (concept 4); `CaptureAuto`, `CheckDefaults` and `Enqueue(Replace)` (rows 7 and 9), which are the ingredients the plan's "one engine path" needs anyway. Together about 300 lines moved and 100 new; `ship` is then wiring, one engine call and rendering.
- **v0.4.0 part 2, with the renames:** the JSON one-layer work and the per-command records (concept 6), since those files are open then.
- **v0.4.0 part 3, with X1:** the host half of the context (concept 5) and H9's fixtures; `t.Parallel` across the package follows.
- **v0.5.0, `branchstate`:** rows 1 and the rest of 2 as planned; `BaselineComparison`, `OutdatedReport.Summary`, `Queue()` and `RunLogs.ForPort` as its siblings; `Refusal` with the `Next:` contract.

After the planned deletions (≈1,000 lines), the judgments moved (≈1,100), the wording folds (≈150) and the seams (≈100), command is about 8,500 lines of wording, wiring, views and IO. That is its job, and no package boundary needs to move for it.

## Method and verification

Three review passes ran in parallel over the checkout: inventory and structure (per-file roles, the helper graph, the engine surface, seams, the deletion estimate); domain logic in command (71 sites, grouped by the record they interpret, with duplication map); views, wording, IO, composition and concepts. My own go/types cross-reference measured the function count, the engine surface and the intra-package graph. Every row in section 2a and every file:line this page cites in its own voice was checked by reading the cited lines at 5eb101a; one claim from the views pass (that submit.go:281-283 mutates an exit message) did not hold up on reading and is left out. The role line counts in section 1 are the inventory pass's by declaration span, not re-counted by me; my coarser dominant-signal count puts the same files at the top in the same order. No file under the checkout was changed.
