# Dockhand language review: `032836b8`

This is an editorial handoff for a follow-up implementation, not a patch. It reviews the CLI help, status and progress output, refusals, macOS notifications, and text Dockhand generates for GitHub. The locations and existing text refer to commit `032836b8cc194e6bf617138ef9b4d4fa6330bebf`. Line numbers are starting points; find the enclosing branch and its callers before changing copy. `%s`, `%d`, and similar markers below represent the existing values, in the order shown unless otherwise noted. Replacements are proposed wording, not an instruction to change behavior.

The review concentrates on high-visibility and consequential paths, with examples across the product. It is **not an exhaustive inventory of every string**: errors also propagate from providers and lower-level packages, and runtime output can include messages from Git, MacPorts, and GitHub. After the listed changes, search for the recurring patterns below throughout non-test source. Do not mechanically rewrite every occurrence: some are technical identifiers, quoted upstream text, or intentionally compact table cells.

## Editorial direction

Dockhand has useful, unusually specific information, but too many sentences make the reader reconstruct the subject, object, and action. Phrases such as “held for a look,” “what it read,” “as it stands,” and “what needs you” recur across unrelated screens. Prefer direct subjects and ordinary verbs: “review,” “check,” “build,” “failed,” “queued,” “submit,” “changed,” and “could not read.” Name the branch, check, file, or environment again when a pronoun could refer to several things. Short fragments are fine in tables when the column provides the context.

- Lead with the outcome, then the reason, then an actionable next step. Keep paths, check IDs, commands, and links close to the facts they explain.
- Preserve the difference between **not checked**, **not built**, **failed**, **passed with advisory test failures**, **stopped**, **stale**, and **unknown**. “Passed” must not imply that binary functionality or variants were tested by a person.
- Say “review required” or “needs review” for holds; explain whether the hold affects unattended operation, submission, or both. An automatic hold does not necessarily block a human from proceeding.
- Say “unattended” or “without confirmation” instead of “where nobody looks.” Describe what `--yes` and noninteractive mode actually do in each command; do not imply that all `--yes` flags behave alike.
- Use “check” for the Dockhand operation and “build” for its build work. A check can cover multiple ports and environments; a test phase is only one part of it. Say “base” or “master” precisely, rather than treating every old result as the same thing.
- Use “Dockhand” in prose and `dockhand` in commands, config keys, generated identifiers, and product signatures. Keep GitHub, MacPorts, macOS, Tart, Portfile, worktree, and Git capitalization consistent. The project currently uses `master`; don't rename a Git ref as an editorial change.
- Use sentence case and punctuation for sentences; compact labels and table fragments need not end in periods. Keep the existing marks, grouping, exit codes, streams, prompts, and output structure unless an improvement requires an explicit behavior change.
- Technical caution and destructive effects belong in the copy. Never simplify away the worktree/file deletion warning, lease condition on a push, unknown/partial results, local-root execution, or the limits of a test rerun.
