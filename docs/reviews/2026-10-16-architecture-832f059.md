# Dockhand architecture review

Reviewed 2026-10-16. Snapshot: [`832f059ed61355f39a5755be12203d1810fff60a`](https://github.com/herbygillot/dockhand/commit/832f059ed61355f39a5755be12203d1810fff60a).

The main architectural pressure is concentrated in the application layer. Dockhand has several useful, well-separated domain and infrastructure packages, but `engine` and `command` still share ownership of workflows and policy. Some repeated operations also lack a common semantic contract: deciding whether a source is unchanged, validating a corrective edit, deciding whether an existing check satisfies a request, and reporting a build together with its observed inputs. These are better refactoring targets than reducing package sizes indiscriminately.

The first changes I would make are to unify ship-stage decisions, complete evaluated source identity, and give corrective edits one fidelity contract. Each has a concrete discrepancy in the reviewed code. After that, extract the concrete MacPorts query adapter from `engine` and consolidate application dependency assembly. This would reduce the two largest packages while making their responsibilities clearer.

## Scope and method

This assessment uses a separately materialized snapshot of HEAD, not the live working tree. All source references below point to that commit. The review covered first-party production Go packages, embedded Tcl, SQLite schema, and the maintenance programs in `tools/facts` and `tools/survey`. Existing documentation, `_test.go` files, test fixtures, test-support packages, the acceptance harness, and vendored dependencies were excluded. Repository instructions were read for the review workflow; existing architecture reviews were not consulted.

The assessment combined a package/import inventory with source inspection and traced call paths across authoring, discovery, assessment, planning, execution, publication, persistence, and provisioning. No tests, builds, live Portfile evaluations, network operations, or VM runs were used to substantiate findings. A traced discrepancy establishes what the source permits; illustrative scenarios below were not executed. This is an architecture review, not an exhaustive correctness or security audit.

Inventory, excluding package-only `doc.go` files: 404 Go files, 89,137 physical Go lines, and 78 package directories. Physical lines include comments and blanks, and platform-specific files are counted together. There are also 2,696 Tcl lines and 581 schema SQL lines. Counts are descriptive, not quality scores.

That makes it a plausible application façade, but too much concrete implementation is currently trapped behind that façade.

## Existing boundaries to preserve

- **The domain vocabulary is independent of infrastructure.** `model` has no first-party package imports. Immutable revisions, source trees, plans, observed build inputs, and model validation provide useful anchors for further extraction. `Revision.SameTree` already distinguishes commit provenance from file/base equivalence ([internal/model/revision.go:64](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/model/revision.go#L64)).
- **Parsing, comparison, and MacPorts policy are substantially separated.** `project` reads source facts, `sourcecompare` identifies changes, and `macports/assess` applies policy. Keep that direction. A large ecosystem parser is not automatically a monolithic package.
- **Planning and history have meaningful seams.** `planning.Decide` is a data-oriented decision boundary ([internal/planning/planning.go:151](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/planning/planning.go#L151)). `history.Transitions` owns locking and recovery around Git/store transitions ([internal/history/history.go:30](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/history/history.go#L30)). Preserve those responsibilities when shrinking engine.
- **Build providers depend on a neutral contract.** `buildenv.Provider` and its optional capabilities avoid a dependency on `engine` ([internal/buildenv/buildenv.go:18](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/buildenv/buildenv.go#L18)). Capability-specific interfaces are useful; expanding every provider into one comprehensive interface would be a regression.
- **Evidence and reuse answer different questions.** Evidence judges what checks establish; reuse must establish equivalent build inputs across checks. Keep these packages distinct, even where they share small rules.
- **Infrastructure already has useful subdivisions.** `credential`/`keychain`, `store`/`sqlite`, `coord`, and Tart's `host`, `guestssh`, and `provision` packages have recognizable ownership. SQLite's size does not justify separate databases or a generic repository framework.

## Findings

Priority describes refactoring urgency. “High” findings have a traced behavioral or invariant gap; “medium” findings identify concrete coupling or incomplete contracts, sometimes with a conditional failure scenario. Proposed package and type names are illustrative.

### 1. High — Ship policy has two owners, and the implementations have diverged

The CLI implements the sequence in `shipOne`, `queueHead`, and submission helpers ([internal/command/ship.go:310](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/ship.go#L310), [internal/command/ship.go:425](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/ship.go#L425), [internal/command/submit.go:229](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/submit.go#L229)). The background preparation path uses a separate `Engine.Ship` ([internal/engine/ship.go:75](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/ship.go#L75)), reached through `PrepareOutdated` ([internal/engine/outdated.go:393](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/outdated.go#L393)). Both decide how an update proceeds through editing, committing, and checking.

Two discrepancies make this more than duplicated plumbing:

1. **Suppressing prompts becomes approval of hand edits in CLI ship.** `shipOne` unconditionally sets `linked.yes = true` ([internal/command/ship.go:312](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/ship.go#L312)), including when its caller classified execution as unattended. That flag reaches `tidyBranch` and then `decideTidy` ([internal/command/author.go:302](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/author.go#L302)). `decideTidy` translates it into `AnsweredYes` ([internal/command/review.go:151](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/review.go#L151)), and `TidyPlan.AppliesUnasked` permits a nonblocking plan without requiring `Unambiguous()` for that answer ([internal/engine/tidy.go:136](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/tidy.go#L136)). Thus even a nonterminal ship invocation without an explicit `--yes` can receive the stronger approval internally. The background path retains `AnsweredNobody` and holds a plan that requires review ([internal/engine/ship.go:61](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/ship.go#L61)). This also conflicts with the unattended hand-edit hold described by the active command's help text ([internal/command/ship.go:43](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/ship.go#L43)).
2. **Background ship misses the early duplicate-PR gate.** `Engine.Ship` creates an `UpdateRequest` without forwarding `Unattended` ([internal/engine/ship.go:82](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/ship.go#L82)). The gate for an existing remote PR, or inability to look for one, is inside `if request.Unattended` ([internal/engine/update.go:402](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/update.go#L402)). The background planning path checks local branches, which is a different question ([internal/engine/outdated.go:347](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/outdated.go#L347)). The consequence established here is unnecessary preparation and potentially expensive checking before a later hold. Final submission still evaluates concerns; this is not evidence of an unsafe publication bypass.

There is also no single interpretation of decision provenance: CLI `shipAll` treats everything except `AnsweredAsked` as unattended ([internal/command/ship.go:261](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/ship.go#L261)); `ShipOptions.Unattended` treats only `AnsweredNobody` that way ([internal/engine/ship.go:48](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/ship.go#L48)). `model.Answered` already supplies useful vocabulary, but callers reinterpret or overwrite it.

**Recommendation:** Give one application service ownership of ship-stage transitions and gates, shared by CLI and serve. Preserve decision provenance at each stage; distinguish a request to proceed without prompts from approval of a particular derived plan. Keep terminal interaction and rendering in command. Start by centralizing the edit/tidy gates and forwarding context consistently, then consolidate queue/resume and submission completion.

Preserve two valuable properties during that work: the CLI queues the batch before following checks, and submission is bound to the reviewed commit. The latter includes replanning after checking and refusing a changed commit ([internal/command/submit.go:247](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/submit.go#L247), [internal/command/submit.go:264](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/submit.go#L264)), plus the engine's explicit-head check and conditional push ([internal/engine/submit.go:749](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/submit.go#L749)). A shared workflow must retain those guarantees, not merely call the shorter implementation.

### 2. High — Evaluated source identity is incomplete and reused for different guarantees

`ReleaseStateOf` records sites, extraction directory, epoch/version/revision, Git ref, distfiles, and checksums, but omits `git.url` and fetch kind ([internal/macports/scope.go:49](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/scope.go#L49), [internal/macports/release_scope.go:44](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/release_scope.go#L44)). `SameSource` compares this state, ignoring revision, plus the patchfile list ([internal/macports/scope.go:59](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/scope.go#L59)).

For two otherwise equal evaluated ports, changing only `git.url` therefore leaves `SameSource` true. `assessPort` takes that result before its Git-source comparison branch and reports that there is nothing upstream to compare ([internal/engine/assessment.go:267](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/assessment.go#L267)). This can omit assessment of a different repository at the same version/ref. Release-scope protection uses the same incomplete state for protected siblings ([internal/macports/scope.go:40](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/scope.go#L40)), so that check also cannot distinguish this change.

The code already has several related interpretations: `PortInfo.GitSource`, GitHub tag interpretation, discovery's `portsource`, resolved `model.GitSource`, and release-scope state. Their purposes differ, but the overlapping source fields are manually reconstructed.

**Recommendation:** Establish one checked representation of an *evaluated fetch source*: fetch kind, repository URL/ref where applicable, archive declarations, and relevant extraction/patch context. Use it for source equality and protected-sibling validation. Preserve invalid/unknown values as such; absence of a field must not silently establish equality. Distinguish the declared source from a later resolution to a commit or archive digest.

Keep discovery conventions separate: the release catalog used to find a version is not necessarily the source a build actually fetches. Also keep this concept distinct from `model.Source`, which identifies the MacPorts ports-tree snapshot. Repair the missing fields and invalidate affected cached assessments/scope records before undertaking wider package moves.

### 3. High — Corrective edits implement different fidelity protocols

After preparing a version or dependency edit, portedit may raise a Go toolchain minimum, remove a stealth-update directory setting, or drop patches already merged upstream. Each performs a similar operation: change text, evaluate it, check that only permitted semantics changed, and publish the new prepared result.

The implementations differ materially:

- Toolchain correction compares the previous family against the candidate with an explicit allowed option change and records a fidelity report ([internal/macports/portedit/go_toolchain.go:75](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/go_toolchain.go#L75)).
- Stealth-directory removal uses a specialized comparison report and records it ([internal/macports/portedit/stealth.go:152](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/stealth.go#L152)).
- Merged-patch removal checks only the selected port's patch list, version, and revision, then directly replaces `Result.Prepared` ([internal/macports/portedit/patches.go:104](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/patches.go#L104), [internal/macports/portedit/patches.go:116](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/patches.go#L116), [internal/macports/portedit/patches.go:123](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/patches.go#L123)). It does not establish equality of other metadata or siblings, or append the corresponding fidelity report.

Patch removal happens after primary preparation/fidelity ([internal/macports/portedit/version.go:123](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/version.go#L123), [internal/macports/portedit/dependencies.go:474](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/dependencies.go#L474)). The final Git-tree evaluation verifies equivalence with the *already replaced* `Prepared` value ([internal/editprep/editprep.go:246](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/editprep/editprep.go#L246)). It verifies materialization faithfully, but cannot supply the missing before/after semantic check. For example, a Portfile whose dependency declarations depend on the patch list could change dependencies when a patch is removed and still pass the local patch/version/revision checks. That scenario was not executed, but the missing comparison is explicit.

**Recommendation:** Add a small validated-correction operation inside portedit. It should own the previous prepared snapshot, candidate evaluation, complete family/set comparison, explicit allowed delta, any required scope rebinding, and publication of files/snapshot/report together. A correction should not be able to replace `Prepared` independently of its evidence. Migrate patch removal first, then reuse the operation for toolchain and stealth corrections. Reuse the existing `fidelity` implementation rather than inventing another comparison engine.

This is a stronger reason to introduce a shared concept than portedit's line count: the same invariant is already being enforced differently.

### 4. Medium — “Same revision” is used where “satisfies this check request” is needed

`checkHead` skips a check based on branch standing before considering the requested location or test policy ([internal/command/ship.go:412](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/ship.go#L412)). When queueing meets an active run, ship follows it whenever `ActiveRunError.SameRevision` is true ([internal/command/ship.go:440](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/ship.go#L440)). The runner defines that flag as revision-ID equality ([internal/engine/runner.go:112](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/runner.go#L112)).

A check's source identity does not identify its verification requirements. More generally, two plans for the same revision can request different providers/releases, variants, extra targets, or test policies. For example, an active advisory-tests check can be followed in response to a ship request requiring tests. The passed-check shortcut likewise does not compare explicit `--on`, `--build`, or `--tests` with what passed. This observation concerns Dockhand's production test-policy feature; the repository's tests were not reviewed.

**Recommendation:** Introduce a small check-intent/satisfaction operation. Bind the requested source, coverage, environments, and test semantics, then decide whether a passed or active check covers it. Existing richer evidence may satisfy a narrower request; byte-for-byte plan equality is unnecessarily strict. Reuse `TestPolicy.Stands` where judging completed results ([internal/model/plan.go:117](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/model/plan.go#L117)), while treating compatibility of an unfinished plan separately. Make skip/follow/queue/replace decisions in the application layer and let command render the explanation.

### 5. Medium — Engine contains concrete source-query infrastructure and discovers its capabilities implicitly

`evaluatedPorts` lives in engine and handles workspace acquisition, target resolution, native/modeled evaluation, indexing, and related queries ([internal/engine/ports.go:34](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/ports.go#L34)). Its archive planning/fetching implementation is in another engine file ([internal/engine/archivediff.go:200](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/archivediff.go#L200)). This is largely a concrete adapter over `macports/selection`, `workspace`, the evaluator, and the port index, rather than application workflow.

Consumers then discover capabilities from the dynamic type of `PortReader`: family reading ([internal/engine/changes.go:61](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/changes.go#L61)), dependency graphs ([internal/engine/plan.go:573](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/plan.go#L573)), archive planning ([internal/engine/assessment.go:130](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/assessment.go#L130)), and archive fetching ([internal/engine/archivediff.go:189](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/archivediff.go#L189)), among others. Missing capabilities can mean retaining text-only scope, omitting auxiliary information, falling back to direct dependency ordering, or returning an error. A replacement that satisfies `PortReader` does not fully describe which behavior it provides.

**Recommendation:** Move the concrete adapter into a MacPorts source-query package below engine. Keep small consumer-owned interfaces, but assemble the capabilities explicitly and expose consequential degraded behavior. Move neutral result types such as `FetchedArchive` and `Dependent` out of engine as necessary to avoid the extracted adapter importing its consumer. Do not combine all capabilities into one mandatory interface.

This is the clearest first package extraction from engine. Next candidates are check execution/recording and serve supervision, each with explicit dependencies. `Engine` can remain the public application façade. Splitting its files into sibling packages that all receive `*Engine` would retain the existing coupling and likely add cycles.

There are also smaller misplaced responsibilities: `throughUnchanged` mixes graph acquisition with graph-closure planning ([internal/engine/plan.go:572](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/plan.go#L572)); its pure traversal belongs with planning decisions. `VariantsFlag` handles command syntax ([internal/engine/plan.go:543](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/plan.go#L543)). Semantic comparison predicates such as `SourceUnchanged` live alongside rendering in `words.go` ([internal/engine/words.go:364](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/words.go#L364)). Separate those predicates from presentation before extracting shared report rendering.

### 6. Medium — Persisted revision analysis lacks an explicit evaluation-context identity

Change records and upstream assessments correctly bind their results to a ports-tree/base and policy version. Their lookup/reuse logic is nevertheless duplicated, and the evaluation context is not part of that identity.

`revisionChanges` filters by branch/tree/base and `ChangePolicy`, retaining successful records ([internal/engine/changes.go:33](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/changes.go#L33), [internal/engine/changes.go:77](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/changes.go#L77)). `ChangeRecord` stores a platform but no evaluator-runtime fingerprint ([internal/model/change.go:16](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/model/change.go#L16)). `revisionAssessments` similarly filters by tree/base and assessment policy ([internal/engine/assessment.go:48](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/assessment.go#L48)). Assessment records have no evaluation-context field ([internal/model/assessment.go:11](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/model/assessment.go#L11)). SQL upserts key these records by revision and subject, without context ([internal/store/sqlite/history.go:221](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/store/sqlite/history.go#L221), [internal/store/sqlite/history.go:235](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/store/sqlite/history.go#L235)).

The evaluator already distinguishes a session's runtime from an observation's platform: snapshots carry `Runtime` and `Platform` ([internal/macports/metadata.go:38](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/metadata.go#L38)), and runtime includes host/model platform, MacPorts Base version, and Tcl version ([internal/macports/runtime.go:10](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/runtime.go#L10)). Those inputs can affect evaluated dependencies and sources. Reopening the same repository/database after a host/toolchain/MacPorts change has no corresponding cache-key distinction. The unseen-text safeguards are useful, but do not establish that two evaluation contexts are equivalent.

**Recommendation:** Make the context under which derived analysis stands explicit. Define the relevant evaluation identity from modeled/native context, tools, evaluator/Base semantics, and policy; avoid pretending a platform alone captures all host inputs. Choose deliberately whether results are reusable across contexts, kept side by side, or conservatively invalidated. Surface unknown context as limited provenance rather than treating it as current.

A revision-analysis service could then own common revision binding, cache acceptance, collection-versus-read-only behavior, and freshness explanations for both change records and assessments. Keep their payloads and retry rules distinct: successful change records and transient assessment failures currently have intentionally different reuse behavior. Do not force them into a generic cache abstraction merely because their storage keys resemble one another.

### 7. Medium — Project facts are interpreted independently by creation and comparison

Creation decides Cargo binaries in `portcreate.Binaries`. With a `[package]` and no explicit `[[bin]]`, it returns the package name ([internal/macports/portcreate/manifest.go:48](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portcreate/manifest.go#L48)). Source comparison contains a second implementation that also consults captured source-layout information through `Reading.CargoProgram` ([internal/sourcecompare/compare.go:630](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/sourcecompare/compare.go#L630), [internal/sourcecompare/compare.go:646](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/sourcecompare/compare.go#L646)). When program-directory information is present, it can exclude library-only members, unlike creation. `CargoProgram` also treats nil information as a program for compatibility ([internal/project/read.go:102](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/project/read.go#L102)), so comparison does not consistently prove that an executable exists either.

For a library-only member of a workspace with captured program-directory information, these consumers can therefore reach different conclusions about whether it builds an executable. Creation passes the inferred binaries into its Portfile specification ([internal/engine/create.go:190](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/create.go#L190)) and generates installation commands from them ([internal/macports/portcreate/portcreate.go:373](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portcreate/portcreate.go#L373)). The practical failure is a generated install command for a program that was never established to exist.

Related build recognition and manifest metadata are divided between `project` and `portcreate`. This is an ownership issue: project facts should be interpreted once, while MacPorts policy should remain in the MacPorts-specific package.

**Recommendation:** Put project target discovery and declared metadata in `project`, returning evidence and an explicit unknown result when the captured files are insufficient. Both creation and comparison should consume those facts. Keep category/PortGroup selection, MacPorts naming, and Portfile rendering in `portcreate`. Start with Cargo targets; there is no demonstrated need for an ecosystem plugin framework.

### 8. Medium — Read-only version discovery depends on the editor's full preparation model

Outdated discovery constructs a `portedit.Service` solely for probing ([internal/outdated/outdated.go:88](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/outdated/outdated.go#L88)). It quiets editor-specific progress because loading a port can announce that it is “editing” during a read-only lookup ([internal/outdated/outdated.go:192](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/outdated/outdated.go#L192)). The probe retains the full service and edit request ([internal/macports/portedit/probe.go:29](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/probe.go#L29)), and candidate version evaluation calls the editor's version transformation with fidelity checking disabled ([internal/macports/portedit/probe.go:88](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/probe.go#L88)).

The shared mechanics are legitimate: bind a source/target, resolve a stub, open an interpreter session, find version carriers, and evaluate candidate values. Their placement makes discovery depend on preparation policy and its messaging, with a boolean selecting a different semantic mode.

**Recommendation:** Extract source-bound evaluation/session and version-mapping mechanics below discovery and editing. Preserve `upstream.VersionProbe`, which is already a good consumer-owned seam ([internal/upstream/bound.go:12](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/upstream/bound.go#L12)). Keep final edit orchestration, authorization, revision resetting, and strict fidelity in portedit; temporary candidate rewrites used to evaluate a version can belong with the probing mechanics. The existing quieting is evidence that a lower-level operation is needed, rather than a reason to add more output-suppression branches.

### 9. Medium — Source-file reading is attached to dependency generation

The Go toolchain check has separate Git and archive branches that both read and parse `go.mod` ([internal/macports/portedit/go_toolchain.go:109](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/go_toolchain.go#L109)). The archive branch imports `depblock` for its `Manifest` helper ([internal/macports/portedit/go_toolchain.go:132](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/portedit/go_toolchain.go#L132)). That helper performs bounded archive member reading and source-root selection ([internal/macports/depblock/archive.go:17](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/depblock/archive.go#L17)), which is useful beyond dependency-block generation. The forge implementation returns the same missing-manifest sentinel ([internal/upstream/manifest.go:20](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/upstream/manifest.go#L20)).

**Recommendation:** Start with a narrow source-files capability bound to a known source/root/release, with explicit size limits and missing/ambiguous outcomes. Move archive member selection below `depblock`; adapt the existing forge reader to the same consumer need. Let project readers and toolchain checks use it without importing the dependency generator. MacPorts-specific extraction-root translation can remain in a MacPorts adapter over a generic archive reader.

Keep the intentionally different trust policies: dependency generation's strict source confirmation and comparison's best-effort reading should not become interchangeable. A file-access bridge should unify acquisition mechanics, not erase those policies or eagerly materialize whole projects.

### 10. Medium — Build reporting relies on an order-sensitive callback protocol

`buildenv.Build` requires providers to report `Consumed` and `Fetched` before `Record`, then retain archives afterward ([internal/buildenv/buildenv.go:128](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/buildenv/buildenv.go#L128)). The engine buffers the observations in maps until recording ([internal/engine/runner.go:759](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/runner.go#L759), [internal/engine/runner.go:855](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/runner.go#L855)). The durable recording itself is transactional, which is good; the weak point is the implicit protocol before that transaction.

Each provider converts similar target/result/input concepts. Tart performs target membership checks, outcome normalization, log retrieval, fetched-source reporting, active-input reporting, and recording in its adapter ([internal/buildenv/tart/provider.go:1058](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/buildenv/tart/provider.go#L1058)). Script independently converts and validates its results ([internal/buildenv/script/script.go:238](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/buildenv/script/script.go#L238)). Validation is distributed differently between these adapters and later model/store validation.

**Recommendation:** Pass one target-report value containing the result plus optional fetched-commit and observed-input evidence. Preserve the difference between unknown inputs and known empty inputs. Normalize/validate the host-side semantic report once, and keep test-policy and expected-source judgments in the engine's recorder. Keep provider wire DTOs and trust/transport handling distinct, with archive transfer as a separate post-record operation. This can simplify the recorder without standardizing all providers on one wire format.

No corruption was demonstrated from the current callback ordering. This is a contract improvement that becomes more valuable as providers acquire capabilities.

### 11. Medium — GitHub state has multiple independently assembled lifetimes

`e.github()` constructs a fresh `github.SystemClient(keychain.Store{})` on each call ([internal/engine/preparer.go:47](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/preparer.go#L47)). Publication, discovery, project inspection, and source assessment obtain these through separate factories. Actions receives another client from command composition ([internal/command/settings.go:130](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/settings.go#L130)).

The shared implementation does not imply shared state. SDK/auth caches live on each client, and each SDK transport constructs its own primary/secondary limit tracker ([internal/github/client.go:149](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/github/client.go#L149), [internal/github/ratelimit.go:80](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/github/ratelimit.go#L80)). The process-wide request pacer and spend metrics *are* global ([internal/github/pace.go:21](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/github/pace.go#L21)); rate limiting is therefore partly shared, rather than wholly fragmented. Still, one client's observed backoff is not the other client's state.

There is a conditional credential consequence as well: a successfully renewed token that cannot be persisted is retained in the renewing client's pending-login memory ([internal/github/login.go:190](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/github/login.go#L190)). A separately constructed client cannot see that fallback and can read the older saved token. The renewal lock serializes file operations but cannot share unpersisted memory. This failure scenario was not reproduced.

**Recommendation:** Assemble one account-scoped GitHub runtime for a command or long-running serve process: token source/pending renewal, transport policy, and rate-limit observations. Inject it into forge, discovery, project inspection, and Actions. Give account changes/invalidation one owner rather than clearing only publication's forge instance ([internal/engine/forge.go:61](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/engine/forge.go#L61)). This is also a concrete reason to move concrete assembly out of engine into an application composition package.

Preserve `internal/github` versus `internal/forge/github`: authentication/SDK transport and repository adaptation are useful separate responsibilities. Sharing runtime state does not require a global singleton or merging the packages.

### 12. Medium — Tart image administration is exposed through the build-execution provider

The Tart provider implements release selection, image identity, cache retention, remedies, leftover cleanup, guest schemas, staging, VM execution, polling, and result/artifact collection. Its `setup.go` adds image setup and Xcode administration on the same provider. The concentration reaches consumers: setup obtains a build provider for `Status`, `Setup`, `Xcodes`, and `DownloadXcode` ([internal/command/providers.go:23](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/providers.go#L23)); configuration imports the provider package for Xcode choices ([internal/command/config.go:97](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/command/config.go#L97)). Host MacPorts version inspection also resides under this build adapter ([internal/buildenv/tart/setup.go:381](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/buildenv/tart/setup.go#L381)).

**Recommendation:** Put prepared-image inventory/readiness and image administration in an image-management service under the existing Tart infrastructure. Let the build provider consume it for selection and identity. Move host installation inspection toward `macports/installation`, and pure release/toolchain selection toward the corresponding macOS policy. First separate guest DTO conversion and validation into focused files; create another package only when there is a real consumer boundary.

Reuse `tart/host`, `guestssh`, and `provision`; they already own VM safety, connectivity, and provisioning. A small build-provider façade can continue implementing optional `buildenv` capabilities. The objective is to stop image administration from depending on an execution adapter, not to create another general VM framework.

## Smaller follow-ups

- **Make secondary-download transport explicit.** Forge archive links are obtained through the configured GitHub client but their bodies use global `fetch.Client` ([internal/forge/github/archive.go:43](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/forge/github/archive.go#L43)). Actions log downloads instead use the client's HTTP configuration ([internal/buildenv/ghactions/github.go:150](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/buildenv/ghactions/github.go#L150)). An injected API transport/proxy/instrumentation therefore does not consistently govern secondary requests. Supply an explicitly unauthenticated download client; do not forward authenticated SDK transport to arbitrary download origins.
- **Reduce domain work in the downloader.** `distfetch` also validates local patches and derives an own-archives Portfile by stripping generated declarations ([internal/macports/distfetch/download.go:60](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/distfetch/download.go#L60), [internal/macports/distfetch/download.go:298](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/macports/distfetch/download.go#L298)). Move patch resolution beside patch handling and archive-plan transformation beside source preparation; retain download/checksum/mirror/credential mechanics in distfetch.
- **Share PR-status reducers within the GitHub adapter.** REST inspection and GraphQL reading each derive review/check conclusions ([internal/forge/github/inspect.go:40](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/forge/github/inspect.go#L40), [internal/forge/github/reading.go:143](https://github.com/herbygillot/dockhand/blob/832f059ed61355f39a5755be12203d1810fff60a/internal/forge/github/reading.go#L143)). Keep their different acquisition and partial-read behavior, but normalize observations and share the pure precedence rules when changing this area.
- **Split large implementation files only after ownership is clear.** Moving SQL record families into separate files, or separating ecosystem comparisons inside sourcecompare, can help navigation. It does not require a package boundary. Avoid new `util`, `common`, or catch-all service packages.

## Proposed ownership and sequencing

| Responsibility | Suggested owner | Boundary to keep |
| --- | --- | --- |
| Ship transitions and stage gates | One application workflow service | CLI/serve provide intent and receive structured progress/results |
| Check-intent satisfaction | Application policy using model/evidence | Source equivalence and verification coverage remain distinct |
| Evaluated fetch-source identity | MacPorts domain vocabulary | Distinct from ports-tree identity and discovery catalog conventions |
| Corrective edit validation | portedit, using fidelity | Explicit permitted semantic delta before accepting a candidate |
| Concrete source queries and projections | MacPorts source-query adapter | Small consumer interfaces and explicit capability wiring |
| Persisted analysis freshness | Revision-analysis service | Context/policy binding, read-only versus collect, distinct result policies |
| Version probing/session binding | Lower-level Portfile evaluation component | Editing fidelity/authorization stay in portedit |
| Project facts and target discovery | project | MacPorts rendering/policy stay in portcreate/assess |
| Source-file access | Small bounded reader plus adapters | Source confirmation policies stay at their consumers |
| Target result plus observations | buildenv report value | Engine judges policy; adapters own wire transport |
| Account runtime and concrete assembly | Application composition | Forge, Actions, credentials, and transport keep their existing roles |
| Prepared-image administration | Tart image service | Build execution depends on image inventory/provisioning |

This table describes responsibilities, not twelve packages to create immediately. Several can begin as types and focused files in existing packages.

1. **Repair the three highest-priority contracts first.** Preserve decision provenance through ship, complete source identity and invalidate affected persisted results, and make patch correction use full fidelity. These are bounded changes with clear semantic acceptance criteria.
2. **Introduce check-intent satisfaction while consolidating workflow resumption.** Ensure a request for stricter tests or different coverage is either honored or explicitly explained. Preserve batch queueing, commit binding, and conditional pushes.
3. **Extract the concrete source-query adapter.** Move its neutral data contracts first, then implementation, then explicit wiring. Existing behavior should remain visible, including limited-capability fallbacks.
4. **Centralize application assembly and account state.** Keep engine as a façade while services receive only their actual dependencies. This creates a stable place to wire execution, source queries, image management, and credential invalidation.
5. **Refactor repeated semantic operations incrementally.** Migrate project target discovery, lower-level probes, source-file access, and target reporting one consumer at a time. Add context-aware revision-analysis reuse deliberately, including treatment of older records with unknown provenance.

Future validation should target the contracts rather than merely assert the new package graph: CLI/serve decision parity; implicit nonterminal consent versus explicit approval; Git URL/fetch-kind changes; corrective edits that affect siblings or dependencies; same-source checks with different requirements; context changes when reusing analysis; and input-report completeness. These are proposed checks for implementation work, not claims about the existing test suite.

The desired result is a smaller application layer with one owner for each consequential decision, supported by the strong domain and infrastructure boundaries already present. Most of the recommended work can proceed through narrow extractions and explicit values rather than a broad rewrite.
