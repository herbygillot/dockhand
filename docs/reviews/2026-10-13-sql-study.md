# SQL study, 2026-10-13

Read at `9b8bb0cb` (main, "docs(roadmap): the coalesced roadmap's decisions 2 to 5"). This study covers every statement dockhand sends to SQLite: 30 migrations, about 50 queries in `internal/store/sqlite/`, and every caller outside the store. It asks three questions. Is each query efficient and the right scope? Does each caller ask the database the right question? And should the SQL logic be concentrated, split, or simplified? Recommendations are placed against the coalesced roadmap's order (v0.4.0 parts 1 to 3, then v0.5.0, layer 1).

There was an earlier study, [2026-09-28-sql-review.md](2026-09-28-sql-review.md). All ten of its findings are fixed except one: the plan decode in `RecordResult`, which it said to leave alone without a measured need. This study doesn't repeat those findings. It covers what was added since: D6's pruning, assessments, change records, dependency archives. It also covers how the engine and command layers use the store, which the earlier review didn't look at.

## The short answer

1. **One real defect, P1: daily cleanup's `PruneHistory` goes quadratic.** On a synthetic database the size of a year of heavy serve use, it passes the 30-second operation timeout and rolls back. At a quarter of that size it already takes 23.8 s. When it fails, `Cleanup` stops at that step, so archive and journal pruning never run either, and nothing is pruned again. While it runs it holds the writer lock, and every other writer, a running check's result included, gives up after the 5-second busy timeout. Three query changes and four small indexes bring it to **3.9 s at year scale for the whole backlog** (S1). This isn't live at today's database sizes. It belongs in v0.4.0 part 1, next to the cleanup.go move that already touches this code.
2. **Every other query is an index lookup** taking 0.03 to 0.6 ms at year scale. Two daily window queries take about 1 s. Three indexes are dead or missing (S3).
3. **The N+1 reads and polling loops the callers make are not a performance problem.** A read transaction costs 37 µs, and a one-record read 72 µs. Status's six-plus transactions per branch cost milliseconds. I recommend **not** rewriting them for speed.
4. **The real cost is in code organization.** The same questions are answered three to five ways: "the latest check of a branch", "runs of a tree", "results of a run", "who holds this run". The answers are assembled from one-record transactions in Go loops, and a few of them disagree. The fix is a handful of named store reads that do the join and the limit in SQL. The judgment stays in Go. Each one goes in at the roadmap item that already rewrites its callers (O1 to O8), so nothing is opened twice.
5. **Writes are where the time goes**, at about 4 ms per commit on macOS with fullfsync. A check commits once or more per target, plus every progress line. That is fine today. It becomes a cost when **live progress from the guest** (v0.4.0 part 3) multiplies progress events, so progress should be coalesced there (S4).

## Method

- **Every production query explained and timed** through the store's own `Open`, so with the real migrations, pragmas, and `PRAGMA optimize` statistics. The synthetic database matches the earlier review's year of heavy serve use, extended to the newer tables:
  - 300 branches (one third open), and 6,000 each of revisions, plans and runs
  - 18,000 executions, 200,000 results, 200,000 inputs, 20,000 archives, 5,000 dependency archives
  - 100,000 events, 18,000 assessments, 18,000 change records
  - edits, checkpoints, reviews, sessions and leases
- **A quarter-scale copy** was used to find where cleanup crosses its timeout.
- **The callers**, every `View` and `Update` outside `internal/store`, were mapped by a teammate and checked against the code at the lines cited.
- **The roadmap and the earlier review** were read by a second teammate for queued work that touches the store.
- **The probe** is [2026-10-13-sql-probes.patch](2026-10-13-sql-probes.patch), a test file for `internal/store/sqlite/`. It measures and asserts nothing. Run it in a scratch worktree, after `git apply docs/reviews/2026-10-13-sql-probes.patch`, with `STUDY_DIR=<dir> go test -run 'TestZZ(Study|Prune|Steps|Overhead)' -v ./internal/store/sqlite/`.
- Timings are from this Linux container (vendored SQLite through modernc). On Linux, fsync is cheaper than macOS's F_FULLFSYNC, so commit costs below use the earlier review's M5 Max figure of about 4 ms. Query plans and the ratios between timings carry over.

## Findings

### S1 [P1]: `PruneHistory` is quadratic in history, and its failure stops all pruning

**Where:** `internal/store/sqlite/records.go:903-953`. It is called from `Engine.Cleanup` (`internal/engine/clean.go:743`), daily from serve (`engine/serve.go:636`) and from `dockhand clean`.

Three of its eight statements visit rows in proportion to the product of two tables' sizes:

- **executions:** `NOT EXISTS (… r.execution_id=e.id OR r.reused_from=e.id)`. `reused_from` has no index, and the `OR` stops SQLite using the primary key, so the plan is `CORRELATED SCALAR SUBQUERY … SCAN r`, a walk of every result for each candidate execution. After the results step has removed an ended branch's results, almost no candidate finds a match early.
- **results:** `(execution_id, target_id) NOT IN (SELECT … FROM (reusableBuilds))`. The row-value `NOT IN` over the window subquery is probed through an automatic index keyed on `newest`, not on the pair. As written it takes **30 s at year scale even with every other fix in place**.
- **plans and revisions:** `NOT EXISTS (… u.plan_id=p.id)`, `u.revision_id=v.id`, `p.revision_id=v.id`. None of these columns is indexed, so each candidate scans `runs` or `plans`. Deleting a plan or a revision also makes SQLite's foreign-key check scan the same unindexed child columns. The earlier review was right that "foreign keys whose child columns lack indexes cost only when a parent row is deleted". D6 has since made plans, revisions, runs and executions parents that get deleted.

**Measured** (store `Open`, real `PruneHistory`, one `Update`):

| Scale | As written | With the fix |
|---|---|---|
| quarter (50,000 results, 4,500 executions) | 23.8 s | not run |
| year (200,000 results, 18,000 executions) | **timed out at 30 s and rolled back**; 4 min 45 s with no timeout | **3.95 s** for a whole first-time backlog |

The year-scale steps, run in order on copies of the same database:

| Step | Rows | As written | With the fix |
|---|---|---|---|
| results | 130,395 | 28 s | 2.9 s |
| executions | 6,532 | **4 min 6 s** | 0.11 s |
| runs | 2,161 | 0.05 s | 0.06 s |
| plans | 2,161 | 3.8 s | 0.05 s |
| revisions | 2,161 | 6.3 s | 0.04 s |
| inputs | 130,395 | 0.71 s | 0.76 s |

A daily run in steady state removes about a day's worth of rows, so it takes a fraction of that.

**What failure does:**

- `Cleanup` returns at "cleaning build history" (clean.go:756) before `PruneArchives` and `PruneJournal` (clean.go:760-). So once history passes the threshold, kept archives on disk and the event journal stop being pruned, and every later cleanup hits the same timeout. The failure feeds itself.
- While it runs, the transaction holds `BEGIN IMMEDIATE`. Other writers wait at most the busy timeout, 5 s (`sqlite.go:132`; engine opens with defaults, `engine.go:176`), and then fail with `ErrUnavailable`. That includes a check's `Record` of a target result, its heartbeats, and serve's own writes. Serve runs cleanup while its checks run.

**Fix** (no change to what is pruned):

1. A new migration, `031.sql`, adding the foreign-key child indexes and the one `reused_from` index:
   ```sql
   CREATE INDEX run_plan ON runs(repository_id, plan_id);
   CREATE INDEX run_revision ON runs(repository_id, revision_id);
   CREATE INDEX plan_revision ON plans(repository_id, revision_id);
   CREATE INDEX result_reused ON results(repository_id, reused_from);
   DROP INDEX result_archive;  -- S3
   ```
2. **executions:** split the `OR` into two `NOT EXISTS`, one per column, each served by an index. Without `result_reused`, the form `e.id NOT IN (SELECT execution_id …) AND e.id NOT IN (SELECT reused_from … WHERE reused_from<>'')` also measured 0.16 s.
3. **results:** compute the keep-set once, `WITH keep AS MATERIALIZED (reusableBuilds) … AND NOT EXISTS (SELECT 1 FROM keep k WHERE k.execution_id=results.execution_id AND k.target_id=results.target_id)`. That is 2.9 s where the original took 30 s.
4. **Tests:** add the prune statements to `TestHistoryIsReadThroughIndexes`. Assert that no plan line contains `CORRELATED` together with `SCAN`, so a later edit to the wording can't bring a scan back. None of the prune statements has a plan test today.

**Roadmap slot:** v0.4.0 part 1, *Hygiene*, with the move of cleanup's code into its own `cleanup.go` and X5 ("the store stops inventing `EndedAt`"), which open the same functions. It doesn't need v0.3.0: today's databases are far below the threshold, and the fix is a new migration plus query text.

### S2 [P2]: a write transaction must stay well under the 5-second busy timeout

The store's two limits disagree. A transaction may run for 30 s (`OperationTimeout`), but a waiting writer gives up after 5 s (`BusyTimeout`). So any write transaction longer than 5 s fails the writers queued behind it. After S1, cleanup's longest transaction is a first-time backlog of about 3 to 4 s at year scale. Its second longest is `PruneArchives` at about 1.3 s.

**Recommendation:** make "every write transaction stays under a second at year scale" a stated rule beside the plain-index rule in development.md. Hold to it in two ways:

- Prune the history of ended branches in bounded chunks of branches, so a large first-time backlog commits a chunk at a time.
- The planned **"forget an archived branch for good" (`clean --delete`, v0.4.0 part 3)** needs exactly PruneHistory's foreign-key-ordered delete, scoped to one branch. Only `dependency_archives` cascades. So write the delete once, as a store-internal function over a set of branch IDs. `PruneHistory` calls it for "ended before T", in chunks, and forget calls it for one ID. That gives one ordered delete instead of two that would drift apart.

**Slot:** the chunking with S1, in v0.4.0 part 1. The shared delete is shaped in S1 so that part 3's forget reuses it.

### S3 [P3]: three indexes are dead or missing, and two lookups ignore an index that exists

- **`result_archive` is dead.** D6 rewrote `PruneArchives` around `reusableBuilds` and `openBranchArchives`, and no query filters `results.archive` by value any more. It costs a write per result. Drop it in `031.sql`.
- **`branch_pull_request` exists, but nothing reads through it.** `PullRequestBranch` (engine/selector.go:40) and `AdoptPullRequest` (engine/branches.go:610) read every branch and match the PR number in Go. A `Reader.BranchTracking(prRepository, number)` uses the unique index. Mostly this gives one definition, not speed (O5).
- **Merged names have no index.** `MergedBranchNamed` scans `branches`, because `branch_name` is partial (`WHERE state <> 'merged'`). The queued 1c item "a merged, cleaned, closed, or archived branch's name is said from its record" adds a name lookup across all states. A plain `branches(repository_id, name)` serves both. The table is small, so this is optional; take it only if that item's query wants it.

**Slot:** with S1's migration. The PR lookup goes with the 1c Branches items.

### S4 [P3]: commits per check, which matter once progress is live

Each write transaction is one fsync, about 4 ms on macOS. Per check today (engine/runner.go, engine/archives.go):

- per target: `Record` (inputs + result + event), 1 commit. This is correct: it's the checkpoint.
- per kept archive: `Keep` is a `keptArchive` View plus one `KeepArchive` Update. **`KeepDependency` makes two Updates**, `KeepArchive` and then `KeepDependencyArchive` (archives.go:93, :201), which can be one transaction.
- per execution: `Refer` and `Observe`, 1 commit each.
- **every Info-level `Progress` line**: 1 fenced commit (`driver.emit`, runner.go:246). There are 28 call sites across the providers.

A 300-target check makes roughly 1,000 commits, about 4 to 5 s of writer time over a run that lasts hours. That's fine. **Live progress from the guest** (v0.4.0 part 3) adds a line per port phase, which could reach thousands of commits per check. While they flow, `watch` redraws the whole status every second (see O6).

**Recommendation:**

- With live progress, coalesce progress per execution: at most one progress commit per second, carrying the latest line, and flushed on the next state change.
- Make `KeepDependency` one transaction when the 1c dependency-archive items open archives.go.
- A separate connection with `synchronous=NORMAL` for progress was considered and not recommended: it adds a second durability mode for little gain over coalescing.

**Slot:** v0.4.0 part 3, live progress, for coalescing. v0.4.0 part 1, the *Check and evidence* dependency-archive items, for `KeepDependency`.

### S5 [P3]: noted and left alone

These were measured, and I recommend not changing them:

- **Polling.** The foreground follower reads `RunEvents` every 200 ms. Each running driver's `watchCancel` reads `Run` every second. Serve's 2 s tick runs a no-op `Fenced` plus `Runs(active)` plus a `Holder` per run. Sessions write a heartbeat every 5 s. At 40 to 70 µs per read and no sync for a no-op, this is noise. It shouldn't be rewritten for performance.
- **Observer sessions.** `status`, `queue` and `watch` write an observer session and end it, 2 commits each. That's about 8 ms on macOS. It's harmless; leave it.
- **`RecordResult` decodes the whole plan for each result.** This is the earlier review's finding 5, still open. It costs about 0.85 ms for a 300-target × 6-environment plan. Revisit only if `ship`'s batches produce much larger plans.
- **`Archives()`** reads all 20,000 rows once a day for the orphan-file sweep. That is the right scope for it.
- **`PruneArchives`' two window queries** cost about 1 s daily, linear in results. That's acceptable. S1's materialized keep-set is the same subquery. Sharing it across cleanup's two transactions isn't worth a temp table.

## Code organization: where SQL-backed answers are duplicated or assembled the long way

The pattern is the same everywhere. The store offers one-record and one-table reads. The engine answers a question by composing several of them, often in separate transactions, and filters in Go. Then a second or third caller answers the same question again, slightly differently. This costs little time (S5). It costs consistency:

- Answers can disagree. Five definitions of "latest check" exist, for instance.
- Reads spread over separate transactions can see different states, such as a check finishing or cleanup pruning between them.
- Every new feature has to find the right existing helper.

The recommendation keeps the store's single contract (D5) and its rule that methods are specific to records. It adds a few **named reads for the questions dockhand asks**, which do the join, the filter and the limit in SQL. It keeps every **judgment in Go**: evidence (`internal/evidence`), liveness (`coord`), and later readiness (`branchstate`). The SQL loads; the Go decides. No new package, query builder, or dependency is needed.

### O1: one definition of "a branch's latest check", and "runs of a tree" in SQL

There are five definitions today:

- `engine/status.go:233-245`: the first run not active, not canceled, not a baseline. It then switches to the tree's newest check.
- `engine/baseline.go:191`, `latestCheck`: the first finished run that isn't a baseline.
- `command/queue.go:426`, `latestCheckHere`: `Runs{Branch, Limit:1}`, which **counts baselines and canceled runs**. It's used by `logs`, `retry` and `wait`.
- `command/watch.go:309`: `Runs` with **no limit**, and with no branch it reads **every run in the repository**, all to take `runs[0]`.
- `engine/retention.go:92`: the newest per branch, for log retention.

`PruneHistory` has a sixth, "each branch's newest run", in SQL.

Two related helpers read whole tables and join in Go. `runsOfTree` (engine/evidence.go:249) reads every revision and every run of the branch to keep those whose revision has the tree. Status calls `treeRuns` twice per branch, and `Runs` a third time.

**Shape:** add `Tree model.ObjectID` and `Baselines bool` (include baselines, default false) to `store.RunFilter`. The query joins `revisions` by primary key and filters on `tree_id`. Then "latest check" is `Runs(RunFilter{Branch, States: finished, Limit: 1})`, defined once in the engine as `LatestCheck(branch)`. Every caller uses it, or says on purpose why it differs. Whether `logs` and `retry` should land on a baseline or a canceled run is a product question that should be answered once.

**Slot:** v0.4.0 part 2, item 5, where `queue` and `watch` fold into `status`. That rewrites `latestCheckHere` and watch's `l` key anyway. Status's own definition moves when layer 1's `branchstate` (4.5) takes status's verdict, as the roadmap already keeps status changes minimal until then.

### O2: one loader for "a check's records"

Four places assemble "a run's executions and each one's results":

- `loadCheckWith` (engine/evidence.go:194)
- `driver.environment` (engine/runner.go:404), filtering executions by environment in Go
- `Logs` (engine/status.go:419)
- `finishCanceled` (runner.go:150), executions only

Evidence adds, per run:

- `Plan`, read twice (evidence.go:110-124, then in `loadCheck`)
- `Results` per execution
- `Execution` plus `Run` per reused origin (evidence.go:210-214)
- `Inputs` per passed cell (:157, :226)

**Shape:** `Reader.Check(run) (store.Check, error)` returns the run, its plan, its executions, and its results grouped by execution, with each reused result's origin execution joined (as `Reusable` already does) and the inputs records it names. That is a few queries in one call rather than one per row. `evidence.Judge` and the driver keep their logic. Evidence keeps its two phases: plan environments, then provider identities read outside any transaction, then records, as the store rule requires.

**Slot:** `ship`'s engine (v0.4.0 part 2, item 3) makes the check pipeline one enqueue path and rewrites the driver's reading of its own executions, so the loader is introduced there. Evidence and `Logs` adopt it in layer 1's 4.1 (one revision analysis), which re-keys evidence by tree and base and opens evidence.go anyway.

### O3: command-layer summaries read in one transaction

`Engine.Run`, `Revision`, `Plan` and `Branch` (engine/runner.go:1141-1167, engine/branches.go:572) each open a whole transaction. Commands call them in loops:

- `queueRow` (command/queue.go:84-105) makes four Views per run, four more with `--json` via `checkResult`.
- `checkResult` (command/check.go:766-780) makes four separate Views.

The four reads can see four different states.

**Shape:** one engine call, `RunSummary(run)` or the status row, reads branch, revision, plan and holder in one View. **Slot:** v0.4.0 part 2, item 5, which replaces `queue`'s rows with status's.

### O4: run holders read with the runs

A `Holder` View per run (`coord.go:348`) is called from:

- `Candidates` (runner.go:1243), every 2 s in serve
- `ServeState` (serve.go:1033)
- `Stopped` (status.go:97)
- `queueRow`
- `judgeLeftover` (clean.go:557)
- `wait` (queue.go:143)

**Shape:** a `coord` helper that takes the runs and reads all their leases and holders' sessions in the caller's View (`Holders(reader, resources)`). The liveness judgment stays in `coord`. **Slot:** with O3 in part 2, item 5. Serve's `Candidates` adopts it in item 4 (`serve.ship_to`), which reworks serve's queue.

### O5: small single-question reads that replace whole-table scans

Each is local. Take each one when its caller is opened anyway:

| Question | Today | Read | Slot |
|---|---|---|---|
| Branch tracking PR #n | `Branches` scan, twice (selector.go:43, branches.go:611) | `BranchTracking(repo, n)` via `branch_pull_request` | 1c *Branches* |
| A branch's name in any state | `BranchNamed`, then `MergedBranchNamed`, then `followRenames` | one lookup across states (S3's index) | 1c *Branches*: "name said from its record" |
| Newest applied, unrestored checkpoint | `Checkpoints` scan, twice (tidy.go:982, history.go:192) | `LatestCheckpoint(branch)` | when touched |
| Change records of a port across open branches | one View per open branch, all trees (`PortBranches`, update.go:784-829) | `ChangeRecords` filtered by directory over open branches' current trees | 1c *Branches*: "a branch started for a port", which rewrites `PortBranches` |
| A kept archive, per digest during reuse | `keptArchive` opens a View per call (archives.go:38; reuse.go:86, :113, :288) | read inside `earlier`'s View, or `Archives(digests)` | 1c *Check and evidence* dependency-archive items |
| Events at Info level for `watch` | `Events` pages all levels; filtered in Go (watch.go:102) | `Events(after, limit, minLevel)` | part 2, item 5 |

### O6: watch redraws the whole status whenever an Info event arrived

`watch` reads every new event each second, keeps the Info ones in Go (command/watch.go:101-110), and redraws the whole status when any arrived (:263). Each check `progress` line is one. So while a check runs, watch recomputes every branch's status once a second. With live progress that becomes the steady state for the whole of every check. **Shape:** redraw only on state-changing event kinds, or only the branch the event names, with progress shown in place. That needs C4b's `EventKind` constants (layer 1, 4.5). A small allow-list of kinds is enough before then. **Slot:** part 2, item 5, where watch folds into status. It must land before part 3's live progress.

### O7: the revision's analysis read once

`revisionChanges` re-reads `Branch(id)`, which every caller already holds (engine/changes.go:37). It is called twice in `PlanSubmit` (submit.go:282, and again via `revisionAssessments`, assessment.go:73) and twice at the end of a check. `revisionChanges` and `revisionAssessments` then write in two transactions (changes.go:110, assessment.go:87). This is exactly what layer 1's **4.1, one revision analysis keyed by tree and base**, replaces. The recommendation is only that 4.1's single loader reads change records and assessments in one View and writes both in one transaction. **Slot:** v0.5.0, 4.1. Nothing earlier.

### O8: serve's PR refresh, and status writing PR CI

`RefreshPullRequests` (engine/follow.go:99) makes one `Update` per tracked PR, and always writes, because `Observed.At` changes. The queued 1c item **"status reads pull requests' CI itself"** makes status a writer of the same column. **Shape:** one shared function, which status and serve both call. It observes every PR outside any transaction, as the store rule requires, then writes the changed ones in one `Update`. **Slot:** v0.4.0 part 1, the 1c *Status* item.

### Splitting the store's files

`records.go` is 979 lines and mixes branch, run, execution, result, archive and pruning code. When S1 is done, move the prune functions and their shared keep-set and ordered-delete into `internal/store/sqlite/prune.go`, as the engine moves its cleanup into `cleanup.go` in the same batch. I'd leave the other splits by record family until a batch touches them; they are mechanical and buy little.

## What I'd push back on

- **No ORM, query builder, sqlc or generated code.** The library survey already rejected these, and nothing here needs them. The queries are short, fixed text, held as named constants with plan tests.
- **Don't split the store package or add a generic query layer.** D5 and the store's "methods specific to their records" rule stand. The named reads above are record-specific.
- **Don't move model rules into SQL.** No evidence judgment, readiness, `ReplacedBy` or liveness in queries. The earlier fix note declined JSON functions in SQL for the same reason.
- **Don't rewrite the N+1 reads or the polling for speed.** They're measured at microseconds. Concentrate them only where O1 to O8 put them, because the roadmap rewrites those callers anyway. That is the low-churn path to one definition per question.
- **No plan-decode cache, prepared-statement cache, or second durability mode.** None is justified by a measurement.

## Appendix: the index rules this leaves

- Plain indexes, not partial ones, as the earlier review set.
- **New:** once a table's rows are deleted by a parent's prune, every foreign-key child column referring to it has an index, because SQLite's own foreign-key check scans for children on every parent delete.
- **New:** no write transaction is expected to exceed about a second at year scale (S2). Every prune and window statement has an `EXPLAIN QUERY PLAN` test that rejects a correlated `SCAN`.
